软件 MCP 和物理工具调用差在哪

结论：协议上没区别，语义上几乎是相反的。

MCP 把"怎么调用"标准化了——工具名、JSON Schema、返回值。这是它真正的价值。但它没有定义"调用之后世界变成什么样"。

同一套 tools/call，可以是"查一下这条记录"，也可以是"伸手进柜子抓那个杯子"。最核心的一句：软件工具的返回值可以证明调用成功；物理工具的返回值只能证明调用被执行了。

因为软件系统是静止的：你不调用它，它就不动。物理世界不是——东西会滑落、会被移动、会被人拿走。

这个差异推出五条。

一、做错了回不去。事务可以回滚，机械臂不能 rollback——返回成功也只说明命令执行完了，不说明杯子真的夹住了。

二、幂等性不是想加就能加的。软件里加个幂等键就解决了；物理世界里"前进一米"发两次，它真的走两米。三、结果不确定时不能重试。软件超时重发即可；物理动作超时，你不知道它做完了没有——可能刚启动，可能做了一半，也可能已经做完。

四、响应时间差三个数量级。查数据库是毫秒级，一次抓取是几十秒到几分钟。

说说我们做了什么。

工具目录 30 个工具里，14 个标了 mutates_world：返回成功不算完成，必须有新的观测证据。另外 14 个标了 idempotent=false：重发就是重做一遍。

有个设计我特别在意：标了"改世界"却没标"有副作用"的工具，加载时直接报错拒绝启动——那等于一边说不需要确认，一边让闭环等一份永远不会到来的证据。

状态机上，返回成功之后不是"完成"，而是一个独立状态：待取证。必须附上命令之后采集的新鲜证据才算完成。

失败也不笼统重试，而是分七类：瞬时、感知、规划、许可、资源、参数、结果未知，每类唯一安全的下一步都不一样。

其中"结果未知"是核心。超时、断连、崩溃之后物理结果无法确定，它不意味着失败也不意味着成功，处置只有一个：先对账，禁止自动重试。不认识的错误码也一律归到这一类。默认值选"不许重试"，系统才会在遇到没见过的故障时停下来。

证据还要过四道校验：有观测 ID、有采集时间、采集晚于命令下发、来源没过期。第三道挡掉的是最隐蔽的错误：拿旧照片当完成证据。

最后说 MCP 的价值：它把接入标准化了。但决定可靠性的是接入层下面的语义、校验、验证和恢复——这些 MCP 管不着，必须机器人系统自己定义。
