这是"深入理解分布式机器人AgentOS"长文系列的第 1 期，先看总体架构。
我做的是一套机器人的"操作系统"：你对着控制台说一句中文，它自己拆任务、走到地方、看懂现场、伸手把活干完，每一步都留下能回放的证据。

一、它到底是什么：不是遥控台，是分布式 AgentOS

机器人圈子有两个常见起点：一个是"遥控器加脚本"，一个是"让大模型直接输出关节角"。这条路线两个都不选。

它把自己定位成分布式的 agent 控制面，加上面向具身机器人的边缘运行时，有两种部署形态：

一种是云端形态：浏览器控制台 → Fleet API → 任务服务／协调器／事件总线 → WorldHub 世界模型加 Harness 裁决 → 经 mTLS 下发到 N 台 Edge（每台一个机器人）→ Robot Runtime → 实机或仿真工具。

一种是离线形态：控制台 → 本地 Agent 加 SQLite → 同一个 Robot Runtime → 实机或 MuJoCo 仿真。

关键点在这里：两种形态共用同一套 Runtime 契约、工具目录、观测契约和世界快照格式。也就是说，"大脑"可以装在机器人身上离线跑，也可以接云端调度多台；换一台机器人、换一种本体，任务和证据链都不用重写。（当前主线是一台机器人在装修家庭里把活干完，云端多机是仓库里已经实现的扩展路线。）

二、整体架构：八层，各管一件事

我按"从人到电机"的顺序讲，每一层都能在仓库里找到对应目录。

第一层，交互层：web/ 和 console/。网页控制台里有工作台（说一句话、看机器人此刻的画面）、任务记录、任务全过程回放、SLAM 建图、我的机器人、开发诊断。另有 robot/mcp/ 作为给外部智能体的统一入口；通过它创建的任务依然要人工审批，也不暴露裸关节动作。

第二层，理解与规划层：agent/ 和 orchestration/。把一句中文变成可执行的任务图。设计上很克制：已知意图优先走确定性解析，歧义要求澄清，只有剩下的自然表达才交给可选的大模型；规划器另有一条确定性后备路线。模型不接触坐标、轮速和关节角，它只说"去厨房""拿杯子"。

第三层，任务与协调层：tasks/、fleet/coordinator/、fleet/eventlog/。任务是聚合根，版本不可变：需求变更叫改版，会给出保留哪些步、改哪些步、取消哪些步，确认时必须带上当前版本号和幂等键，防止并发覆盖。协调器单写派发：领取步骤、分配机器人、检查租约、只在安全点切换版本、做资源监护权转移与恢复。

第四层，世界模型与裁决层：core/worldmodel/、core/observation/、core/harness/。这是我最喜欢的一层。WorldHub 把各个来源的状态合并成带单调版本号的世界快照，按来源序列去重，陈旧或者自相矛盾就"失败关闭"，不猜。观测注册表会预先声明"应该观察什么、多久算过期"。最后 Harness 拿世界证据去核对每一步的后置条件，输出原因、证据编号和世界版本——它不接受"工具调用成功"这一个信号。

第五层，执行与安全层：edge/、edge/runtime/、robot/gateway/。Edge 负责连接、执行工具、上报观测，断网重连、幂等；Robot Runtime 提供统一的工具执行、观测流、取消和急停，仿真和实机之间只替换适配器。每条命令必须同时满足：截止时间、审批、工具目录版本、世界坐标系版本、任务版本、资源 fencing、幂等键。安全监督和执行日志也落在这一层：软件状态永远低于实体急停和硬件限制。

第六层，机器人能力层：skills/ 和 robot/gateway/。导航、抓取、放置，以及三个"验证"工具（到位、抓稳、放好）。工具目录用大白话描述用途和安全参数，智能体只能调用当前版本里已注册的工具。标定、稠密 SLAM 建图、导航规划和避障，都在这里作为注册服务提供。

第七层，适配与本体边界：examples/robots/、sim/mujoco/、robot/ros2_ws/、policy/sidecar/。新本体接入走一条统一路径：先声明结构和传感器，再用厂商 SDK 或 ROS 2 实现动作，最后复用原有审批、租约、日志、取消和急停。策略（视觉语言动作模型、模仿学习、强化学习）通过 policy/sidecar 接进来：候选动作先过身份与数值边界校验，再进 Runtime 执行，最后还是由 Harness 确认真实世界发生了什么。

第八层，契约与协议层：proto/robot/v1、proto/fleet/v1、python/tangying_robot_proto。跨语言、跨进程的硬约定：Runtime 接口、世界快照、三维重建、机器人数描述。接口不变，本体可换——这就是"换机器人不用重写任务"的底气。

三、一句话任务，在系统里怎么走完

第一步，你提交自然语言，任务服务创建第 1 版，未审批。

第二步，控制台先复述它理解到了什么、准备怎么做，你确认之后才置为已审批。

第三步，协调器领取步骤，检查机器人租约、工具目录版本、世界新鲜度、资源归属。

第四步，命令经 Edge 下发到 Runtime，用命令号加幂等键去重，全过程流式回报状态与观测。

第五步，观测回到 WorldHub，投影成新的世界快照版本。

第六步，Harness 用它核对这一步的后置条件，满足才判定完成，资源监护权换新的 fencing token 交给下一台。

第七步，所有步骤满足、最终资源归属正确，任务才算成功。

中途你说"改成放到右边垫子上"，就是第 2 版提案加安全点切换；中途断电重启，就按持久化的事件与快照恢复——恢复后只接受更新的证据，旧观测不会变成新证据。

四、第一次打开仓库，按这个顺序读

一是 README.md，一条命令加一句话任务，先看它想干什么。

二是 docs/README.md，文档索引按"你想做什么"分组：装机、标定、建图、接实机、发版。

三是 docs/production/architecture.md，完整架构，就是本期头图那张。

四是 docs/development/single-robot-loop.md，当前主线的感知、执行、恢复链路。

五是 core/closedloop/，闭环契约的判定与失败分类，全项目最该先读的代码。

想直接跑：make setup，然后 make home-furnished，打开 http://127.0.0.1:8897/ 。仿真不需要显卡；演示默认走确定性解析，不配 API Key 也能跑通完整闭环。开发或实机要用 LLM 理解更多自然表达时才需要自备 Key（只放本机，不会发给机器人）。
