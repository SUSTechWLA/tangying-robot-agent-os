## 2. 五个故障剧本：逐条出处

文案第四节的五个剧本，全部对应仓库里可运行的测试：

| 剧本 | 文案里的说法 | 测试 / 实现 |
| --- | --- | --- |
| ① 网络断 30 秒 | 已发出命令结果未知时，**不许猜**，更不能靠"改需求换个版本"绕过 | `edge/agent/recovery_test.go` · `TestUnknownPhysicalStepCannotBeBypassedWithAnotherRevision`：步骤已开始但结果未知时，`Run` 返回 `ErrPhysicalOutcomeUnknown`，且断言 `manipulation.pick` 调用次数为 **0**（真的没有动手） |
| ①（续） | 边缘断线重连续租 | `fleet/registry/registry_test.go` · `TestRegisterAndHeartbeatRenewLease`、`TestDeviceGoesOfflineAfterLeaseExpiry`（心跳续租；租约过期即判离线） |
| ② 指令重复下发 | 命令号 + 幂等键去重，重复送达返回同一结果而不是重放动作 | `edge/runtime/dispatch.go`（按命令号与幂等键去重） |
| ②（续） | 低 fence 的完成被拒；完全相同的重复是幂等的 | `fleet/coordinator/revisions_test.go` · `TestCompletionRejectsLowerFenceAndExactDuplicateIsIdempotent`：`FencingToken-1` 的上报返回 `ErrIntentIdentityConflict` **且不写入任何事件**；重复上报同一完成不增加事件数 |
| ③ 消息队列挂了 | 事实先落盘再投递，队列宕机不破坏任务图，发布者恢复后重新投递 | `fleet/coordinator/coordinator_test.go` · `TestQueueOutageLeavesCommittedHandoffOutboxForRecovery`（Redis 不可用时 outbox 里留下可恢复记录，任务图 `StatusReady` 未被改坏）、`TestOutboxDispatcherRecoversAfterPublisherReturns` |
| ④ 协调器换主 | 只有持有当前 fence 的 leader 能推进，旧主写不进 | `fleet/coordinator/coordinator_test.go` · `TestOnlyCurrentFencedLeaderCanAdvance` |
| ④（续） | 租约过期可被他人获得，但 token 继续单调增加、绝不回退 | `fleet/lease/manager_test.go` · `TestExpiredGrantCanBeAcquiredButTokenKeepsIncreasing`、`TestTransferInvalidatesPreviousFencingToken`（转移后旧 token 校验返回 `ErrStaleFencingToken`） |
| ⑤ 观测迟到 / 丢失 | 游标落后超过保留窗口就**明确要求重新同步**，不给有洞的历史 | `fleet/worldhub/hub_test.go` · `TestHubRequiresResyncWhenRetentionCannotCoverCursor`：保留窗口 2、游标 1、已推进到 4 时 `Subscribe` 返回 `worldmodel.ErrResyncRequired` |
| ⑤（续） | 同一观测重复投递只发布一次 | 同文件 · `TestHubPublishesOnlyAcceptedWorldRevisions` |
| ⑥ 任务改需求 | 新版本 + 安全点切换，保留/修改/取消逐条列出 | `tasks/service.go` 的 `CurrentRevision` / `RevisionState` 与 `fleet/coordinator/revisions.go` |

## 3. 断网到底会怎样（**最容易说过头的一条，务必按这里写**）

一次自查中我发现初稿写成"断网后边缘继续跑"，**这是错的**，已全量修正。仓库的真实口径是 **断网停止**：

| 说法 | 依据 |
| --- | --- |
| 不向离线机器人分派新步骤 | `docs/production/operations-and-failures.md` §4 故障处置表：机器人离线 → 设备 OFFLINE、步骤等待，安全不变量为"**不向离线机器人分派**" |
| 网络恢复后自动重新注册 | 同上表：恢复列为"网络恢复自动注册；**持物时现场处置后提高 fencing**" |
| "断网停止"属于实机验收项，不是仿真结论 | `docs/production/testing-and-acceptance.md` §"仿真通过后仍需"清单里列有 **断网停止**、命令幂等、旧 fencing 拒绝；`docs/production/release-evidence.md` §79 要求客户现场重新演练"断网停止、旧 fencing 拒绝" |
| 唯一实际速度执行通道与停止检查在 Runtime | `docs/production/architecture.md`：Runtime 保有唯一实际速度执行通道及停止检查 |
| 边缘断线会重连并退避 | `edge/cloudclient/link.go:97`（注释即"断线重连"）、`:113`（记录 `fleet link disconnected` 并按 backoff 重连） |
| 租约过期即判离线 | `fleet/registry/registry_test.go` · `TestDeviceGoesOfflineAfterLeaseExpiry` |

**正确表述**：控制环本来就在本地，所以断网不会让机器人失去"停下来"的能力；慢环负责在线时把顺序与证据理清楚，**断网期间不派新活，恢复后对账，持物时提高 fencing**。

**不要写**："断网后机器人还能自己接着干"。那既不是当前实现，也不是这套设计想追求的东西——失联但仍在动的机器人，恰恰是分布式系统最该消灭的"没人知道的写者"。

## 4. 持久化与恢复：做到哪一步，没做到哪一步

这一节是**本期最容易被质疑的部分**，所以逐句给出边界。

| 文案里的说法 | 实际依据 | 边界 / 没做到的部分 |
| --- | --- | --- |
| "事实先落盘再投递" | `fleet/eventlog`、`fleet/mysql` 的 Task/Revision/Event/Outbox 适配器；`fleet/mysql/store.go` 的 `ClaimOutbox` | 只覆盖单主进程；不提供跨主机共识，也不提供跨存储事务 |
| "世界快照可持久化，重启后仍能按版本去重" | `fleet/worldhub/persistence_test.go` · `TestPersistentHubRecoversRevisionDeduplicationAndStaleEvidence` | 同机单主 checkpoint |
| "保存失败就失败关闭，不会发布半个快照" | 同文件 · `TestPersistentHubNeverPublishesFailedCheckpointAndRequiresRestart` | 需要人工重启，不自动降级 |
| "不会多开 writer 抢同一个文件" | 同文件 · `TestFileStoreExcludesAnotherWriterAndReleasesLock` | 文件锁；损坏或保存失败应失败关闭，**不允许**删快照或降 token 来"恢复服务" |
| "断电重启能回到原来的地图与任务账本" | Local 形态使用 SQLite；地图 `active-map.json` 与激活时恢复 | Local 是单机单进程形态 |

**明确写在"仍须独立验证"清单上的**（`docs/distributed-agentos.md` §"仍须独立验证的范围"），文案里对应第八节的坦白：

- leader fencing 与所有业务提交的同存储原子校验；
- MySQL、Redis、世界投影与物理结果之间可恢复的资源转移 saga；
- 数据库 / 队列切主、网络重排和长期多进程故障验证；
- 实机传感器质量、坐标标定、匹配策略、实体急停、停止响应和受限任务验收；
- 目标终端可见帧率、现场容量、备份恢复和长期运维。

> 引用这些时的口径：**不要说"已经高可用"**，说"单主进程重启范围内的一部分状态恢复已经实现并有测试；跨主机共识与跨存储事务不在已完成范围"。
