为什么机器人一定要做分布式

这是"从零到一入门机器人开发"系列的第 2 期。第 1 期讲了总体架构，这一期回答一个更容易被跳过、但迟早会撞上的问题：

为什么非要分布式？我本地跑一个 agent 不也能控制机器人吗？

先说结论：能，而且一开始就应该那么做。但只要出现第二台机器人、第一次网络抖动、第一次断电重启，本地单机就会开始拖住你。本期不讲高深的分布式理论，只讲机器人工程里那些让你不得不分布式的具体时刻。

一、机器人有一个后端没有的约束：执行体不能"再开一个"

写后端的人谈分布式，动机通常有两个：扛并发、做容灾。进程不够就多开几个，机器不够就加机器，一份无状态服务想复制多少份都行。

机器人不给你这个自由。

一个执行体就是一台物理机器人。它有重量、有电量、有位置，正在某个房间里抓着某个东西。你不能因为负载高了就"再开一个机器人实例"，也不能因为这台机器卡住了就把任务无缝迁到另一台上——除非另一台正好在附近、正好有空、正好能抓得动。

这件事决定了机器人系统的分布式和互联网的分布式不是一回事。互联网的分布式主要在解决"请求太多"，机器人的分布式主要在解决另外三件事：

第一，身体在哪儿。感知、控制、急停必须在机器人身上，因为它们不能等网络。这一层天然是分布式的一个节点，不是设计选择，是物理事实。

第二，谁说了算。一旦有两台机器人可能碰同一件东西，就必须有一个能看见全局的地方来裁决顺序。这个"地方"不可能装在某一台机器人身上，因为那样另一台就成了它的下属，它一死全盘皆输。

第三，出了事怎么查。机器人动作是不可回滚的。数据库事务失败可以回滚，机械臂把杯子碰倒了不能回滚。所以每一次动作之前依据了什么、之后世界变成了什么样，都必须留下能事后逐条调出来的记录。

所以"要不要分布式"这个问题，在机器人语境下应该换一个问法：

你的系统里，有几个东西在写同一个世界？

只有一个，本地单机就够。超过一个，你就已经在做分布式了——只是做得好不好、有没有把规则写下来的区别。

二、本地 agent 的三个具体塌法

我不想泛泛地说"单机不可靠"。下面三个场景，做机器人的人应该都遇到过。

场景一：断一次网。

如果大脑跑在云端，网络一断，机器人当场失去规划能力。它手上那条命令可能执行到一半，你不知道它做完了没有。

如果大脑跑在本机，网络断了它确实还能跑，但第二台机器人也断网了——两台各自以为自己该去拿同一块料，因为谁也看不见谁。本机大脑把"分布式"这个难题推迟了，没有解决它。

场景二：进程重启。

本地 agent 的任务状态通常在内存里。进程一重启，任务进度清零。你可能会说"那就把状态存文件"——存了之后立刻遇到下一个问题：谁在写这个文件？如果两台机器人共用一个状态文件，谁后写谁覆盖。如果各写各的，那它们看到的世界又不一样了。

更麻烦的是重启之后的对账。重启前你发出了"抓取"，重启后机械臂里是否夹着东西？这个信息不在你的状态文件里，它在你没拍的那张照片里。恢复时必须重新观察环境，而不是照着旧计划继续往下走。

场景三：指令重复。

网络不稳的时候，客户端最常见的做法是超时重发。重发一次"前进一米"，机器人就真的又走了一米。这类事故在机器人上不是"数据重复"，是物理损坏。

单机 agent 通常只有一个"成功/失败"的返回值。工具返回成功就是成功，没有第二个人复核；工具超时就当作失败重试，可它可能已经执行了。

这三个场景的共同点是：本地单机把整个系统的正确性，押在了"没有意外发生"这个假设上。

三、分布式的真正含义：不是"很多台机器"，是"很多个写者"

我先拆一个误会。很多人一听分布式，想到的是"服务器集群""高并发""QPS"，觉得跟自己没关系——我那台机器人一天就干几十个任务，哪来的并发。

这里的关键不是并发量，是写者数量。

一个有状态系统最怕的是多个写者同时修改同一份状态。后端用数据库事务、行锁、乐观锁来处理这件事。机器人系统里"同一份状态"包括：地图、机器人位姿、谁抓着什么、充电位占用、电梯占用、门禁。这些东西的写者天然不止一个——每台机器人都在写。

于是分布式在机器人里的最小内核，其实只有一条：

让同一份状态只有一个写者，其他人只能提交请求。

我做的这套系统里，这条规则体现得很直接：任务是一个聚合，版本不可变；协调器是单写派发；世界的权威视图由 WorldHub 统一投影，别的组件不能直接改它；每一份独占资源（红方块、充电位）有唯一 owner 和一个只能单调增加的 fencing token。旧持有者拿着旧 token 来写，会被直接拒绝。

这条规则跟"你有几台机器人"无关，跟"你有几个写者"有关。哪怕只有一台机器人，只要它有云端控制台和本地控制两条路径，那就是两个写者，就需要这条规则。

四、五个故障剧本：同一句需求，两种系统的反应

下面这五个场景，我在仓库里都写了对应的测试。我把它们放在一起，是因为它们代表了机器人系统必须提前回答的五个问题。

剧本一：网络断了 30 秒。

朴素做法的反应：命令状态变成"未知"，代码里没有"未知"这个状态，于是被当成失败重试，重试出第二次物理动作。

系统的反应：边缘节点重连续租；已经发出去的命令不许猜，先分类。仓库里有一个测试叫"未知的物理步骤不能被另一个版本绕过"，讲的正是这件事——不允许用改需求的方式把一次结果未知的动作糊弄过去。

这里要说清一个设计取舍：断网时这套系统选择的是**停机等待**，而不是"让机器人自己接着干"。不向离线机器人分派新步骤；网络恢复后自动重新注册；如果断网时手里正抓着东西，需要现场处置并把 fencing token 提高之后才能继续。宁可停，也不让一台"失联但还在动"的机器人成为没人知道的写者。

剧本二：同一条指令送达两次。

朴素做法：工具白跑两遍。

系统的反应：命令带命令号加幂等键，重复送达返回同一个结果而不是重放动作。协调器对完成上报做多重身份校验：聚合版本、步骤、命令号、fencing token 全都要对上，低 fence 的完成被拒绝，完全相同的重复是幂等的。

剧本三：消息队列挂了。

朴素做法：一次机器人之间的交接丢了，任务链断在这里，图上的状态和实际不一致。

系统的反应：事实先落盘再投递。这就是 Outbox 模式——提交事件与投递事件分开，队列不可用的时候先把要发的消息写进存储，队列回来再接着发。仓库里对应的测试验证了队列宕机期间任务图没有被改坏，以及发布者恢复后 Outbox 会被重新投递出去。

剧本四：协调器换主。

朴素做法：单机没有第二个协调器，只能人工介入。

系统的反应：leader 用租约选主，只有持有当前 fence 的 leader 能推进状态，旧主的写入被拒绝。租约还有个容易被忽略的细节：租约过期后可以被别人重新获得，但签发出去的 token 必须继续单调增加，绝对不会回退到旧值——否则旧持有者就能用旧 token 冒充新人。这两条都有独立的测试。

剧本五：观测迟到或者丢了。

朴素做法："没报错"就等于成功。

系统的反应：世界快照是带单调版本号的，观测按来源序列去重。如果某个订阅者的游标落后超过了保留窗口，系统不会假装无事发生，而是明确要求重新同步。宁可要求客户端重同步，也不给它一段有洞的历史。

把这五个剧本连起来看，你会发现分布式系统真正在做的不是"让故障不发生"，而是：给每一种故障提前规定好它该被怎么处理。

五、云端与边缘不是主从，是快慢两个环

到这里要解释一个质疑：既然控制环必须在本地，那云端到底在干什么？是不是为了架构好看硬加的一层？

不是。这两个环解决的是不同时间尺度的问题。

快的环在机器人身上，周期是毫秒到几十毫秒。它管避障、限速、急停、执行确认。它的正确性不依赖网络，因为网络不可能给你毫秒级的确定性。这一层不联网也必须活着。

慢的环在控制面，周期是秒到分钟。它管的是：这句话该怎么拆成任务、下一步该派给谁、这块料归谁、这一步到底做完了没有、改需求怎么切版本、加了新机器人怎么纳管。这些事情的特点是——它们都需要全局信息，而全局信息不可能完整地存在于任何一台机器人上。

所以云端和边缘不是上下级，是慢环和快环。慢环负责一致性与调度，快环负责实时与安全。快环本来就不依赖网络，所以断网不会让机器人失去"停下来"的能力；慢环则负责在联网时把顺序和证据理清楚，断网期间不派新活，恢复后再对账。

这一层分工还有个副作用，对机器人工程师特别重要：它把"不确定"挡在了慢环里。快环只做确定性的事——收到速度就执行，收到停止就停。所有需要判断、需要妥协、需要等待的地方，全部留在慢环。物理世界最怕的就是一个正在犹豫的控制器。

六、为什么现在就写这些代码

有人会说：你说得都对，但我现在只有一台机器人，等有十台了再重构不行吗？

不行，原因是这些结构一旦缺席，后期补的代价不是加代码，是改契约。

任务的版本化、幂等键、证据链、资源归属，这些都不是"加一个模块"能补上的。它们是贯穿整个系统的字段和约束：工具目录要带版本、命令要带幂等键和截止时间、观测要有来源序列、任务变更要能表达"保留哪些步、改哪些步、取消哪些步"。这些信息如果一开始没采集，后面无论怎么重构都补不回来，因为历史数据里根本没有。

反过来，这些结构在单机阶段就已经在付红利了，不需要等到多机：

断电重启能回到原来的地图和任务账本；
改需求是提一个新版本，而不是从头再来；
每一步都有证据，出错时能定位到是哪一次采集的问题；
恢复时重新核对历史，不盲目重放动作。

这些全是单机就受益的东西。分布式在这里不是额外成本，是把单机该做对的事情做对了而已。

七、两个必须澄清的误解

误解一：分布式一定更慢。

不会，因为控制环不在云端。决定机器人反应速度的是本地的执行与安全层，跟你在云端放了几层服务没有关系。真正会被网络影响的是"下一步做什么"的规划延迟，而规划本来就不是毫秒级的事。

会慢的是别的东西：开发复杂度、调试难度、部署步骤。这些是真实成本，别装看不见。所以我在下面第八节给了判据——不是所有项目都该上。

误解二：分布式等于高可用，上了就不会挂。

这是最危险的一个误解。分布式系统不会让你不挂，它让你挂得"有据可查、有人接手、有边界可退"。

而且必须说清楚我做到哪一步了。这套系统的当前形态是：单主进程重启时的一部分状态恢复，有持久化事件、快照和 Outbox；有租约和 fencing 来防止越权写入。它不提供跨主机共识，也不提供跨存储事务。leader fencing 与所有业务提交的同原子校验、数据库与队列切主、跨主机的长期故障验证，这些还在待验证清单上，我没有把它们写成已完成。

还有一个取舍值得单独说：**断网时它选择停机，不选择自主继续。** 有人在演示里看到"断网后机器人还站在那儿"，会以为系统"扛住了"。真实情况是：不向离线机器人派新活，网络恢复后重新注册，断网时如果手里抓着东西，要现场处置并把 fencing 提高之后才允许继续。停机比"失联但还在动"安全得多——后者是一个没人知道的写者，正是分布式系统最该消灭的东西。

把边界写清楚不是示弱。机器人系统里最贵的事故，都是把"测试通过"当成了"生产可用"。

八、五个判据：你该不该上分布式

把上面的内容压成五个可操作的判断。命中任意两条，本地单机就会开始拖住你。

一，同时干活的机器人不少于两台。只要两台机器人会碰同一件东西、同一张地图、同一个充电位，你就需要一个能看见全局的裁决者。信号是：你开始口算"谁先谁后"。

二，网络不是理所当然。现场 Wi-Fi 会断、4G 会抖、厂区会屏蔽。如果断网后机器人该继续还是该停，你答不上来，说明这个决定还没被设计过。

三，任务比一次上电更长。一个任务要跑半小时，而机器人随时可能断电、被推、被急停。信号是：重启一次就得从头再来。

四，要有人能签字负责。谁批准了动作、依据哪一份证据、当时的世界是什么样，必须能事后逐条调出来。信号是：出事后只能翻日志文件。

五，机器人会越来越多、型号会越来越杂。工具、任务、证据契约要与本体解耦。信号是：加一台新机器就要动上层代码。

反过来说，如果你是"一台机器人、一个工位、一个操作员"，那就别提前上分布式。老老实实单进程加 SQLite，把闭环跑通：感知、执行、验证、恢复。我这套系统的当前主线就停在这里，云端 Fleet 是仓库里已经实现的扩展路线，不是"单机已经具备跨地域生产级高可用"的意思。

九、三句话记住本期

第一句：写机器人程序时，你有一个执行体；写机器人系统时，你必须假设执行体会死。

第二句：数据库可以回滚，机械臂不能。所以机器人系统对"不确定"的处理必须比后端更保守——宁可停下来等人，也不猜一个成功。

第三句：云端负责慢的对账，边缘负责快的控制。快的环不依赖网络，慢的环不依赖内存。
