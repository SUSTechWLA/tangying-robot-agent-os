# 短文连载计划（每天一更，长文拆成短文）

**为什么改**：第 01–03 期长文（3046 / 5501 / 4292 字）数据不好。这个平台的阅读发生在**几秒钟**里：读者点进来是为了拿一个能立刻用上的点，不是为了读一章。所以改成短文连载——**一条一个点，一条一个可验证的结论**。

**目标**：每天一更，先有 20 天存货；三个月后把这些短文按论文骨架重排，形成一篇有系统、有实现、有实测的工程论文。

---

## 一、语气：讲人话（这一步比结构更重要）

**受众不是同事，是"对机器人好奇的普通人"**：可能是产品经理、学生、做后端想转硬件的人、家里有老人的子女。他们不关心你的目录结构，关心"这东西靠不靠谱、能不能用在我家"。

| 要 | 不要 |
| --- | --- |
| 开头用生活场景（拿药、点外卖、停电、导航、盖章） | 开头用系统术语（闭环契约、幂等键、fencing） |
| 术语出现时先给一句人话再给名字 | 直接抛代码名与文件名 |
| 数字最多一个，而且能"心里比大小" | 连报五个毫秒数与百分比 |
| 结论句要好记、能被复述 | 结尾写"综上所述" |
| 讲"我踩过的坑"和当时的犹豫 | 讲"本系统采用了……" |
| 一张真实截图/数据图 | 拼图、示意图冒充界面 |

**技术出处留在计划表和各期 `素材来源与数字出处.md` 里，不写进正文**（正文要能被完全不懂的人读完）。发布前自查：把这条念给一个不做机器人的朋友听，他能不能说出"这条在讲什么"。

### 去术语对照表（写的时候照着换）

| 系统里的话 | 说给人听 |
| --- | --- |
| 闭环契约 / post-condition | 干完必须自己看一眼，看到结果才算完 |
| 幂等键 | 认出"这条我处理过了"，不会重复干 |
| fencing token | 班次号：交接之后前任的签字作废 |
| 租约 / lease | 值班表：现在这台机器人归谁管 |
| WorldModel / WorldHub | 它对"现在世界什么样"的统一记账本 |
| outbox / 事件日志 | 先记在纸上再送出去，别丢单 |
| ATE / RPE | 走一圈回到原点，差了几厘米 |
| ICP 配准 | 把两次拍的画面对齐，看差了多少 |
| 前端 / 后端 / 运行时 | 你看到的界面 / 背后干活的程序 |
| 能力门禁 / 失败关闭 | 该不能动的时候，就是不动 |
| 语义地图 / work area | 它会记"厨房在哪、杯子在哪儿见过" |

## 二、每条的解剖（照这个写，不要变）

| 部件 | 规格 | 说明 |
| --- | --- | --- |
| 标题 | ≤20 字，第一行 | 一个具体结论或反直觉事实，不要"XX 系统介绍" |
| 正文 | **300–450 字** | 一个点讲透；超过 500 字就是长文，拆。受众越广，越要短 |
| 结构 | 生活场景钩子（1–2 句）→ 为什么会这样（2–3 句，打比方）→ 我怎么做（2–4 句）→ 一句能被复述的收尾 | 不要小标题堆叠，不要 ①②③ 超过三个，不要代码名 |
| 配图 | 一张 | 优先真实截图/地图产物；没有就用手绘信息图 |
| 行动 | 一行仓库链接 | `github.com/SUSTechWLA/tangying-robot-agent-os` |
| 标签 | 4–6 个 | 与内容相关，不堆无关热门标签 |
| 纪律 | 每个技术说法都指得出实现或测试 | 出处见各期的 `素材来源与数字出处.md` |

**求职诉求**只在**置顶那条**和**每周一条**里出现，不要每条都求内推——那是掉粉最快的方式。

## 五、最后攒成论文：短文即章节

短文不是散点，每条都是"设计决策 + 实测证据"。按下面骨架重排即得一篇工程论文（属于 **systems / robotics 工程论文**，不是算法论文）：

| 论文结构 | 由哪些短文组成 | 仓库里现成的硬证据 |
| --- | --- | --- |
| 1 引言与问题 | S01、S06、S11 | README 的主张、`docs/production/architecture.md` |
| 2 相关工作 | 新写（对比 MCP、Nav2 生态、VLA 工作流、ROS 2 安全监督） | 需要补：这一节必须新写，仓库里没有 |
| 3 系统设计 | S02、S03、S07、S12 | 八层架构、工具目录、七类失败、九道闸门 |
| 4 实现 | S04、S09、S10、S14、S15、S22 | 证据库、fencing、恢复语义、幂等、模块故障契约 |
| 5 评测 | S16–S21 | `evaluate_slam.py`（ATE 0.2–8.5 mm / 注入漂移 43–134 mm vs 里程计 85–212 mm）、探索覆盖 38.9%→81%、语义层 606 B/条与 9 ms 规划、故障矩阵 21 项 |
| 6 讨论与局限 | 各条的"边界"段落 | 各升级文档的"仍未解决"小节（诚实清单已经写好了） |
| 7 结论 | — | — |

**诚实提醒**：论文还差三样仓库里没有的东西——① 相关工作（必须新写并引用）；② 统一的实验协议（现在每个模块各有夹具，需要一套共同口径；`scripts/evaluate_slam.py`、`benchmark_semantic_layer.py`、故障矩阵可以合并成一张评测表）；③ 与至少一个外部系统的对比。这三件不解决，短文拼起来只是**技术报告**，不是论文。先把连载跑起来，攒够 30–40 条再回头补这三项。

## 六、发布纪律（沿用且强化）

1. **每个技术说法指得出实现或测试**；指不出来就删，或写"尚未验证"。
2. **数字只引用当期出处表里的**，不要现场算。
3. **不虚构画面**：截图必须是客户端/文档的真实渲染。
4. **主线与扩展路线分开说**：当前主线是一台机器人把活干完；多机 Fleet 是仓库里已实现的扩展路线。
5. 每条发完，回到 `00-选题与索引.md` 登记状态与数据表现（阅读/收藏/涨粉），**两周后按数据淘汰选题方向**。
