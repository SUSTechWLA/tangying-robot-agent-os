工具调用的本质区别 · 04 · 证据的四道校验

不是随便一份数据，都能当证据

上一张图说：返回成功之后要附上"新鲜的、命令之后的观测"。但这句话里的每个词都要落在具体的校验上—— 否则"新鲜"会变成一个可以商量的形容词，而旧证据会被洗成一次完成。

要通过 观测证据 ⟶ ① 观测 ID ② 采集时间 ③ 晚于命令 ④ 来源新鲜 ⟶ 计入完成
01
必须有观测 ID
证据要指回观测注册表里的一条记录，不能是一句"我看到了"。
挡掉的是
工具自己声称成功、但不附带任何可追溯观测的情况。
no observation id
02
必须有采集时间
而且必须是传感器采集时间，不是系统收到这条数据的时间。这两个时间在真实系统里能差好几秒。
挡掉的是
用"收到时间"冒充"看到时间"，把一份晚到的旧画面说成刚刚拍的。
no observation time
03
采集时间必须晚于命令下发时间
早于命令的观测，哪怕再清晰，也证明不了命令之后发生了什么。两边统一按整毫秒比较。
挡掉的是
最隐蔽的一类错误：拿一张命令之前的照片，当作动作完成的证据。
observed 12:00:03.412, dispatched 12:00:05.008
04
来源的新鲜度判定不能是 STALE 或 UNKNOWN
时间戳对得上还不够——数据源自己得说它是新鲜的。缺失或过期的来源判定同样拒绝。
挡掉的是
一个已经过期的数据源，被"洗"成一次完成。
source verdict STALE

为什么第 3 条要精确到毫秒

运行时的观测只带 Unix 毫秒。所以"命令和紧跟其后的那张照片谁先谁后"，在原理上就分辨不到毫秒以下—— 这不是我们放宽的容差，而是可观测性的上限。两边于是统一按整毫秒比较：

还有一个维度：坐标系与版本
物理世界里"杯子在 (0.3, 0.1)"如果没有说明是哪个坐标系、哪个标定版本，这句话本身就没有意义。 所以观测还要与命令使用同一个坐标变换版本；版本不一致时不混用，而是拒绝并重新定位。
这些校验防的不是"错误"，是"看起来对"
过期数据不会报错，它只会静静地给出一个合理的答案。四道校验里有三道都在做同一件事： 确认这份证据确实产生于这次命令之后——而不是一次精心伪装的旧事实。
