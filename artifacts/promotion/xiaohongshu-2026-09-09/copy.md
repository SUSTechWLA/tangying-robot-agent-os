# 小红书标题

我在做一个真正面向机器人的 Agent OS：让一句话变成可恢复、可验证的行动

# 正文

最近在做一个开源项目：**躺营 · Tangying Robot Agent OS**。

我想解决的问题不是“让机器人演示一次动作”，而是：

> 用户说出一句话后，机器人能不能只依靠自己的传感器，观察现场、拆解任务、规划路线、执行动作，再确认环境真的发生了预期变化？

当前系统已经把这条链路拆成了可追踪的工程流程：

**自然语言 → 任务分解 → RGB-D 观测 → 感知 / 建图 → 导航与执行 → 新观测 → 结果确认 → 可恢复记录**

例如在限定仿真工位中，参考任务“把红色杯子放进右侧收纳盒，再把蓝色瓶子拿过来”已经完成过包含导航、抓取、放置和结果核对的 18 步流程；系统保留每一步的原始 RGB-D 证据、工具回执和任务时间线。

这次最新版本又加入了一个更接近实机的家庭场景：客厅、走廊、厨房、卧室、卫生间，机器人只通过顶部和底盘 RGB-D、里程计和自身状态工作。RTAB-Map / Nav2 负责地图和导航，仿真场景不会把房间真值直接塞给 Agent。

家庭路线测试也暴露出了真实的工程边界：当前视觉就绪后，客厅段导航和到达确认可以完成；当厨房区域还没有被地图覆盖时，系统会因为未知空间而拒绝规划，而不是把未知区域当成“肯定能走”。下一步是受控低速探索覆盖整套房屋，再接入真实 XLeRobot 做标定、驱动和现场验收。

我认为这个项目的几个创新点在于：

**1. 观测和动作来自同一个现实闭环**

系统使用机载 RGB-D 作为主要环境输入，彩色、深度、点云和位姿在采集时关联保存。没有看到的区域保持未知，动作完成后必须重新观测，避免使用仿真真值或“全知视角”替机器人下结论。

**2. 任务失败后可以回溯和恢复**

每个步骤都有 checkpoint、原始图像、时间戳、工具参数和结果状态。地图未就绪时是可重试失败；如果动作已经发出但终态不确定，系统会进入需要核实的状态，阻止盲目重复执行。

**3. 机器人差异被收敛在适配层**

机械结构、传感器和执行器通过 robot profile、统一工具和 MCP 接口接入，上层任务逻辑不绑定某一个机器人。当前先把单机器人任务做扎实，同时保留多机器人协作的扩展位置。

**4. Sim2Real 不是换一个模型文件就结束**

项目同时保留 MuJoCo 仿真入口、ROS 2 / RTAB-Map / Nav2 导航入口和真实机器人适配器边界。真实设备需要提供经过标定的 RGB-D、CameraInfo、TF、里程计、速度限幅、急停和失联归零；每一项都有明确的验收位置。

和很多“能跑起来的机器人 Demo”相比，我更关注三件事：

| 传统演示常见做法 | 躺营的工程取向 |
| --- | --- |
| 只展示规划结果或一次动作 | 把感知、规划、执行、验证串成完整闭环 |
| 直接使用仿真地图或环境真值 | 只使用 RGB-D、里程计和可审计的观测 |
| 出错后重新开始任务 | 根据 checkpoint、证据和物理不确定性恢复 |
| 机器人型号和任务代码强绑定 | 通过 profile、MCP 和适配器接入不同机器人 |
| 未知区域默认当作可通行 | 地图覆盖不足时主动停止并要求探索 / 验收 |
