# 第 15 章 未来方向：这套系统自己承认还有哪些没解决

> **版本口径**：本章包含 v0.6.0/v0.7.0 演进案例。代码片段、计数与实验按原时点解释；出版复核修正论证，不表示历史缺口均为当前状态。当前云边能力见第17章，来源与证据边界见出版说明。

> **本章的核心命题**
>
> 一个项目的诚实度，最好的检验方式是看它有没有一份**"我还没验证过的东西"**的清单。
>
> 这一章就是那份清单——以及从它推出的方向。

## 15.1 从一份清单开始

`docs/architecture/distributed-agentos.md` 有一个小节，标题是：

> ## 仍须独立验证的范围

内容只有五行：

```
- leader fencing 与所有业务提交的同存储原子校验；
- MySQL、Redis、世界投影与物理结果之间可恢复的资源转移 saga；
- 数据库/队列切主、网络重排和长期多进程故障验证；
- 实机传感器质量、坐标标定、匹配策略、实体急停、停止响应和受限任务验收；
- 目标终端可见帧率、现场容量、备份恢复和长期运维。
```

**这不是路线图，是「我做了但没能证明」的清单。**

而它的前面还有一句边界声明（`:31`）：

> 这解决**单主进程重启的**一部分状态恢复，**不提供跨主机共识或跨存储事务**。
> 文件锁/损坏/保存失败应失败关闭；**不能多开 writer、删除快照或降低 token 来"恢复服务"**。

### 逐条展开：每条要做什么实验

**① leader fencing 与所有业务提交的同存储原子校验**

**问题**：今天的 leader lease 在 Redis、业务提交在 MySQL（或本地 SQLite）。**两处存储之间没有原子性**——一个刚失去 leadership 的实例，在"租约过期"到"它下一次尝试提交"之间的窗口里，理论上仍能写入。

**fencing token 防住了"旧 token 的写入"**，但"token 校验"与"业务提交"**本身不是同一个事务**——"检查通过 → 提交前被打断"是真实窗口。

**要做什么实验**：注入"leader 切换恰好在检查与提交之间"的故障。**注入时机要精确到提交前 N 毫秒**，并断言"同一 task event 只落一次"。

**② MySQL、Redis、世界投影与物理结果之间可恢复的资源转移 saga**

**为什么这条最重要**：这是**唯一一个跨越"软件事务"与"物理世界"的转移**。

方块从 robot-1 的 owner 转给 robot-2，中间可能宕机在**四个不同位置**：

| 崩溃点 | 状态 |
| --- | --- |
| 数据库提交前 | 没有转移 |
| 提交后、事件发布前 | **数据库说转了，对方不知道** |
| 机器人抓取中 | **结果未知** |
| 抓取完成但 ACK 丢失 | **结果未知** |

今天的设计用 outbox + 幂等 + 世界对账覆盖了大部分，**但没有一个显式的、可恢复的 saga 状态机**。

**要做什么实验**：把**崩溃点参数化**——同一场景在 **8 个不同的提交边界各崩一次**，断言最终只有一个 owner 且不重复物理动作。

**③ 数据库/队列切主、网络重排和长期多进程故障验证**

今天的所有故障注入都在**单机可控环境**里。真实切主涉及 DNS/连接池/客户端重连/时钟漂移的组合。

**项目自己指出的根本缺口**：

当前 `make test-python` 包含 `tests/e2e`，CI 的 `make test` 已执行它们。缺口是定时、随机化、真实切主和长期多进程故障矩阵，不是完全没有 CI 覆盖。

**以及一条硬前置**：

> **不在没有真实 Redis/MySQL 的测试之前，把 Fleet 用于任何真机。**

**④ 实机传感器质量、坐标标定、匹配策略、实体急停、停止响应和受限任务验收**

这是**软件一切结论的边界条件**。书中物理闭环实验主要是仿真；另有真实模型测量、契约测试和容器验收，均不能替代实机放行。

**量化的门槛**：

> 至少按已有手册完成 **30 次真实试验**，再补充限定任务成功率、**24/72 小时长稳**、备份恢复和故障注入。

**⑤ 目标终端可见帧率、现场容量、备份恢复和长期运维**

**一次实测记录**：浏览器约 498 px 宽、RGB/深度各约 **18 秒**刷新、底盘三路各约 **7 秒**——并明确标注：

> **这是本次短时 UI 验收，不代表长时间网络、导航或实机可靠性验收。**

## 15.2 刻意的非目标：五条判断与它们的代价

`README.md` 第十节，作者自己给这一节的理由是：

> **一个项目的取舍比功能列表更能说明它的判断。**

### ① 不用软件急停替代实体急停

**判断**：软件状态永远低于硬件限制。

**落地为一条不可绕过的实现约束**：

> Remote APIs **never** expose clear/reset.
> A physically present operator must clear the condition **locally**.

**代价**：`set_speed_limit` 之类的软件安全能力**不能宣称等于安全**；软件层能做的最正确的事只是"把请求送达"并记录。

### ② 不把仿真模型当作未经标定的实机真值

**判断**：

> 视觉模型与真实硬件 revision 不匹配时明确降级，**不能把当前官方模型当作已标定数字孪生**。

**代价**：**所有仿真验收都不能转化为实机放行。**

**一条容易被忽略的推论**：

> **仿真里的"数字孪生"只是视图，不是世界模型。**

设计文档的技术表述：

> **GLB 决定对象"长什么样"，`WorldSnapshot` 决定对象"在哪里、处于什么状态"。**

### ③ 不在观测陈旧、资源冲突或证据缺失时猜测成功

**判断**的原文推论：

> 未验证的物理动作**既不能重试**（可能重复执行），**也不能宣告成功**（可能没做），
> 只能进入"**未知终态 + 人工对账**"。

**代价**：**系统会主动失败。**

README 里那条"返程导航 ⚠️ 受地图覆盖限制"就是这条非目标的日常代价：

> 参考地图上返程点未认证可通行，`navigation.navigate` 以 `GOAL_NOT_CLEAR` 结束。
> 这是"不知道的地方不进去"，不是缺陷，但**在这一版上返程确实没走通**。

**一条正面的副作用**：

> 因为它**不猜**，所以"**不知道**"可以被度量。

### ④ 不承诺单机开发栈已经具备跨地域生产级高可用

**判断**：

> 当前**主线是一台机器人**在受限环境把活干完……恢复能力限于**单主进程重启范围内的一部分状态恢复**，
> 跨主机共识与跨存储事务**仍在待验证清单上**。

**代价**：Fleet 那一整套代码（`fleet/` 13 个包 + `edge/` 7 个包）**在当前主线里不产生价值**，只作为扩展路线保留。

**这条判断的元价值**：它把一个容易被误读的架构（"分布式系统怎么只跑一台？"）变成了一个**明确的产品陈述**。

### ⑤ 不让大模型输出关节角

**判断**：**物理动作的粒度是任务，不是电机。**

**代价**：**模型的表达能力被人为收窄。**

而 ADR-2 的原文承认这条张力并给出了解法：

> `move_arm_to_joints` **保留为底层兜底工具**，但标记 `llm_visibility: "fallback"`，
> 「这样『底层兜底可选、LLM 默认看不到』**两个要求同时成立，而不是假装它不存在**」。

**教学要点**：**"假装它不存在"是最省事也最坏的做法。**

正确的做法是：**工具存在、可被工程调用、但不给模型**——而这个区别由一个字段表达。

### A22 那一条值得单独说

**这是本书里最好的一个"留白"样本。**

一个几何问题（`GOAL_NOT_CLEAR` 的返程失败）有**三条修法**：

| # | 修法 | 代价 |
| --- | --- | --- |
| ① | 厨房路点移约 0.3 m | 改变了操作员标注的位置 |
| ② | 换方向补扫 | 增加一次物理动作 |
| ③ | 放宽 goal 净空判据 | **降低安全裕度** |

而作者写的是：

> **"我没有替项目做这个决定……这是导航语义的决定，不是机械修补。"**

**教学要点**：**知道怎么改，但不去改**，是一种能力。

三条修法都有明确的代价，而**这个代价该由谁付**是一个**产品决定**，不是一个工程决定。

**一个把这三种都实现、用一个开关暴露出来的"灵活"设计，只是把决定推迟给了用户**——而用户没有足够的信息做这个决定。

## 15.4 六个更深的方向（推断）

以下每一条都显式标注 **(推断)**。

---

### 方向 1：世界模型的自学习——从「重放观测」到「预测世界」（推断）

**当前卡在哪一步**

世界模型今天是**纯确定性 reducer**：规则写死，没有任何"预测"或"学习"成分。

**而且连语义记忆都还没有完整落地**：`TagMap` 本轮未实现，理由是：

> 仓库没有把关键帧 ID 暴露到观测契约里；**在没有真实关键帧标识的情况下建 TagMap，
> 只能用采集序号冒充关键帧，会把"看起来有据可查"写成事实。**

**这句话本身就是一个很好的判据**：一个"看起来有据可查"的东西，比"明确没有"更糟。

**解决它需要什么**

| 步 | 内容 |
| --- | --- |
| 1 | 先补齐**身份**：观测契约里加入可选的 `keyframeId` 与地图 revision |
| 2 | 再建**持久语义层**，带观测计数、软删除、多视角一致性过滤 |
| 3 | 然后才有资格谈预测：世界模型的输出从"当前事实"扩展到"下一个观测的概率分布"——**并且必须与 Harness 的证据判定分开**，否则**预测会污染证据** |

**为什么这条收益最大**

README 那两句（"尚未实现未知住宅的自主 frontier 探索"、"返程导航受地图覆盖限制"）其实是**同一个缺口的两个症状**：

> **机器人在没去过的地方，没有任何可依赖的模型。**

---

### 方向 2：跨机经验的真实闭环（推断）

**当前卡在哪一步**

这条**没有任何实现**（第 12 章 §12.9 已详述）。

**而且更关键的是：训练语料本身还不够。**

实测：

```
negative.jsonl  0 行
65 任务 → 15 请求
sft 0 / refusals 6 / negative 0
```

**而账本曾经有 99.3% 是噪声**（159,314 条事件里 158,193 条由观察者产生，执行事实只有 0.7%）——

> **在那种账本上做跨机学习，学到的是观察者的行为。**

**解决它需要什么**

| 阶段 | 内容 |
| --- | --- |
| 0 | **账本只记状态迁移**（已完成） |
| 1 | **拒绝样本要先被采集**——项目自己列为"**没有替代来源**"的高价值项 |
| 2 | 数据集版本化、脱敏与许可 |
| 3 | **跨机场景下同一条经验的可用性判据**：`robot.profile.v1`、标定 revision、地图 revision 都要匹配才允许迁移 |

**一个具体的实验设计**

```
机器 A 的 30 次失败任务 → 导出
→ 在机器 B（同 profile、同标定）上跑同样 30 个任务
→ 看成功率差
对照组：不做任何迁移
```

**"结果出现前决定如何比较"** —— 这是这个项目的评测契约要求：

> 候选/基线、固定条件、随机化/配对、预算、假设、样本量、检验族、门禁版本。

---

### 方向 3：VLA 与 Agent 层的接口标准化（推断）

**当前卡在哪一步**

**契约已经在了**：`policy.manifest.v1` / `policy.observation.v1` / `policy.inference.request.v1` / `policy.inference.result.v1`——以及框架无关的 HTTP sidecar。

**但没有真实的消费者。** 今天实际在跑的"策略"是**确定性仿真**，不是学习模型。

而一条明确的验收门槛是：

> A real-robot release remains **`NO-GO`** until hardware calibration, camera/verifier integration,
> emergency-stop drill, **signed policy artifact**, physical shadow run, and supervised handoff
> evidence are attached.

**解决它需要什么**

**① 动作空间标准化。**

今天 `action_chunk` 的键名由适配器决定。而设计文档里已经定义了一组**规范关节键**（共 14 个），并规定：

> Console **不解析 MuJoCo 私有名字**，也不依赖具体驱动 ID。

**把这组键从"可视化绑定"提升为"策略动作契约"是自然的下一步（推断）。**

**② 观测 bundle 的内容寻址**——已经具备（`frameRef` + SHA-256，而不是原始字节）。

**③ 策略的失败分类要和 Go 侧同源**——已经处理了一侧（"取 `core/closedloop` 的分类结论"），并有跨语言一致性测试。

**一个具体的实验设计**

```
同一批 50 次抓取
  A = 固定控制器
  B = 技能策略
→ 同一份独立判据（Holding ∧ ¬On ∧ Stable 三帧连续）
```

### 方向 4：多机共识与跨存储事务（推断）

这一条**就是 17.1 的前三条**，此处补工程视角。

**今天的一致性模型**：

> **"局部强一致 + 跨组件幂等/补偿"**，而不是假设跨 MySQL、Redis、机器人和物理世界存在一个全局事务。

**具体的技术债已经被点名**：

> 云侧一个 **2 分钟定时器** `reclaimStaleLocked` 会把任何超期的 RUNNING 节点改回 READY、清空 claim，
> **完全不检查物理动作是否仍在飞**。
>
> **"这正是 `core/closedloop` 花 369 行要防的事，在 `fleet/` 里被一个定时器放回来了。"**

**另一处结构性缺口**：`fleet/` **完全不 import `core/closedloop`**——

> 即**云侧的完成判定与本地侧的闭环契约是两套**。

**解决它需要什么**

| 步 | 内容 |
| --- | --- |
| 1 | **让 fleet 用上同一套闭环契约** |
| 2 | **删掉或改造那个 2 分钟定时器** |
| 3 | 然后把 leader fencing 与业务提交放进同一存储事务 |

**一个极具体的实验**（已写在文档里）：

> 协调器在**交接中途**崩溃……值得单独造一个"**提交后立刻杀协调器**"的用例。

---

### 方向 5：长时程任务——从「12 步」到「一个下午」（推断）

**当前卡在哪一步**

今天最长的一条已验证链路是 **12 步**。

长时程会遇到三个**今天没有覆盖**的问题：

**① 预算耗尽**

探索有总里程与 30 分钟期限。

**② 人在不在**

第 1 章那张对照表里有一行写得极准：

> 人在不在：Codex / Claude Code **一直在**；机器人 Agent 运行时 **常常不在**。

**长时程意味着必须把"人不在"当作常态**——而这正是"人到场"（EscalationAgent）要解决的，**当前未开始**。

**③ 经验与记忆的时效**

"回忆新鲜度成为部署参数"已经落地，但**这只是一个参数的开始**。

**解决它需要什么**

- **EscalationAgent** + 认领/移交/解决/忽略的工作流；
- **持久化的尝试预算**：

> **物理写的重试预算必须持久化才有意义。** 内存里的尝试计数在进程重启时归零，
> 于是崩溃过的 Agent 会永远重试——**正是上限要防的那件事**。

- 分级保留策略（部分已做）。

**验证方式**：从"三场景各 10 轮，端到端成功率 ≥ 90%"开始，再到 **24/72 小时长稳**。

### 方向 6：仿真到真机的自动标定（推断）

**当前卡在哪一步**

**标定今天已经是软件的一部分，但不是自动的。**

而有一处明确的"曾经是错的"（CHANGELOG 段落标题）：

> **检验当前标定：头部相机的位姿一直是错的，而且没有任何测试能发现**

以及一次真实的修复：**底部相机被挂在了顶部**——即**仿真模型里的相机位姿与真实硬件不一致**。

**另一条硬约束**：

> **存档标定与模型矛盾时拒绝启动**，而不是每一帧发布错的相机位姿。

**解决它需要什么**

| # | 内容 |
| --- | --- |
| 1 | **标定的来源要可追溯**：实机 proprioception 发布相同规范关节键 + manifest 注册模型 revision |
| 2 | **仿真模型与真实硬件的偏差要可测量**——注意：固定依赖版本是**依赖版本**，不是**几何保真度** |
| 3 | **自动标定的闭环**：发现、配对、自检这三块已经做出来了（"上电就能用"），**缺的是标定环节的自动化** |

**验证方式**

判据可以是"**同一标定流程在仿真与真机上产出可比的数值**"——已有的基础是"一份标定文档同时服务仿真与真机"和"用仿真机器人跑标定流程"。

**而反面判据同样重要**：项目记录过一个真实缺陷——**模拟向导的产物被标为 `measured`**。

> **自动标定的第一个敌人是"看起来标好了"。**

## 15.5 八条可迁移的经验

这一节是本章最"抄得走"的部分。

### ① 证据 > 回执

> **"Tool 成功不等于物体到了目标。"**

**可迁移形式**：为每一类副作用定义一个**独立的完成判据**，并且这个判据**不能由执行者提供**。

**最有力的证据是这个项目自己的翻车**：`Result.Executed` 无条件为 true，于是"一次工具都没调用"的运行被报成 `executed: true, verified: true`。

作者的定性值得整句引用：

> **"这是本仓库最不该出现的一类错误：它把『我们什么都没做』说成『机器人动了，而且确认动对了』。"**

### ② 分类表 > if 分支

**可迁移形式**：把"失败之后怎么办"写成**可穷举、可测试的映射表**，而不是散落在调用点上的 `if`。

**两条配套纪律**：

| 纪律 | 内容 |
| --- | --- |
| **默认值的方向** | 未识别的错误码归入 `UnknownOutcome`，而不是猜成可重试——**猜测的方向选的是安全那一侧** |
| **清单要手工提交，不要自动爬取** | "未分类"作为**默认**是正确的，作为**意外**是危险的 |

**反面教训也在仓库里**：58 个码曾静默退化成 `UNKNOWN_OUTCOME`，让操作员"去对账一个从未发生的动作"。

### ③ 先有刻度，再谈自训

> **"不在 grounding 修好之前做 RL。环境是坏的，reward curve 看起来会像学习，实际在拟合噪声。"**

**一条极硬的纪律**：

> **判卷的人不能改判据。**
>
> **判据不能由被判者提供。**

**以及一条诚实的自评**：系统级 Eval 上线时的记录是"新增模型调用 **0**，机器人动作 **0**……它**没有证明新系统本身已变强**"。

### ④ 刻意非目标比功能列表更能说明判断

**可迁移形式**：把非目标写在**最显眼的位置**，并给出**代价**，而不只是给出理由。

**示范级样本**（ADR-5）：

> 明确不宣称对接 MoveIt 2，并列出三条可核对的事实，末句给出判据：
> **"声称 MoveIt 2 可用却无法运行，会让整套工具层的可信度归零。"**

**更强的版本是"给代价"而不是"给理由"**：

> `why-distributed.md` §6「这份文档没证明的事」，三条全部指向**自己论证的薄弱处**：
> 没有性能基准、没有多机实测、"更简单"是定性判断。
>
> 以及 1.3 主动说出反面：**"一台机器人 + 一个人看着 + 非安全关键 → 三层是过度设计。"**

### ⑤ 让唯一知道答案的那一层开口

**可迁移形式**：当一个事实只有一个地方真正知道时，**判定必须回到那个地方**，不能在上层从字符串/状态码推断。

**两次应用**：

| 案例 | 做法 |
| --- | --- |
| "到底有没有真的调用过工具" | `Outcome.Calls` 在**唯一一处真正下发调用的地方**自增 |
| 告警身份 | 前缀与后缀**在同一个函数里剥离**，边界用同一条规则 |

**并且明确否决了替代方案**：

> 为什么不在 `recoveryexec` 里从 verdict 字符串推断……**那是把派发规则抄第二遍，两份必然漂移。**

**推论**：

> **当你在两个地方写了同一个判断，你已经有 bug 了，只是还没显形。**

### ⑥ 「没通电」是一种缺陷，而且可以被测试

**这是这个项目最独特、最可迁移的一条工程经验。**

**现象**：有大量能力**实现完整、测试通过、生产环境永不触发**。

**五个具体样本**：

| 样本 | 表现 |
| --- | --- |
| 慢步骤告警 | 规则完整，但唯一的输入构造点**从不填 `Latency` 字段** → 永不触发 |
| 事故包计时 | 注释承诺"控制台的延迟报告逐字"，唯一写入点**从不设置** → `timing` **恒为 `null`** |
| 跨进程因果字段 | `observation.Causation` 走 protobuf 线，生产端 `.Causation =` **零命中** |
| 四段耗时遥测 | 采集器在、分位数在、HTTP handler 在，**前端零消费** |
| 闭环契约本身 | "Gate 在**全仓只有 2 个生产调用点**" |

**解法**：把"已实现的能力有没有生产数据源"做成**声明式检查表**，未通电项**会红**。

**为什么这条对行业最有价值**：

> **绝大多数团队的测试覆盖率指标天然无法发现这类问题**——
> 代码被覆盖了，规则被断言了，只是**没有任何生产路径到达它**。
>
> **这是一个测试覆盖率永远照不到的角落。**

（本书在写作中还发现了四个新的样本：`agentruntime.RequestMutation` 零生产调用点、`deployment-policy.json` 无消费者、`remedyOutcomes` 无解释者、`train/` 与 `training/` 不在 CI 里。）

### ⑦ 「失败可见」优先于「失败可复现」

**可迁移形式**：当无法复现一个用户报告时，第一步不是再试一次，而是**让这条路径的失败变得可见**。

**两次应用**：

- 提交标题直接写 **"让失败可见，并说明我没能复现"**——把不可复现本身记录为事实；
- "横幅负责有事找你，页面负责怎么办"——把**通知**和**处置**拆开。

**更硬的一条纪律是"如实说没修"**：

> **"没修的那一半才是根治……所以现在的状态必须说清楚：
> 控制台不会再被自己堵死，但首屏仍然很慢。"**

### ⑧ 历史文档不改写，删除要留痕

> **"Architecture simplification must not delete them merely because the corresponding runtime is removed."**

**可迁移形式**：设计文档是**版本化的产品资产**，不是过程垃圾。

被取代的文档：① 加可见的状态说明与替代者链接；② **历史内容保留**；③ 新的协议/安全决策**在实现之前**记录。

## 15.6 一份给读者的路线图

如果你要基于这本书**继续做下去**，我建议的顺序是：

| 优先级 | 做什么 | 为什么先做它 |
| --- | --- | --- |
| **1** | **修执行链**（让 LLM 计划的物理任务真的跑成功） | 训练流水线的报告说"可用正样本 0 条"，**所以现在的正确动作不是训练** |
| **2** | **采集被拒绝的请求** | 项目自己列为"**没有替代来源**"的高价值项，而补法很小 |
| **3** | **接上 `Verify` 端口**（为每个恢复动作定义"好"长什么样） | **它是跨机经验无法积累的根因** |
| **4** | **让 fleet 用上同一套闭环契约** | 那个 2 分钟定时器把 `core/closedloop` 花 369 行防的事放回来了 |
| **5** | **把故障矩阵接进 CI 的定时任务** | 默认 `make test` 已覆盖 e2e；还需定时长稳与真实切主矩阵 |
| **6** | **定义每个动作的"好"** —— 这是 3 的前置 | 一个读不懂效果的复验器比没有更糟 |

**注意第 1 条和第 6 条的关系**：它们看起来是"最后一件事"，实际上是**第一件事**——因为**没有独立的复验，你连"修好了没有"都不知道**。

## 15.7 本章小结

1. **这套系统有一份"我做了但没能证明"的清单**，五条，写在一个架构文档的小节里。**而它的存在让它比一个声称全都做完的项目更可信。**

2. **五条刻意的非目标，每条都有代价。** 而**代价比理由更有教学价值**——它告诉你"选择这条路要付什么"。

3. **二十四条明确的未实现声明**，全部带出处。**其中最好的一条是"我知道三条修法，但我没有替项目做这个决定"**——因为那个代价该由谁付是一个产品决定。

4. **六个更深的方向**（全部标注推断）：世界模型的自学习、跨机经验的真实闭环、VLA 与 Agent 层的接口标准化、多机共识与跨存储事务、长时程任务、仿真到真机的自动标定。

5. **八条可迁移经验**，其中最有价值的是第 ⑥ 条：**"没通电"是一种缺陷，而且可以被测试**——**它是测试覆盖率永远照不到的角落。**

6. **继续做下去的优先级**：**先修执行链，再谈训练**；**先接上复验，再谈跨机经验**。
