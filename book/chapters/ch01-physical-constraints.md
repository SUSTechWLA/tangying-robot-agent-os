# 第 1 章 物理世界的三条硬约束：为什么机器人 Agent 必须长得不一样

> **本章要建立的一个判断力**
>
> 读完这一章，你应该能看着任何一个"大模型控制机器人"的系统，
> 用五分钟判断出它是**真的把物理世界当回事**，还是**把一个聊天机器人接到了电机上**。

## 1.1 从一次失败的演示说起

设想一个很常见的场景。

你写了一个 agent，让它调用 `pick("红色杯子")`。工具返回：

```json
{"success": true, "message": "grasp completed"}
```

你的程序标记任务完成。屏幕上打一个绿勾。录屏，发布。

**然后有人问了一个问题：杯子现在在哪？**

三种可能的答案：

| 实际发生 | 工具知道吗 |
| --- | --- |
| 杯子确实在夹爪里 | 知道（猜对了） |
| 夹爪合拢时滑了，杯子还在桌上 | **不知道**——工具只报了"指令已送达" |
| 夹爪夹住了旁边的蓝色杯子 | **不知道**——工具根本没做身份校验 |
| 手臂在最后 3 度卡住 | **不知道**——超时被当作成功 |

注意一件事：**这四种情况下，你的代码路径完全一样。**

这不是"工具实现得不够好"。这是一个**结构性**问题：

> **仅凭命令被接受或工具自报成功，不能确认物理后置条件。**

发起方可以通过传感器和经验证的观测知道动作结果；工具也可以返回证据引用。关键是区分指令回执与后置条件证据，并校验来源、身份、采集时序和判据。

**"工具返回成功"是一个关于工具自身的陈述，不是一个关于世界的陈述。** 这两句话，是整本书的地基。

## 1.2 三条硬约束：分层不是架构偏好，是物理强加的

实时预算、停止安全和感知带宽支持把关键控制留在本地；规模、算力和运维也是分层的理由。这些约束不唯一决定进程数或部署拓扑。

### 约束一：控制回路有明确的时间预算

以 100 Hz 与 1 kHz 两个控制频率为例。具体设备的电流环、关节环、导航环和策略环频率不同，须依据控制器规格测量；本节不是项目的性能基准。

换算成时间预算：

| 频率 | 周期 | 一个 LLM 推理的时间预算能装下多少个周期 |
| --- | --- | --- |
| 100 Hz | 10 ms | 完整决策必须在 10 ms 内完成，首 token 到达不等于决策完成 |
| 1 kHz | 1 ms | 完整决策必须在 1 ms 内完成 |

未经有界验证的网络推理不能阻塞硬实时闭环。超时后应由设备控制器进入已验证的保持、减速或停止状态；是否失控取决于本机故障处置设计。

**推论：没有最坏执行时间和失效安全证据的生成式模型，不应作为硬实时控制或安全功能的唯一权威。** 有界的学习策略可以进入策略环，但须验证其时限和下层保护。

这个项目里，模型选的是**工具**（`navigation.navigate`、`manipulation.pick`），低层动作由 Runtime/控制器或已接入的 Policy Provider 提供（接口支持 VLA / 模仿学习 / RL，不表示已交付通用实机模型）。这条边界在 `docs/architecture/llm-driven-execution.md` 有完整论述。

**教学要点**：实时性关乎完成时限，随机性关乎输出行为，两者不同。更小模型可能满足某个策略环预算，但平均延迟不足以证明最坏时限、控制稳定性或安全性。

### 约束二：停止功能不能依赖不受控的网络

> **不能等网络——等得到的那不叫急停。**

这句话是项目文档的原话（`docs/architecture/why-distributed.md`）。

停止不是瞬间消除动量。检测、通信、制动、惯性和重力负载共同决定停止时间与距离；切断动力还可能使悬空负载掉落。停止方式和时限须按设备风险评估验证。如果急停要经过"浏览器 → 云端 API → 云端协调器 → 边缘 worker → gRPC → runtime → 网关 → 控制器"这样一条链路，那么链路上**任何一环慢 100 毫秒，急停就慢 100 毫秒**。

而对于一个以 0.5 m/s 移动、质量 30 kg 的移动底盘，额外 100 毫秒延迟对应制动开始前多走 5 厘米（尚未计入制动距离）——听起来不多。但如果它面前是一只手呢？

所以这个项目有一条刻意的非目标，写在 README 第十节：

> **不用软件急停替代实体急停。** 软件状态永远低于硬件限制。

**注意这条非目标的精确性**：它没说"不做软件急停"，它说"**不用它替代**实体急停"。软件急停在这个系统里存在（`emergency_stop` 工具），但它是**补充**，不是**保障**。

### 约束三：感知带宽是每秒数十 MB

一台带双 RGB-D 相机的机器人，每秒产生的原始数据量：

| 传感器 | 规格 | 数据率 |
| --- | --- | --- |
| RGB 640×480 @ 30fps | 3 字节/像素 | ~27 MB/s |
| 深度 640×480 @ 30fps | 2 字节/像素 | ~18 MB/s |
| 双相机合计 | | **~90 MB/s** |

**能否上传原始数据取决于链路预算、压缩、隐私和容错要求。**

上述双相机约 92.16 MB/s（十进制单位，未计协议开销）。假设可用上行只有 10–50 Mbps，即 1.25–6.25 MB/s，传输一秒采集的 92.16 MB 理想需约 14.75–73.73 秒，持续上传会积压。高速局域网可以传原始流；受限链路宜上传任务需要的摘要或选定证据。

所以结论是：

> **机器人端必须对一切时间敏感的事情自治。**
>
> 不是"分布式更好"，是"**不这么做就不成立**"。
>
> —— `docs/architecture/why-distributed.md`

### 三条约束的合流

把三条放在一起看：

```
约束一（设备控制周期预算） ─┐
约束二（本地停止安全）           ├──► 机器人端必须自治
约束三（数十 MB/s 感知带宽）   ─┘
```

这些约束支持本地闭环，但具体层数还取决于规模、算力、维护和故障域。

## 1.3 每一层的职责与部署选择

分层被物理逼出来了，但**分成几层**是设计选择。这个项目选了三层，理由如下：

| 层 | 存在的理由 | **不是什么** |
| --- | --- | --- |
| **机器人端** | 实时与安全必须在本地闭环 | 不是"边缘计算省流量" |
| **本地 Agent（边缘）** | **断网可用**——连不上云就不干活的机器人不是机器人，是终端 | 不是缓存层 |
| **云端** | **多机与高算力**：派单、审计、集中推理、跨机经验 | 推理规模不赋予绕过本地安全校验的权限 |

（`docs/architecture/why-distributed.md`）

这张表的每一行右栏都值得展开，因为右栏是**常见误解**。

### 「机器人端」不是边缘计算

"边缘计算"的动机通常是**省流量**或**降低延迟**。这两个动机在这个系统里都是次要的。

真正的理由是：**关键控制和停止链路不能依赖未经时限验证的异步服务。** 这跟"边缘节点算力够不够"无关——即使边缘节点有 A100，控制回路**仍然**必须在控制器里。

### 「本地 Agent」不是缓存层

缓存层的语义是"有它更快，没它更慢"。本地 Agent 的语义是"**有它能干活，没它不能干活**"。

文档给出的判据很尖锐：

> **连不上云就不干活的机器人不是机器人，是终端。**

一台扫地机器人如果每次转弯都要问服务器，那它不是机器人，是"带轮子的瘦客户端"。

### 云端兼顾系统协调与高算力推理

云端可以部署大模型，也可以承担多机协调；这两种能力并不要求在同一进程里实现：

- 机队派单（哪台机器人做哪个任务）
- 跨机审计（A 机发生的事故，B 机能不能避免）
- 跨机学习（A 机解决的故障，B 机受益）

而且有一条不可动摇的边界：**云端不直接控制硬件。**

云端的每个动作都要经过边缘 runtime 的安全校验。这不是"为了安全起见加一道检查"，而是**结构性的**——第 8 章会讲到，`edge/runtime.Command` 这个结构体里**根本没有"命令来自哪里"这个字段**。

## 1.4 反面同样成立：什么时候三层是过度设计

这一节很重要，因为一个只会说"分层好"的架构师是有害的。

项目文档自己写了反面（`docs/architecture/why-distributed.md`）：

> **一台机器人 + 一个人看着 + 非安全关键 → 三层是过度设计。**
> 直接一个进程更简单，而且没有分布式一致性问题。

这句话的信息量比它看起来大。它在说：**分层是拿复杂度换能力**，如果那个能力你用不上，你只是白白付了复杂度。

而"复杂度的真实代价"在这个项目里被逐条列出了（`docs/architecture/why-distributed.md`）：

| 代价 | 具体表现 |
| --- | --- |
| **部分失败成为常态** | 网络分区、时钟漂移、状态分歧 |
| **一致性成本** | 谁说了算？本仓库用 fencing token + 租约回答——**那是真复杂度** |
| **调试跨多层** | 一个动作横跨 robot → edge → cloud |
| **版本漂移** | 机器人固件与 agent 版本不一致（本仓库为此专门做了检测） |
| **每个跨层交互都要写契约测试** | |

而下面这段是全书最诚实的一句话之一：

> 这个仓库之所以需要 fencing token、租约、版本不匹配检测（`internal/discovery` 里真有这个），
> 是因为它选了多机路线。**这些复杂度是那条路线的真实代价，不是可以省的**——
> 它们是"部分失败成为常态"的直接后果。

**"不是可以省的"** —— 这是在说：如果你要支持多机，你就得付这些成本；如果你不想付，那就别支持多机。**没有第三条路。**

### 一张选择表

项目文档给了一张判断表（`docs/architecture/why-distributed.md`），我把它保留原样：

| 你的情况 | 选择 |
| --- | --- |
| 一台机器人，有人在现场 | **本地单机**。少一层，少一类故障 |
| 一台机器人，但要远程运维 | 本地单机 + 出网 |
| 多台机器人，统一派单与审计 | 云端 + 机器人端。**云端不直接控制硬件** |
| 实验室调一台机械臂，非安全关键 | **类 Codex 的单进程架构可能完全够用，而且更简单** |
| 安全关键 / 无人值守 | 必须有闭环契约、失败分类、证据与回放——**与几层无关** |

**最后一行是本章的枢纽**，下一节展开。

## 1.5 真正有价值的三样东西（与分布式无关）

这是本书最重要的一个观点，也是我要花最多力气讲清楚的一个。

大多数人看到"分布式机器人 Agent 系统"，会以为价值在"分布式"。**不是。**

真正的价值是下面三样，而它们**跟有几个进程毫无关系**：

| 机制 | 实现 | 解决的问题 |
| --- | --- | --- |
| **闭环契约** | `core/closedloop` 的 `Gate`：`mutates_world=True` 必须有**动作之后**的新鲜证据，否则 `ErrEvidenceRequired` / `ErrEvidenceStale` | "工具说自己成功了"不是证据 |
| **失败分类** | 8 类：`TRANSIENT` / `PERCEPTION` / `PLANNING` / `PERMISSION` / `RESOURCE` / `VALIDATION` / `UNKNOWN_OUTCOME` / `FATAL`；**只有 Transient 与 Perception 可重试** | 决定"能不能重试"的是一个分类表，不是某个 if |
| **证据与回放** | 任务账本：每一步的工具调用、观测证据、失败分类、恢复动作 | 结论可复核；没有这条就没有"事后追责" |

**这三样是物理世界强加的。** 所以：

> **去掉分布式，这三样依然需要**——单机机器人同样会出现"动作发出去了但不知道成没成"。
>
> **去掉这三样，分布式机器人 Agent OS 就只是个很慢的遥控器**——它有 agent 的形状，没有 agent 的实质。
>
> —— `docs/architecture/why-distributed.md`

### 用代码验证这句话

这不是一个修辞论证。项目里有一条可执行的验证：**Local Agent 砍掉了几乎所有的分布式机制，但没有砍掉这三样。**

| 机制 | Cloud Fleet | Local Agent | 证据 |
| --- | --- | --- | --- |
| 协调器 / claim 协议 | 有 | **刻意没有** | `internal/localapp/app.go` 包注释：*"It **deliberately has no distributed claim or task-lease protocol**: SQLite is the business-state authority and one worker serializes physical work."* |
| Outbox / 事件日志 | 有 | **建了表但不用** | `middleware/sqlite/fleet.go` 建了四张协调表，但 Local Agent 不构造 outbox 消费者 |
| 资源 fencing | 有 | **没有** | 不构造 `lease.Manager` |
| **步骤幂等键** | **有** | **有** | `step_runs` 表的 `step_runs_idempotency_idx` 部分唯一索引 |
| **动作后证据门禁** | **有** | **有** | 同一套 `core/closedloop.Gate` |
| **`UNKNOWN_OUTCOME` 的人工对账** | **有** | **有** | 同一套 `ReconcileStep` + `WHERE reconcile_outcome = ''` |

**代码结构本身就证明了这个论断**：去掉分布式，这三样依然在。

### 所以：判断一个"机器人 agent 系统"是不是真的

看它有没有这三样，而不是看它有几个进程。

具体怎么测？三个问题：

| 问题 | 不合格的回答 | 合格的回答 |
| --- | --- | --- |
| **你的完成判据是什么？** | "工具返回 success" | "动作之后采集的新鲜观测确认了后置条件" |
| **动作结果未知时怎么办？** | "重试" | "不重试，先对账" |
| **失败之后能不能查清发生了什么？** | "看日志" | "账本里有每一步的工具调用、证据 ID、失败分类、恢复动作" |

**第一个问题就能筛掉大部分 Demo。**

## 1.6 最关键的差异：重试的代价

如果这一章只能留一节，我留这一节。

在隔离工作区中重跑纯测试通常风险较低，但仍消耗时间与算力。Coding agent 的部署、网络请求、数据迁移和通知也可能产生不可逆副作用：

```
运行测试 → 失败 → 改代码 → 再运行测试
```

Git 能恢复已记录的文件版本，不能撤销外部服务效果、未记录的数据或全部现场状态。因此两类 Agent 都需要按具体工具判断重试安全性。

**机器人不是这样。**

机器人 Agent 的"重试"可能是**把一件已经做过的事再做一遍**：

```
杯子已经拿起来了 → 你以为失败了 → 再拿一次 → 撞
```

这一条差异派生出整个系统里最不直观的那些设计：

```
动作下发
   ↓
结果未知（UNKNOWN_OUTCOME）
   ↓
【禁止自动重试】
   ↓
必须先用新鲜观测对账（待取证）
   ↓
对账之后才允许决定下一步
```

**任何可能产生外部副作用的 Agent 都需要处理未知结果；机器人把这一责任落实到物理执行与现场对账。**

（`docs/architecture/why-distributed.md`）

### 一张完整的对照表

项目文档给了一张对照表（`docs/architecture/why-distributed.md`）。我把它逐行加上代码事实，因为这张表是本书第 16 章的骨架：

| 维度 | Codex / Claude Code | 机器人 Agent 运行时 | 代码事实 |
| --- | --- | --- | --- |
| **世界** | 文件、进程和外部服务 | **物理世界** | — |
| **观测成本** | 通常较易重复读取，但有权限、并发和资源成本 | **昂贵，有时不可观测** | 双 RGB-D 90 MB/s，且被遮挡就是看不见 |
| **动作可逆** | 文件编辑常可回退，外部效果未必 | **常常不可逆** | `core/closedloop` 的 `UnknownOutcome` 类 |
| **失败代价** | 算力损耗，也可能停服、丢数据或产生外部损失 | **撞坏东西 / 伤人** | 不做软件急停替代实体急停 |
| **重试** | 依工具副作用与隔离条件判断 | **结果未知时禁止重试** | `Retryable()` 只对 `Transient`/`Perception` 返回 true |
| **验证** | 测试与目标状态、外部效果核验 | **新鲜证据 + 闭环门禁** | `Gate(declaration, dispatchedAt, evidence)` |
| **真相在哪** | 当次字节可读取，不等于全部业务真相 | **世界是真相，只能被观测** | `worldmodel.Snapshot` 的每条事实都带 `EvidenceRef` |
| **会话长度** | 可跨会话与长期任务 | **需支持长期持久状态，未证明多年运行** | SQLite 增量迁移、`mapRevision`、标定版本 |
| **人在不在** | 交互或无人值守，依部署而定 | 现场监督或无人值守，依部署而定 | `StepReconciliation` 必须有 `Actor` + `Note` |

### 最后一行值得单独说

"人在不在"这一行看起来最不像技术差异，但它的后果最深远。

交互式 Coding Agent 常可询问用户，但无人值守软件任务也会遇到无人回应的情况。

无人值守时，机器人遇到歧义可能**无法立即获得人的回答**。所以它必须：

- 能**表达**"我不知道"（三值逻辑：`TRUE` / `FALSE` / `UNKNOWN`）；
- 能在"不知道"的时候**停下来**（`GOAL_NOT_CLEAR`、`PLACEMENT_NOT_OBSERVED`）；
- 能把"我不知道"变成一个**等人来处理的排队项**，而不是一个错误日志（`StepReconciliation`）。

**一个"人不在场"的系统，它的每一个"不知道"都必须有归宿。**

## 1.7 关于“OS”：项目名不等于实时保障

这个项目叫 "Robot AgentOS"。项目架构文档提醒，名称不能承诺它没有实现的操作系统职责：

> **"OS"这个词用错了地方。** 这个项目是**机器人 Agent 运行时**，它结构上不保证实时性，也不该保证。

展开来说：

| 操作系统要管什么 | 谁来管 |
| --- | --- |
| **调度** | 设备控制器与适用的 RT 内核；ROS 2 executor 本身不自动保证硬实时 |
| **内存** | 机器人控制系统 |
| **驱动** | 机器人控制系统 |
| **实时性** | **机器人控制系统** |

而**实时性恰恰必须在 gateway / controller 里，不能在 agent 层**：

> 本仓库从结构上就保证不了它，也不该保证：一个会被 LLM 推理延迟影响的控制回路是危险的设计。

**建议的命名**（`docs/architecture/why-distributed.md`）：

| 层 | 名字 |
| --- | --- |
| 电机 / 关节 / 安全监督 / 实时控制 | **机器人控制系统**（Robot Control System） |
| Agent 层（这个项目） | **机器人 Agent 运行时**（Robot Agent Runtime） |
| 多机编排 | **机队控制面**（Fleet Control Plane） |

### 为什么这件事重要：期待错位比能力不足更危险

> 叫它 OS 会让人期待它保证实时性，而它保证不了——**期待错位比能力不足更危险**。

这句话值得每个做系统的人抄下来。举几个机器人领域的例子：

| 说法 | 合理的期待 | 实际的期待错位 |
| --- | --- | --- |
| "机器人操作系统" | 保证实时调度 | 实际上只是个中间件集合 |
| "AI 全自主" | 无需人工介入 | 实际上需要人处理异常 |
| "闭环控制" | 保证收敛 | 实际上只保证"有反馈" |
| "安全认证" | 常被误读为零事故保证 | 验证明确范围内的要求符合性；一般流程检查不能冒称认证 |

**这本书在后续章节里会反复做一件事：明确地说出每个机制"保证什么"和"不保证什么"。** 这是我认为技术写作里最重要的一项纪律。

## 1.8 这一章的三句话

如果你只带走三句话：

1. **裸工具成功回执是进一步核验的触发器；工具携带的可信证据仍可用于确认后置条件。** 这不是工具实现得不够好，是结构性的——裸成功回执没有提供可校验的后置条件证据。

2.  **本地闭环需满足设备时限、停止安全与链路预算** ；具体频率、停止时限和带宽应按设备测量。但 **"分布式"本身不是价值** ——价值是闭环契约、失败分类、证据与回放，这三样在单机上同样需要。

3. **最关键的差异是"重试的代价"。** Coding Agent 的纯测试重试通常风险较低，但外部副作用也须对账，机器人重试可能是"把做过的事再做一遍"。这一条差异派生出了这个系统里所有不直观的设计。

## 1.9 教学要点

### 一个可以先做的课堂演示（10 分钟，不需要机器人）

让每个学生写一个假的 `pick()` 函数：

```python
def pick(object_name: str) -> dict:
    """模拟一个会随机漏夹的抓取。"""
    import random
    # 30% 的概率实际没夹住，但工具层完全不知道
    return {"success": True, "object": object_name}
```

然后让他们写一个"任务完成判定"，要求：**不信任 `success` 字段**。

学生通常会写出三种方案：

| 方案 | 问题 |
| --- | --- |
| 再调一次 `pick()` 确认 | **灾难**——第二次抓取可能撞到已经夹住的杯子 |
| 调 `get_gripper_state()` 看夹爪宽度 | 好一些，但"夹爪闭合"不等于"夹住了目标物体"（可能夹住了旁边的） |
| 调 `detect_object(名称)` 看物体还在不在原地 | 接近正确，但"物体不在原地"不等于"在夹爪里"（可能掉地上了） |

**然后引入"证据必须晚于命令下发"这条规则**：如果学生用了一个缓存的观测（比如 5 秒前拍的画面），这条规则会拒绝它。

这个演示不需要任何硬件，但它能让学生亲手体验"为什么完成判定根本不是一个简单问题"。

### 学生最容易误解的五个点

| # | 误解 | 纠正 |
| --- | --- | --- |
| 1 | "工具返回成功只是工具实现得不好，我写个更好的工具就行" | 开环回执没有完成证据。工具可集成观测，但系统仍须核验其来源、关联与后置条件 |
| 2 | "分布式就是为了扩展性" | 分布式同时服务故障隔离与扩展；必须明确部分失败和所有权假设 |
| 3 | "多一层就多一份能力" | 分层是**拿复杂度换能力**。一台机器人 + 有人看着 + 非安全关键 → 三层是过度设计 |
| 4 | "仿真里跑通了就是跑通了" | 仿真证明契约闭合，不证明物理策略可用。**软件发布与实机放行是两项独立结论** |
| 5 | "叫它 OS 只是叫法问题" | 期待错位比能力不足更危险。叫它 OS 会让人以为它保证实时性 |

### 三道练习题

**题 1**

一台机器人在 0.5 m/s 移动。有人提出："我们用云端 LLM 做急停决策，因为它能判断当前情境是否危险，比固定规则更智能。"

请计算：若假设首 token 出现时就能立即形成停止命令，首 token 延迟800 ms，链路额外120 ms，恒速0.5 m/s，则命令到达前至少经过多久、移动多远？为什么真实停止距离还会更长？为什么这组平均/单次延迟不足以放行急停设计？

<details>
<summary>答案要点</summary>

- 在题设的简化假设下，命令到达耗时至少800 + 120 = **920 ms**。首 token 通常不是完整决策，还可能有后续生成、解析与排队。
- 命令到达前恒速行程至少0.5 m/s × 0.92 s = **0.46 m**；之后还需控制器响应和机械减速。没有减速度、负载与制动条件，不能计算最终停止距离。
- **为什么不足以放行**：需给出端到端响应时限、检测漏判、超时/失联行为和停止回路的验证证据。平均200 ms或一次5秒都不能确定最坏上界。可用预算和看门狗约束模型调用耗时，但超时后必须由独立可靠路径承担停止责任。
- 加分点：本项目把停止责任留给本地控制和实体停止回路；其响应与机械效果仍须实测和设备验证，不能仅因使用固定规则就声称毫秒级保障。模型可提供分析或受控建议，不能自行变更安全策略或成为唯一停止保障。

</details>

**题 2**

有人说："你们这套闭环契约、失败分类、证据回放，都是因为你们做了分布式。我们做单机，不需要这些。"

请用项目里的一条可执行证据反驳，并给出你自己的验证方法。

<details>
<summary>答案要点</summary>

- **证据**：Local Agent 是单机形态（SQLite + 单进程），它的包注释明确写着 *"deliberately has no distributed claim or task-lease protocol"*——它砍掉了协调器、租约、outbox、fencing。**但它保留了步骤幂等键、动作后证据门禁、`UNKNOWN_OUTCOME` 的人工对账。**
- 也就是说：**分布式机制被砍掉了，闭环机制一个都没砍。** 这证明两者是正交的。
- **自己的验证方法**：问单机系统三个问题——① 完成判据是什么？② 动作结果未知时怎么办？③ 失败之后能不能查清每一步发生了什么？单机系统同样会"动作发出去了但不知道成没成"（进程崩溃、网络抖动、工具超时）。
- 加分点：指出**去掉这三样的单机系统，是一个遥控器**——它有 agent 的形状，没有 agent 的实质。

</details>

**题 3**

下面是一个"完成判定"的三种实现。请按安全性排序，并说明每一处的问题：

```python
# 方案 A
def done(tool_result):
    return tool_result["success"]

# 方案 B
def done(tool_result, latest_observation):
    return tool_result["success"] and latest_observation is not None

# 方案 C
def done(tool_result, observation, dispatched_at):
    return (tool_result["success"]
            and observation is not None
            and observation["observed_at"] >= dispatched_at
            and observation["observation_id"] != "")
```

<details>
<summary>答案要点</summary>

- **排序：C > B > A**。
- **A 的问题**：把工具的自述当证据。参见四种失败情形（漏夹、夹错、卡住、超时）。
- **B 的问题**：有观测，但**没有检查它是不是这次命令的观测**。一个 5 秒前的缓存观测同样是"not None"。这是最隐蔽的一类 bug——代码看起来做了检查，实际上检查了什么都没说。项目里的真实案例：历史实现里两个调用点都写字符串字面量 `"FRESH"`，导致"来源过期就拒绝"这条规则**永远不会触发**。
- **C 还差什么**：
  - **缺 `Freshness` 检查**。项目里的 `validateFreshness` 还要拒绝 `STALE` 和 `UNKNOWN`。
  - **时间比较的粒度问题**。当前 Gate 截断到整毫秒并接受同桶，这是兼容策略，不能证明采集发生在下发之后；还须考察设备序列、命令关联及跨机时钟误差（第 3 章、附录 D）。
  - **缺错误分类**。C 只回答了"能不能算完成"，没回答"失败了该怎么办"——而后者决定了会不会重复一次物理动作。
- 满分答案会指出：**C 是 `Gate` 的简化版**，真正的实现还要加 `Reason` 字段让拒绝原因可诊断。

</details>
