# 第 6 章 多 Agent 运行时：为什么不能只做一个万能 Agent

> **本章的核心命题**
>
> 通用 coding agent 的多智能体（subagent / workflow）是一种**上下文经济技术**——
> 为了并行、为了不让一个子任务污染主对话的上下文。
>
> 机器人 Agent 运行时的多智能体是一种**权限与证据技术**——
> 为了让"观察者碰不到机器人"成为**类型的性质**，而不是一条纪律。

---

## 6.1 从一次真实事故说起：发布通道没接上

这个项目的多 Agent 运行时来自一次**具体的失败**。

早期的接线代码手工给**执行 Agent** 装了发布通道，但**观察 Agent 没装**。后果：

- 观察 Agent 发现的每个问题都进了告警存储；
- **从未上过事件总线**；
- 因此没有任何订阅者看到它们；
- 恢复 Agent 从来没被触发过。

**而单元测试全绿。**

原因写得很精确（`agentruntime/orchestrator.go:141-155`）：

> 因为每个测试都**自己注入了 sink**：它们验证的是一套**生产环境并不存在的接线**。

### 修法：把注入从组合根移进运行时

```go
// Start 里做的事（orchestrator.go:156-167）
// 把总线「注入」每个实现了 Publisher 的已启用 Agent
```

**为什么这是修法？** 因为"每个 Agent 有没有发布通道"从"接线代码的职责"变成了"**运行时的职责**"。

而且运行时还把结果打进启动日志（`:614-618`），理由是：

> **"没什么可说的"和"根本说不了话"从外面看一样。**

**教学要点**：这是一个"**把纪律变成机制**"的例子。

| | 纪律 | 机制 |
| --- | --- | --- |
| 形式 | "实施者要记得给每个 Agent 注入发布通道" | "运行时给每个 Agent 注入" |
| 失败模式 | **静默**——忘了一个，测试还全绿 | 结构上不可能忘 |

**"测试自己注入了 sink，所以它验证的是一套不存在的接线"** —— 这与第 2 章修复 1（测试用手工 fixture 替换真实生产者）是**同一个失效模式的两种形态**：

> **测试里那个"恰好对"的东西，在生产里恰好不存在。**

## 6.2 Agent 契约：九个方法，两半

Agent 的接口定义在 `core/` 而**不在**运行时包里。这个位置选择本身有理由（`core/agentcontract/contract.go:1-11`）：

> TaskAgent 必须能作为 Agent 使用，而**核心执行路径不应因此导入那个还知道注册表、事件总线和编排的层**。

真实签名（`contract.go:199-229`）：

```go
type Agent interface {
	// 静态半：启动任何东西之前被读
	Name() string
	Version() string
	Capabilities() []Capability
	Subscriptions() []string
	Permissions() Permission

	// 动态半：运行期用
	Health(ctx context.Context) Health
	OnEvent(ctx context.Context, event Event) error
	Execute(ctx context.Context, request ExecuteRequest) (ExecutionOutcome, error)
	Shutdown(ctx context.Context) error
}
```

**"静态半 / 动态半"这个划分值得注意**：身份、订阅、权限可以在启动任何东西**之前**被读出来——所以运行时能在启动前拒绝一个配置不合法的 Agent，而不是在运行到一半时才发现。

### `Permission` 的零值是最安全的读法

```go
// contract.go:70-91
// 零值：只读、不改世界、需要批准
```

**这是一个"零值安全"的设计**：一个忘了填权限的 Agent，得到的是**最小权限**，而不是最大权限。

（这与第 9 章 `RecoveryAction.Executable()` 的白名单、第 3 章 `Classify` 的保守兜底是同一条原则：**默认值必须是收紧的那一侧**。）

### 发布能力不在 `Agent` 里

发布是**可选接口**：

```go
// core/agentcontract/publisher.go:27-29
type Publisher interface {
	SetPublish(func(Event))
}
```

**为什么可选？** 因为不是每个 Agent 都需要发布——一个纯粹的计算型 Agent 可以不发布任何东西。把它放进 `Agent` 会让每个实现都要写一个空方法。

**教学要点**：接口的**大小**是一个设计决定。"所有 Agent 都必须能发布"和"能发布的 Agent 实现额外的接口"，前者更简单，后者更准确。这里选了后者，而代价是**运行时必须做一次类型断言**——这也正是那次事故的场所（接线代码手工做断言，忘了一个）。

## 6.3 注册表：注册与启用分离

`Registry` 的三个字段就是它的全部（`agentruntime/registry.go:19-23`）：

```go
agents map[string]agentcontract.Agent
order  []string
config Config
```

### 注册拒绝五种情况

`Register`（`:44-71`）拒绝：

| # | 拒绝 | 理由 |
| --- | --- | --- |
| 1 | nil | — |
| 2 | 空名 | — |
| 3 | 名字带首尾空白 | **它是配置键，必须精确** |
| 4 | **`len(agent.Capabilities()) == 0`** | **什么都不声明的 Agent 更可能是接线错误** |
| 5 | 订阅了词表外模式 | 见下 |

重名返回 `ErrAgentAlreadyRegistered`，理由是：

> **名字给持久事件归属，冲突会让回放有歧义。**

**第 4 条值得单独说**：一个"什么都不声明"的 Agent 被拒绝，而不是被接受为一个无害的空实现。

**这是一个关于"配置错误"的判断**：一个没有能力的 Agent 有 99% 的概率是接线写错了，而不是真的设计成一个无所事事的 Agent。

### 订阅必须能被发布

订阅模式的检查返回 `UnknownTopicError`（`:423-431`），理由（`:135-138`）：

> **订阅一个没人能发布的主题是拼写错误**，而启动时失败的拼写错误是一份 bug 报告，**静默失败的是一个永远不上报的 Agent**。

**"一个永远不上报的 Agent"** —— 这就是第 8.1 节那次事故的形态。这次它被一个**启动期检查**拦住了。

### `Validate`：配置启用了但未注册的名字，被拒绝而不是跳过

这条取舍（`:111-130`）的理由：

> 否则**运维会以为一个观察者正在运行**。

**"被拒绝"和"被跳过"的区别，就是"我知道出错了"和"我以为一切正常"的区别。**

### 注册与启用分离是刻意的

`:12-18` 说明了理由：**可以把 Agent 随构建发布，再用配置决定它跑不跑。**

这带来一个非常重要的能力——**`ExecutableConfig()`**：

```go
// config.go:73-75
// 只启用 "task"
```

而它是一个**受支持的配置**，不是测试夹具。它的用途（`docs/architecture/multi-agent-runtime.md:116`）：

> 用来判断"**观测本身有没有改变行为**"。

**这是一个可执行的对照实验**：

```
配置 A：TANGYING_AGENTS=task                → 只有一个执行 Agent
配置 B：TANGYING_AGENTS=task,ops,recovery   → 加上观察者与恢复
```

**断言：两者的任务结果逐字节相同。**

如果不同，说明**观察者改变了自己观察的对象**——这违反了"运行时是观察者，从不是参与者"。

### 一个细节：常量手动重复

`TaskAgentName` / `OpsAgentName` 常量在 `config.go:32,35` **手动重复**而不从实现包导入，因为（`:28-31`）：

> **本包不得导入它托管的 Agent 实现。**

**这是依赖倒置原则在一个很小的地方的体现**：注册表知道"有一个叫 task 的 Agent"，但**不知道 `task` 是什么类型**。

## 6.4 消息总线：八条设计决定

总线类型是 `AgentRuntime`（`agentruntime/bus.go:50-89`）。包注释先立了一条压倒一切的规则（`:1-15`）：

> **运行时是执行过程的观察者，从不是参与者……一个慢的、错的或被关掉的运行时，让执行保持原样。**

**这一句话决定了后面八条设计**。逐条看：

### 决定 1：不是广播，是每订阅者独立队列

`Publish` 遍历订阅者，对 `MatchesAny` 命中的投递（`:195-200`）。

**设计理由**（`:44-49`）：

> 共享队列会让**一个停止读取的观察者拖慢所有其他 Agent**，并在队列满后开始**让别人丢事件**；这里每个订阅者有自己的 pending 集，**溢出记在造成它的订阅者头上**。

**"溢出记在造成它的订阅者头上"** —— 这是多租户系统的一条通用原则：**故障的账单要寄给制造它的人。**

### 决定 2：`Publish` 永不阻塞、永不返回错误

```go
// executor.go:172
func (r *AgentRuntime) Publish(ctx context.Context, event agentcontract.Event)
```

**没有 error 返回值。** 注释明说这"不是偷懒"（`:165-171`）：

> 调用方是**正在执行任务的 Agent**，一个必须处理的发布失败会**把事件流变成安全路径的一部分**。

**"如果发布失败需要处理，那事件流就成了安全路径的一部分。"**

这是一个非常深的判断。如果 `Publish` 返回 error，那么每个调用点都要写：

```go
if err := runtime.Publish(ctx, ev); err != nil {
    // 现在怎么办？重试？失败任务？
}
```

而"怎么办"这个问题**没有正确答案**——因为发布失败**不应该影响执行**。既然没有正确答案，就不要让它成为一个必须回答的问题。

**教学要点**：**API 的形状决定调用方要想多少事。** 一个返回 error 的函数在要求调用方处理一件事；如果那件事无法处理，就不要返回 error。

### 决定 3：去重是必需的，因为一个事实有两条入口

```go
// bus.go:58-69
seen map[string]struct{}   // 记住已投递的事件身份
```

**为什么一个事实会有两条入口？**

```
路径 1：Agent 直接发布一个事实
路径 2：同一事实被记进按任务的持久账本 → 账本观察者喂回总线
```

两条路**携带同一身份**（由账本序号派生），所以第二次到达被识别而不是重复。

注释（`:64-66`）：

> **没有这一层，任务 Agent 做的每个动作都会在回放里出现两次。**

`seen` 有界：每 4096 次投递清空一次（`seenPruneInterval`，`:91-94,220-224`），只需覆盖两条路可能竞争的窗口。

**教学要点**：**去重的必要性来自"同一件事有多个入口"。** 这是一个通用模式——只要一个事实可以从两处到达，就必须有身份。

### 决定 4：溢出按优先级驱逐

每个订阅者的 pending 按 `Priority` 分桶（`:312-324`）。满时 `evictFor(priority)`：

| 情况 | 行为 |
| --- | --- |
| 存在**严格更低**优先级的 pending | 丢**最老的那个** |
| 所有 pending 都比新事件重要 | **丢新事件本身** |

理由（`:306-311`）：

> 否则一个低价值遥测的洪水会**挤掉这个 Agent 存在的唯一理由**——那一条关键事件。

**"如果所有已排队的都比新来的重要，就丢掉新来的"** —— 这一条很讲究。

很多实现的驱逐策略是"总是丢最老的"。但在这里，如果队列里全是 Critical 事件，而新来的是一个 Low 遥测，那么**正确的做法是丢掉新来的**——因为旧的那些更重要。

**教学要点**：一个有优先级的队列，它的驱逐策略也必须是有优先级的。**"先进先出"在混合优先级的队列里是错的。**

### 决定 5：优先级四档，Critical 的定义很具体

```go
// core/agentcontract/event.go:45-58
Low / Normal / High / Critical
// Critical = 「可能要求停止物理工作」的事件
```

**注意 Critical 的定义方式**：它不是"很重要"，而是**"可能要求停止物理工作"**。

**这是一个可判定的定义**，不是一个模糊的等级。

### 决定 6：关闭时先排空再报错

```go
// bus.go:389-408
// Receive 在订阅关闭后先把已 pending 的排空，再报 ErrSubscriptionClosed
```

理由：

> 这样**关停不会静默丢弃 Agent 还没读到的事件**。

**教学要点**：**关闭是一个需要设计的操作。** "关闭时丢弃所有未处理的东西"是最简单的实现，但它会让"系统关停前发生了什么"变得不可知——而那恰恰是排障时最想知道的事。

### 决定 7：持久化与唤醒是两个旁路端口

| 端口 | 作用 | 错误处理 |
| --- | --- | --- |
| `EventSink` + `SetEventSink`（`:445-459`） | 把事件写进已有账本 | **best-effort，错误绝不回传给发布者** |
| `onPublish` + `SetPublishObserver`（`:111-120,439-443`） | 只做一次非阻塞"推一下" | — |

**为什么需要"推一下"？** 因为运行时把事件投进每订阅者队列却**刻意不为每个订阅者起 goroutine**（`:80-88`）。必须有东西告诉排空者"队列值得排空了"。

**"刻意不为每个订阅者起 goroutine"** —— 这是资源上的取舍：N 个订阅者就是 N 个常驻 goroutine 加 N 个 channel。用"推一下"的模式，排空发生在需要的时候。

### 决定 8：寿命计数应该永远是 0

```go
// bus.go:268-273
Published() / Dropped()
```

注释：

> **`Dropped` 应保持为 0**，非 0 意味着某个 Agent 相对于它订阅的速率太慢。

**这是一个可观测的告警指标，而且它的期望值是一个确定的数：0。**

**教学要点**：**一个好的健康指标，它的"正常值"应该是确定的。** "队列深度 500"是正常还是异常？取决于负载。"丢事件数 = 0"永远正常，非 0 永远异常。

### 投递语义总结

| 性质 | 值 |
| --- | --- |
| 投递时机 | **同步**（在发布者 goroutine 上入队） |
| 消费 | **每订阅者异步** |
| 过滤 | 按模式（"定向广播"） |
| ack | 无 |
| 重投 | 无 |
| 去重 | **有**（按事件身份） |
| 驱逐 | **有**（按优先级） |
| 寿命计数 | `Published()` / `Dropped()` |

**注意"无 ack、无重投"** —— 这不是一个可靠消息队列，它是一个**观察通道**。

**而这是对的**：观察者丢一个事件不应该让执行重试。**可靠性属于执行路径，不属于观察路径。**

## 6.5 编排器：唯一拥有「排序」这个决定的地方

`Orchestrator` 明确写出了它**不**做什么（`agentruntime/orchestrator.go:16-30`）：

> 它**不决定**任务是否完成、某步是否可重试、某个物理动作是否可派发——那些已经有主；
> **第二个决策者持不同意见，是系统开始自相矛盾的起点。**
>
> 它唯一拥有的决定是**排序**：观察者在机器人运动中提议时，提议要等。

**"第二个决策者持不同意见，是系统开始自相矛盾的起点。"**

这句话应该被用在每一次"我们要不要再加一层判断"的讨论里。

### 五条具体机制

**① `Start` 先 `registry.Validate()`。**

配置不能被满足时，系统**保持原样而不是半启动**。

**教学要点**：**"半启动"是一个比"启动失败"更糟的状态。** 因为运维会以为它在跑。

**② 编排器自己用 `supervisorPatterns()` 订阅全部命名空间。**

理由（`:46-52`）：

> 把仲裁建立在 Agent 订阅的**并集**上，会让**关掉一个观察者静默关掉保护移动机器人的那条规则**。

**这是一个非常隐蔽的耦合**：如果编排器的订阅范围依赖于 Agent 的订阅集合，那么"禁用某个 Agent"这个操作会**顺手改变编排行为**——而运维完全不会预期到这一点。

**③ `deliver` 先 drain 再等 wake，且从订阅里「拉」而不是被推。**

```go
collect 带 20ms 超时    // :324-332
```

理由：**这样慢 Agent 不能拖住编排器。**

**④ supervisor 的更新先于 Agent。**

顺序上（`:255-266`）：**仲裁状态必须在任何 Agent 看到事件之前更新。**

**教学要点**：**顺序即语义。** "先更新仲裁状态再看事件"和"先看事件再更新仲裁状态"，会让 Agent 看到的事件携带不同的在飞状态。

**⑤ Agent 的事件处理失败不向上传播。**

记为 `agent.health_changed{EVENT_HANDLING_FAILED}`（`permission.go:184-200`），理由：

> **观察者的反应失败是观察者自己的问题**，让任务背上就是把**可观测性变成安全路径的一部分**。

**这是"运行时是观察者，从不是参与者"这条总规则的具体落地**：观察者出问题，任务照跑。

### 一个真实缺陷：计数器留下的永久 +1

`trackPhysicalAction`（`:356-391`）按 `commandId` 记录在飞的物理命令。注释记录了一个真实缺陷（`:56-68`）：

> 早期用**计数器**，`SENDING(+1) RUNNING(+1) CONFIRMED(-1)` 留下**永久 +1**，
> 于是 `PhysicalActionInFlight` 对那个任务**永远为真**、每条恢复建议被永久推迟——
> **"最需要一个操作员的那种情况，恰恰是运行时沉默的那种。"**

**修法**：按 `commandId` 记录，而不是计数。

**为什么计数器会错？** 因为 `SENDING` 和 `RUNNING` 是**同一个命令的两个阶段**，它们都 `+1`，但只有一个 `CONFIRMED` 来 `-1`。

**教学要点**：**计数器的失效是累积的，而且不可恢复。**

| | 集合 | 计数器 |
| --- | --- | --- |
| 表示 | 有哪些命令在飞 | 有几个命令在飞 |
| 重复加入同一元素 | 幂等（集合） | **+1（泄漏）** |
| 重复移除 | 幂等 | **-1（可能变负）** |

**当你能给元素一个身份时，用集合；只有在元素无法区分时才用计数器。**

`AWAITING_EVIDENCE` **结束**在飞窗口（`:344-355`），因为机器人已经停了——这个细节说明"在飞"的定义不是"命令没结束"，而是"**机器人可能还在动**"。

### 推迟必须有记录

`deferIfPhysicalActionInFlight`（`:409-421`）不只扣住事件，还发布：

```
ops.recovery_deferred{deferredReason: "PHYSICAL_ACTION_IN_FLIGHT"}    // :425-435
```

理由：**"没有记录的推迟与丢弃无法区分。"**

`releaseDeferred`（`:439-473`）释放时**赋予新的事件身份**：

```go
released.ID = ""      // 原身份已被去重消费
```

理由：

> 原样重发会被当作**重复抑制**，提议就丢了而不是被推迟。

**教学要点**：这是一个**去重与重放冲突**的经典陷阱。

去重表记得"这个身份见过"，所以"重新投递同一个事件"会被静默丢弃。**释放一个被推迟的事件时，必须给它一个新的身份**——因为它是一次新的投递。

**这和第 3 章那个 `ObservationAttempt` 是同一类修正**：对账时必须用一个**新的读取身份**，否则幂等缓存会把中断前的旧观测当新证据回放。

> **幂等与重试的交界处，必须显式地"换一个身份"。**

## 6.6 三类 Agent：职责边界

当前启用三类：**task + ops + recovery**（`config.go:63-65`）。

| | `task` | `ops`（产品名 **Review Agent**） | `recovery` |
| --- | --- | --- | --- |
| 实现 | `edge/agent.Runner` | `agentruntime.OpsAgent` | `agentruntime.RecoveryAgent` |
| **输入** | 宿主给的 `ExecuteRequest`（**不订阅事件**） | 事件 + 遥测 + 故障台账 + 持久执行记录 + 持久任务索引 | 一个 `Finding` |
| **输出** | 任务终态、动作、证据 | `ops.anomaly_detected` / `root_cause_hypothesis` / `recovery_proposed` / `escalation_required` / `anomaly_cleared` | `ops.recovery_plan`（含轨迹与目录） |
| **权限** | `ReadOnly=false, MutatesWorld=true, MutatesTaskState=true, RequiresApproval=false` | `ReadOnlyPermission()` | `ReadOnlyPermission()` |
| **`Execute`** | 委托给 `RunControlled`，闭环规则一条不少 | **恒返回 `ErrNotExecutable`** | **恒返回 `ErrNotExecutable`** |

### 一个必须纠正的命名问题：Review Agent = OpsAgent

**"Review Agent" 在 Go 里没有对应标识符**（全仓库 `grep ReviewAgent` 只命中文档）。

它是 `OpsAgent` 的**产品角色名**。

**所以：Review Agent 已实现。** 真正"只有接口与扩展点、没有实现"的是三个：

| 未实现 | 状态 |
| --- | --- |
| `eval` | 只有能力标签 + 扩展点文档 + 一段骨架 |
| `experience` | 同上 |
| `escalation` | 同上 |

（`contract.go:59-67` 明确把它们标注为 **reserved**。）

### TaskAgent：不订阅事件

`Subscriptions()` 返回 **nil**，理由（`edge/agent/agent.go:56-59`）：

> 它在**被要求时**执行任务，**不对事件作出反应**；
> 假装它订阅会让它进入一条投递路径，而**慢执行者会在那里丢掉它从不需要的事件**。

**这是一个很实际的判断**：TaskAgent 是执行者，它可能很慢（一次 `build_map` 可能几分钟）。如果它也订阅事件，它的队列会堆积一堆它不需要的事件——而按决定 4 的驱逐策略，这些事件可能会**挤掉别的 Agent 需要的**。

**不订阅，就不占用队列容量。**

它的 `RequiresApproval=false` 也是刻意的（`:61-68`）：

> 物理工作的批准**已经在执行路径里逐步强制**（`Task.Approved` 然后派发门），
> 在 Agent 层再复制一遍"**要么冗余，要么成为以后有人放松的那一条**"。

**"要么冗余，要么成为以后有人放松的那一条"** —— 这是"第二道检查"的一个精确风险描述。

（这与第 5 章 `ScopeOf` 那段"第二道防线"的注释**恰好相反**——那里保留第二道是因为"两者防的是不同的改动"；这里不设第二道是因为"两者防的是同一件事"。）

**判断标准**：如果两道检查防的是**同一件事**，第二道是冗余；如果防的是**不同的改动**，第二道是必要的。

### OpsAgent：不能做，是结构决定的

**这是本章最重要的设计。**

`OpsAgent` **没有任何执行端口、任务服务或总线句柄**（`opsagent.go:20-27`）。而这一点由一张**字段白名单反射测试**钉住（`agentruntime/opsagent_test.go:44-105`）：

```go
for index := 0; index < fields.NumField(); index++ {
	if _, ok := allowed[field.Name]; !ok {
		t.Fatalf("OpsAgent has a new field %q...", field.Name)
	}
}
```

**加任何新字段都会失败**，注释说明理由：

> 这强制"**观察者需不需要这个**"这个问题被**刻意回答**，而不是被静默吸收。

**教学要点**：这是一个非常强的技术手段，值得单独命名——**字段白名单反射测试**。

| | 普通测试 | 字段白名单反射 |
| --- | --- | --- |
| 检查 | 已知的行为 | **未知的字段** |
| 新增一个 `RobotClient` 字段 | 测试可能仍全绿 | **立即失败** |
| 效果 | 验证你想到的 | **强制你重新回答一个设计问题** |

**"恢复 Agent 突然能动机器人了"必须是一次显式的、被评审的改动** —— 这句话的实现就是一个 for 循环。

### 规则是确定性的，不猜

`opsagent.go:35-42` 的原则：

> 当证据不足时，Agent **说出缺哪条证据**，而不是产出一个看似合理的成因。
> 操作机器人的人需要知道**一句话是被证明的还是被怀疑的**。

规则本体在 `opsrules.go`：`Evaluate(input) []Finding` 依次跑：

```
safety → fault → uncertain mutation → failed action → latency → abnormal task → stale telemetry
```

阈值是**文档化常量**而不是学出来的基线：

| 常量 | 值 |
| --- | --- |
| `DefaultTelemetryMaxAge` | 10 s |
| `DefaultStepLatencyBudget` | 30 s |
| `maxEvidenceRefs` | 8 |

### `Finding` 的关键字段

| 字段 | 语义 |
| --- | --- |
| `Category` | 所属**闭环失败类**（非失败类为空） |
| `RecommendedActions` | **人的**动作，按顺序 |
| `MissingEvidence` | 说不清时**说明缺什么** |
| `AutomaticRetryForbidden` | **只为物理结果未知设置**，是"唯一一条不得在下游被软化的建议" |
| `Confidence` | **由产生它的规则给定**，而非从数据估计 |

**最后一条很讲究**：置信度不是算出来的，是规则给的。因为"这条规则的可靠性"是一个**关于规则的陈述**，不是一个关于数据的陈述。

### 身份：一个必须全系统同意的键

```go
Identity() = agentcontract.AnomalyIdentity(code, component)    // opsrules.go:110-121
```

注释记录了一个真实的失败（`:112-118`）：

> 告警存储按 `code@component` 建索引、恢复 Agent 按**裸 `code`** 归档计划、控制台按**裸 `code`** 查——
> 结果是一份计划被显示给 **11 个不同的组件失败**，每个都在读一份**诊断里写着另一个组件名字**的计划。

**三处对"同一个异常的身份"用了三种定义。**

**教学要点**：**"这个异常是谁"这个问题，全系统必须只有一个答案。** 而这个问题在多组件系统里比看起来难——因为"同一个 code 出现在两个组件上"到底是一个问题还是两个问题，取决于你的判断。

这里的答案是：**两个问题，两份计划**（`recoveryagent.go:289-293`）：

> **code 标识一类问题；身份标识这个问题。**

### 上报去重键：稳定条件不刷屏，恶化的状态必须重播

```go
// core/agentcontract/anomaly.go:46-52
AnomalyReportID = Identity + "#" + 数量
```

注释：

> **稳定条件不刷屏，恶化的状态必须重播。**

而 `SameAnomaly` **只在 `#` 边界比较**（`:54-68`），所以 `CODE@a` 不会匹配 `CODE@ab`。

**教学要点**：这是一个"字符串拼接当复合键"时必须显式处理的陷阱。`"CODE@a" + "#" + "1"` 和 `"CODE@a#1"` 是同一个字符串——如果不用分隔符边界比较，就会误判。

### 四类事件的语义分工

```
anomaly       说事实
hypothesis    说结论
proposal      说建议
escalation    说"要人"
```

理由（`docs/architecture/supervision-verification.md:88`）：

> **合成一个事件，读者就分不清哪句是观测、哪句是推断。**

### 「不执行」的三重保证

| 层 | 机制 |
| --- | --- |
| 1 | `AutomationAdvisory = "advisory"`（`opsagent.go:539`）——proposal 恒 `RequiresApproval=true` |
| 2 | `Execute` 恒返回 `ErrNotExecutable` |
| 3 | **字段白名单：没有任何执行端口** |

第 1 层的注释：

> **这个 Agent 的每一条建议都是人的工作；把它提议成自动化会误表述已知的东西。**

### 两类作用域：任务级与机器人级

| 作用域 | 去哪 | 例子 |
| --- | --- | --- |
| 任务级 | 该任务的账本 | 步骤失败、延迟超预算 |
| **机器人级** | `AlertStore` | **急停、模块故障、观测过期** |

理由（`runnermemory.go:18-21`）：

> **急停不是任务问题**，无论有没有任务在跑，它都是**操作员必须听到的那件事**。

而早期版本给机器人级发现**空 taskID**，后果（`:10-26`）：

> **发给了没人、也没记在任何地方。**

**教学要点**：**"不属于任何任务"的发现需要一个归宿。** 一个只有"按任务索引"的存储，会让这类发现静默消失。

### `Health()` 在"看不见"时返回 DEGRADED

```go
// opsagent.go:160-204
// 运行着但没有观测可推理 → DEGRADED，不是 HEALTHY
```

注释：

> **一个看不见的观察者不是健康的**；说清这一点就是**"没有坏事"与"我判断不了"之间的差别**。

**这正是世界模型三值逻辑那条原则在 Agent 健康上的投影**（第 4 章）。

### RecoveryAgent：只提议不执行

定位（`recoveryagent.go:17-41`）：

> 这个类型**不持有执行端口、任务服务或机器人客户端**。即使它决定要跑一个恢复动作**也跑不了**——与观察 Agent 遵循同一条结构规则：
> **"一个只做建议的 Agent"应当是「这个类型」的性质，而不是它当前配置的性质。**
> 执行属于运行时，在权限门控之后，**这样只有一处需要审计**。

而它由 `TestRecoveryAgentHoldsNoExecutionPort` 钉住（`recoveryagent_test.go:46-73`），白名单字段：

```
Catalog / ReadFacts / Model / Publish / RememberPlan / Now / mu / proposals / stopped
```

注释：

> **加一个 `RobotClient` 字段会让它失败**——这是有意的，因为"恢复 Agent 突然能动机器人了"必须是**一次显式的、被评审的改动**。

由此得到一条**可以直接对用户承诺的性质**：

> **在这一版里，恢复 Agent 不可能自己动手。**

### 事实是值，不是活句柄

```go
// recoveryagent.go:77-114
type RecoveryFacts struct { ... }
```

注释：

> 它**刻意是普通结构体而不是存储的活句柄**：Agent 必须**无法触及任何它没有声明的东西**，而**一个值不能被用来跑一条没人记录的查询**。

**"一个值不能被用来跑一条没人记录的查询"** —— 这是一句非常精确的安全论证。

如果 Agent 拿到的是 `*sql.DB`，它可以跑任意查询。如果它拿到的是 `RecoveryFacts`，它能看到的**恰好是**那些被填进去的字段——而"填了什么"在一次代码评审里是可以看完的。

### 三态区分：这是本节的精髓

```go
UncertainSteps             // 确实存在未知步骤
ReconciliationUnavailable  // 问不出来
ReconciliationError        // 原因
```

文档说明了它修的是什么静默漏洞（`docs/architecture/recovery-agent.md:78-102`）：

> **「这个任务没有结果未知的步骤」和「这个部署查不出来」曾经产生同一个结果——空列表**；
> 于是执行存储不可达时，**调查看起来像世界状态已确认**，恢复计划照常给出。

**"空列表"同时表示"没有"和"不知道"** —— 这是本章最值得记住的一处**类型设计失败**。

**修法是把它拆成两个字段**（一个有值的列表 + 一个"问不出来"的布尔），而不是在文档里写一句"注意区分"。

### 一条压倒一切的规则：先对账

`choosePlan`（`:505-630`）在三种情况下**都转人工、不给步骤**：

| 情况 | 轨迹步 |
| --- | --- |
| `AutomaticRetryForbidden` | `rule.reconcile-first` |
| 存在 `UncertainSteps` | `rule.reconcile-first` |
| `ReconciliationUnavailable` | `rule.reconcile-unknown` |

第三种情况的代价是**停下来**，收益是（`recovery-agent.md:102`）：

> **不会在一个可能已经动过的世界上再动一次。**

**注意第三种情况包含了"问不出来"** ——也就是说：**查不到"有没有未对账的步骤"时，系统按"可能有"处理。**

**教学要点**：这与第 3 章 `OpsAgent.uncertainSteps` 在读不到存储时返回 `nil` 是同一个判断：

> **"读不到" ≠ "没有"。**

### 确定性路线永远生效

> **"先看再动永远不会错"** —— 只读匹配永远排在前面（`:588-596`）。

有模型时，模型选出的步骤**前缀在确定性只读步骤之后**（`:615-623`）。

而且只有在模型输出**真的进入返回计划的那一处**才把 `Source` 标成 `"deterministic+model"`（`:627-628`），理由：

> 对一份**模型从未看过的计划**报"来自规则 + 模型"，是关于来源的、**纯粹的假声称**。

### 恢复目录：模型驱动恢复的承重安全边界

`recoverycatalog.go:5-16` 是这套机制的宪法：

> 模型可以推理一个不熟悉的故障并提出**新颖的序列**，这正是用一个模型的意义——
> **但它提出的每一步都必须命名这里的一个条目。**
> **它不能发明动作，也不能触及一个未被列出的接口。**

**16 条动作**：

| 风险级 | 条数 | 批准要求 |
| --- | --- | --- |
| `read_only` | **6** | 不需批准 |
| `bounded_write` | **7** | **必须**批准 |
| `never_automatic` | **3** | **谁的提议都不执行** |

三条 `never_automatic`：`estop.release` / `hardware.replug` / `calibration.change`，**每条带目录自己写的拒绝理由**。

而 `:19-28` 有一条关于"批准"归属的精确陈述：

> **「批准」是动作的属性，不是提议者的属性。**
> 随着更多提议者出现（模型、模式库、未来的策略引擎），否则**每个都需要自己的一套"什么安全"的概念，而它们会漂移**。

**"批准是动作的属性，不是提议者的属性"** —— 这一句话可以推广到所有权限系统。

### 校验：拒绝会否决整份计划

`recoveryagent.go:632-668` + `:365-403`：

| 情况 | 处理 |
| --- | --- |
| 目录里没有的动作 | **按名字拒绝并附目录自己的理由** |
| `!Executable()`（即 `never_automatic`） | 同上 |
| 重复动作 | 只保留第一次（"**对一次写来说，重复运行就是第二次没人要求的物理动作**"） |
| **`refusals` 非空** | **否决整份计划**：`Verdict=ESCALATE`、`payload.Steps=nil` |

而**被拒动作留在轨迹里供复核**，理由（`:365-403`）：

> **提议者既然对"什么允许做"的理解是错的，它剩下那部分推理也不值得执行。**

**教学要点**：这是一个"**一票否决**"的设计。

替代方案是"过滤掉不允许的步骤，保留其余的"。这个项目选了否决整份计划，理由是**提议者的整体判断力已经被证伪**。

**这是一个可以辩论的取舍**，但它的论证是清楚的：一个连"什么允许做"都搞错的推理链，它的其余部分不太可能是对的。

### 冷却

```go
recoveryPlanCooldown = 2 * time.Minute    // :695-696
```

防止持续条件**每个 tick 重新调查、重新问一次模型**。

**教学要点**：这是一个成本控制，但它也是**安全**的——因为"每 5 秒重新规划一次恢复方案"意味着**模型在持续地看**，而每次调用都是一次潜在的幻觉。

## 6.7 执行通道：提议与执行在代码里被分开

### 手动通道：`internal/recoveryexec`

`docs/architecture/recovery-agent.md:197-253` 记录的关键约束：

| 约束 | 内容 |
| --- | --- |
| `Executable()` | 只放行 `read_only` 与 `bounded_write` |
| 工具必须存在 | 声明的工具必须**真的存在** |
| **没配批准入口时不执行** | **"没法问"不等于"可以"** |
| 执行范围 | = 该动作声明的工具 |

**两种批准来源分别记**：

| 来源 | 语义 |
| --- | --- |
| `approval.operator` | 操作者点按钮（**点击即批准**） |
| `approval.granted` | 上游批准端口 |

因为：**"有人能批准"和"这次确实有人批准了"在事后追溯里是两句话。**

**教学要点**：这是一个"**把两种来源区分开**"的例子。它们的**效果**相同（都是批准），但**证据价值**不同——而审计需要的是后者。

### 自动通道：`internal/autorecovery`

**线画在"目录说它 `read_only`"上，不是画在"工具自称不改世界"上**（`internal/autorecovery/supervisor.go:16-23`）。

`runOne` 在 `action.Risk != agentruntime.RiskReadOnly` 时直接 skip 并记理由（`:183-190`）。

文档的关键判断（`recovery-agent.md:266-267`）：

> 目录里 **7 个会动机器人的动作全是 `bounded_write`**，所以自动通道**结构上够不到它们**——
> **守卫和能力是同一个事实，不是一道可以被删掉的检查。**

**"守卫和能力是同一个事实"** —— 这是本章最漂亮的一句设计陈述。

意思是：不是"有一个守卫拦住了它们"，而是"**自动通道的能力范围里根本没有它们**"。删掉那个 `if` 也不会让自动通道动机器人——因为目录里那些动作**标着 `bounded_write`**，而自动通道的逻辑只挑 `read_only`。

它用 `OperatorApproved: false` 标记记录（`:196-204`）：

> 说成别的，就是把**一个人的同意写进了一份没有同意的记录**。

**真实数据**（52 个任务）：

| 动作 | 自动执行成功次数 |
| --- | --- |
| `observe.re-read` | **21** |
| `execution.read-history` | **6**（接线前 8 次全部因工具缺失失败） |
| 账本 | **27 条** `ops.recovery_executed`，且 `operatorApproved` 为空 |

**这组数字很重要**：它证明"只自动跑只读恢复"不是一个空机制——**它真的跑了 27 次，而且没碰过机器人。**

### 触发链：为什么是订阅者而不是内部调用

组合根用一个**独立订阅者**订阅 `ops.anomaly_detected`，把事件还原成 `Finding` 再调 `recovery.Recover`（`cmd/local-agent/agentruntime.go:178-214`）。

理由（`:181-183`）：

> 这样观察 Agent 保持只读、两个角色保持可分离——
> **和这里其他地方 Agent 从不直接互相调用是同一个理由。**

**"Agent 从不直接互相调用"** —— 这是本章的一条隐含架构规则。

它带来的好处是：**Agent 之间的耦合只通过事件**，而事件是有 schema 的、可回放的、可去重的。如果 Agent 直接互相调用，就会出现"两个 Agent 之间的私有协议"——而那是最难审计的东西。

## 6.8 故障矩阵：16 个场景与覆盖守卫

### 分类体系：8 类，179 条表项 / 177 个唯一码

（第 3 章已详述 8 类的定义与唯一安全的下一步。这里只补三个数字的辨析，**因为它们是三个容易混淆的数**。）

| 数字 | 含义 | 出处 |
| --- | --- | --- |
| **113** | 提交 `c8cae5af2`（09-17）那一刻 `runtimeEmittedCodes` 清单的条数 | **历史值** |
| **119** | 今天的 `runtimeEmittedCodes` 清单**唯一码**数（123 条含 4 条重复） | 覆盖守卫的输入 |
| **177** | 今天 `closedloop` **分类表**覆盖的唯一码数（179 条表项） | 分类表的输出 |

**三个数字互不等价。** 文档里的"113 个运行时故障码"是**历史快照**，不是当前值。

**教学要点**：这是第 5 章那条纪律的又一个实例——**引用"数量"时必须给出测量它的方法与时间**。

### `faultmatrix_test.go` 钉住了什么

文件头说明了它回答的问题不是"观察者有没有规则"（那由 `opsagent_test.go` 覆盖），而是：

> 当一个**真实任务**出问题时，监督者**是否真的说了有用的东西**。

每个场景驱动**真实 `OpsAgent`**，断言三件事：

1. **检出了**；
2. **按系统其余部分的方式分类了**；
3. **带一条人能执行的动作**。

第三条是重点，也是**以前从未测过的**（`:30-33`）：

> **一条没有可用建议的 finding 就是一行日志**：它告诉操作员一件他本来就能看到的事，而没告诉他该做什么。

### `wantRetryForbidden` 每个场景都显式断言

`assertScenario`（`:306-348`）里，`wantRetryForbidden` **不是只在为真时断言**，而是每个场景都断言。理由（`:48-52`）：

> **危险的回归是一条失败的"禁止重试"悄悄消失。**

**教学要点**：这是一个**断言设计**的重要细节。

如果只在"应该禁止"的场景里断言，那么当我们**误把**一个场景改成"不禁止"时，测试**不会失败**（因为我们删掉了那个断言或它本来就没写）。**每个场景都断言，才能发现"该禁止的没被禁止"。**

### 16 个场景

**`TestFaultMatrixCoversEveryFailureClass`（10 个，覆盖 8 类）**

注意 `PLANNING` 有**三例**（`TARGET_UNREACHABLE` / `NAV_WORKSPACE_LIMIT` / `NAV_STEP_LIMIT`）——一类多例。

| 类 | 建议必须含 | 关键断言 |
| --- | --- | --- |
| `TRANSIENT` | "可重试" | — |
| `PERCEPTION` | "重新观测/搜索" | — |
| `PLANNING` | "新的目标/路径" | 三例 |
| `PERMISSION` | "审批/租约/资源" | — |
| `RESOURCE` | 同上 | — |
| `VALIDATION` | "参数/版本/重放" | — |
| **`UNKNOWN_OUTCOME`** | **"不要自动重试/对账"** | **severity=critical + `wantRetryForbidden`** |
| `FATAL` | "人工" | — |

**`TestFaultMatrixCoversNonCodeFaults`（6 个非错误码场景）**

| 场景 | 异常码 | `Category` | 关键点 |
| --- | --- | --- | --- |
| 机器人报 `blocked` 模块 | `ANOMALY_COMPONENT_FAULT` | **`""`** | "**blocked 故障不是闭环重试类，监督者不得假装它是**" |
| 急停 | `ANOMALY_SAFETY_STOP` | `Permission` | critical + "人工复位/急停" |
| 执行记录里 `STARTED` 的物理步骤 | `ANOMALY_UNVERIFIED_MUTATION` | `UnknownOutcome` | critical + **禁止重试** |
| 90 s vs 30 s 预算 | `ANOMALY_STEP_LATENCY` | **`""`** | "**慢步骤不是失败类，不得给它安一个**" |
| 120 秒前的观测 | `ANOMALY_TELEMETRY_STALE` | — | — |
| 完全没有观测 | `ANOMALY_TELEMETRY_STALE` | — | **同一个码** |

**两处 `Category = ""` 值得单独讲。**

系统**刻意不给它们安一个失败类**，理由是"**监督者不得假装它是**"。

**这是一个"宁可为空，不要错填"的设计。** 一个被强行归类的异常会得到错误的"唯一安全的下一步"建议——而错误的建议比没有建议更糟（第 3 章：`GOAL_NOT_CLEAR` 被报成"结果未知，先对账"，而底盘根本没动过）。

**最后两行也值得注意**：120 秒前的观测和完全没有观测，得到**同一个码**。因为在"我能不能判断"这个问题上，它们的答案相同：**不能**。

### 升级：重复失败

`TestFaultMatrixEscalatesOnRepetition`（`:285-303`）：同一动作失败 3 次 → severity 从 warning 升到 **critical**。

理由（`:283-284`）：

> **一次发生是平常的；第二次意味着自动处理已经没起作用了。**

**教学要点**：**"重复"本身是一个信号。** 单次故障是噪声，重复故障是模式。系统的严重度不是故障类型的函数，而是**故障类型 + 重复次数**的函数。

### 覆盖守卫：分类表唯一的守卫

`core/closedloop/classification_coverage_test.go` 存在的理由（`:15-30`）：

> 兜底会让"运行时产生了、表忘了"的码**静默降级**成"结果未知、不要重试"——
> **失败看起来像一次安全决定，其实是少了一条表项**。

**真实案例**：`GRASP_NOT_REACHED`（抓手够不到目标）曾经就是这样被报成未知物理结果，于是系统告诉操作员**不要重试一个正确恢复方式是"重新观测再试"的步骤**。

### 一份人工维护的清单，理由值得引用

```go
// classification_coverage_test.go:34-38
// runtimeEmittedCodes 是人工维护而非自动抓取：
// 「对两种语言做正则会是第二件会出错的事」
```

**"第二件会出错的事"** —— 这是一个非常诚实的判断。

自动抓取看起来更"工程化"，但它引入了**第二个可能出错的解析器**（正则跨 Python/Go）。而人工清单的失效模式是**可见的**（守卫会红），自动抓取的失效模式是**静默的**（正则没匹配到，清单少了一条，守卫以为齐了）。

**教学要点**：**"自动化"不总是更可靠。** 当自动化的正确性依赖于一个脆弱的假设（正则能匹配所有写法）时，一个显式的人工清单加上一个会失败的守卫，可能更可靠。

### `Knows()` 把前提本身也钉住了

`TestKnowsDistinguishesListedFromUnlisted`（`:303-317`）断言：

> 一个被列为 `UnknownOutcome` 的码，和一个完全没被列出的码，`Classify` 结果**相同**。

如果哪天两者**不再同样分类**，这个测试会失败并提示"**前提变了**"。

**教学要点**：这是一个"**测试一个函数为什么存在**"的测试。

`Knows()` 的存在理由是"`Classify` 无法区分这两种情况"。如果有一天 `Classify` 能区分了，`Knows()` 就冗余了——而这个测试会告诉你。

**这是一类很少见的测试：它测的不是行为，是"这个抽象还有必要吗"。**

### 一个新发现的未修缺陷：两套词表

`GRASP_NOT_REACHED` 在 **Go 侧**被显式归为 `PERCEPTION`（`closedloop.go:176`），但 **Python 的 `FAMILIES` 八族没有任何一族包含它**，所以巡检报"未归类"。

`commit 5dfa9728e` 修过 `tool_layer.py` 的**镜像表**，但 `diagnose_task.py` 的故障族表与 `closedloop` 的分类表**仍是两套独立词表**。

**这与 ADR-1 拒绝的"新开一条总线"是同一个问题**：**同一个概念有两份定义。**

而它的通用检测方法，**这个项目自己已经有了**——`tools.json` 从代码生成，`--check` 断言逐字节相同。**同一手法应该被用到分类表上。**

## 6.9 Agent 上下文评测：三轮实验的真实数字

这一节是本章最硬的部分。

### 背景：`TANGYING_AGENT_CONTEXT` 三种模式

| 模式 | 内容 |
| --- | --- |
| `legacy`（**默认**） | 不改变旧线格式 |
| `json` | 确定性 JSON 渲染 |
| `stage` | 按环节选择表达 |

### 第一轮：全程上下文

| 指标 | 基线 | 启用后 |
| --- | --- | --- |
| 准确率 | **8.33%** | **74.17%** |
| 提升 | | **+65.83 pp**，CI [+51.67, +79.17]，**p=0.000092** |
| Token | 3,849.1 | 7,789.7 |

**从 8.33% 到 74.17%。**

### 第二轮：按环节选择表达

| 指标 | JSON 基线 | stage 模式 |
| --- | --- | --- |
| 准确率 | 65.00% | **87.19%** |
| 提升 | | **+22.19 pp**，Holm **p=0.000040** |

**但**：vs **统一策略**仅 **+2.19 pp，不显著**。

**教学要点**：这是一个**必须一起给出的对照**。

"+22.19 pp，p=0.000040" 是一个显著的结果；但"vs 统一策略 +2.19 pp 不显著"说明——**提升来自"用了结构化上下文"，不是来自"按环节选择表达"**。

**如果只报第一个数字，读者会以为"按环节选择"是关键；实际上它不是。**

### 第三轮：两模型因子实验

**规模**：480 个完整状态（train 80 / dev 80 / test 320）；**12,484 个不同真实请求**；**31,716,142 tokens**；**协议/传输失败 0 个**。

**四因素主效应**（单位百分点）：

| 模型 | syntax | order | annotation | complete |
| --- | --- | --- | --- | --- |
| deepseek-flash | +0.55（Holm 1） | +4.30（0.2446） | +3.20（0.2504） | **+73.55（0.00016）** |
| deepseek-v4-pro | +1.17（1） | **−4.30**（0.0608） | **+5.08（0.0391）** | **+65.51（0.00016）** |

**四条结论**：

1. **语法主效应在两个模型上都不显著** —— "JSON 还是受控中文"**本身不是决定性的**；
2. **`order` 对两个模型符号相反**（flash +4.30、pro −4.30）；
3. **唯一稳健的显著项是确定性元数据标注**（Pro +5.08 pp）；
4. **"删掉必要字段"是压倒性的**（+73.55 / +65.51）。

**第 4 条是这一轮最重要的发现**：**信息完整性比表达格式重要一个数量级。**

### masked 双生：一个漂亮的反例

> **"模型不知道自己不知道"的反例。**

两个模型的 masked（隐藏必要字段）结果：

| 指标 | 值 |
| --- | --- |
| 状态答案正确 | **0.00%** |
| 证据支持正确 | **100.00%** |
| 拒答 | **100.00%** |
| 无支持断言 | **0.00%** |
| 危险建议 | **0.00%** |

**删掉必要字段后正确率塌到 0，同时拒答率升到 100%。**

**这是"信息不足时拒答可以被系统性做到"的证据。** 模型没有猜——它说"我不知道"。

**教学要点**：这与第 3 章的三值逻辑、第 8.6 节的 `ReconciliationUnavailable` 是**同一条原则**：

> **系统必须能表达"我不知道"，而不是把它降级成一个猜测。**

### 八环节完整信息矩阵：最刺眼的结论

**"规划"环节在两个模型 × 8 种表达下，全部为 0.00%。**

其他环节：

| 环节 | 范围 |
| --- | --- |
| 反思 | 50–75% |
| 交接 | 52.5–77.5% |
| 恢复（Pro） | **低到 2.50–50%** |

结论：**上下文表达解决不了规划环节的能力问题。**

### 统计功效被如实算出来

报告自己算了功效：

| 量 | 值 |
| --- | --- |
| 每环节 n=4 时双侧符号翻转的**最小非零 p** | **2/16 = 0.125** |
| 要让分布无关界 ≤ 5 pp，保守估算需要 | **至少 4,615 个独立族** |

**所以本轮无法提供严格的逐环节优越性证明。**

**教学要点**：**这是本书里最值得学习的一段科研诚实。**

研究者自己在报告里写："我这个实验的功效不够，无法支持我想证明的那个结论。"

**而它比一个虚假的显著性更有价值**——因为它告诉后来的人"要做这个结论，你需要 4,615 个族"。

### 追加实验

**A（层级结构）**：

| 模型 | 准确率 | Token 变化 | 规划环节 |
| --- | --- | --- | --- |
| flash | 71.88% vs 69.79%（+2.08） | **降 36.70%** | **仍然 0%** |
| pro | 65.62% vs 61.46%（+4.17） | **降 27.14%** | **仍然 0%** |

**"规划仍然 0%，所以不能反推『扁平化导致规划失败』"** —— 一个精确的推理边界。

**B（显式决策契约）**：

| 模型 | 恢复环节 | 危险建议率 |
| --- | --- | --- |
| pro | **4.17% → 62.50%** | **仍有 25%** |
| flash | 契约候选**未通过准确率门禁，回退基线** | — |

**"不能把其中一个模型的改善推广到所有模型。"**

### 最终工程处置：`deployment-policy.json`

规划、验证（危险率 12.5%）、恢复（25%）被写进 `blocked_stages`。

文档原话：

> **"规划候选的相对门禁虽然『与零分基线持平』，不具备上线资格"**
>
> **"不能用最高候选分数掩盖这个负结果"**

**"不能用最高候选分数掩盖这个负结果"** —— 这句话应该被抄在每一个做评测的人桌上。

### ⚠️ 一处必须标注的边界：规则没有自动生效的生产接线

`ProjectWithFactorPolicy` 在**全仓库非测试 Go 代码里 0 个调用点**。

生产走的是 `agentcontext.Project` + `ProductionFactors()`（`factorial-fixed.v1`，**不接受模型名**）。

而产物 `deployment-policy.json` 还在被 `.gitignore:109` 忽略的 `artifacts/` 下，**仓库测试加载不到**。

**准确的表述**：

> 这条规则**已实现、有单测覆盖、有真实产物，但没有自动生效的生产接线**。

**教学要点**：这是"**没通电**"的又一个样本（第 5 章的 `RequestMutation` 是第一个）。

它和那个的区别是：`RequestMutation` **完全没被调用**；`deployment-policy.json` **被生成了但没被消费**。

**两种形态的共同点**：**有实现、有测试、有文档，没有生效的路径。**

## 6.10 与通用 coding agent 的多智能体差异

| 维度 | coding agent 的 subagent / workflow | 机器人 Agent 运行时 |
| --- | --- | --- |
| **为什么多** | **上下文经济**：隔离、并行 | **权限分离**：让"不能做"成为类型性质 |
| **能不能互相调用** | 通常可以（父调子、子返回） | **从不直接调用**——只通过事件 |
| **子 Agent 的产物** | 文本结果 | **带来源与有效期的事实包** |
| **安全边界** | 提示词 + 工具白名单 | **字段白名单 + 类型无执行端口** |
| **观察者的失效** | 少一个结果，重跑 | **沉默被读成健康** |
| **危险建议** | 用户可以否决 | **`AutomaticRetryForbidden` 不得在下游被软化** |
| **Agent 的消失** | 任务失败，可见 | **一个 Agent 没跑起来，任务照常，没人知道** |

### 最核心的一条差异

> **coding agent 的多智能体是一种上下文经济技术；机器人 Agent 运行时的多智能体是一种权限与证据技术。**

展开说：

| | coding agent | 机器人 |
| --- | --- | --- |
| 主要成本 | **Token 与上下文窗口** | **物理动作的不可逆性** |
| 主要风险 | 子任务结果不对 | **观察者获得了动手的能力** |
| 因此的结构 | 尽可能共享上下文 | **尽可能少连接口** |

### 一条具体的对比：`OpsAgent` 的字段白名单

在 coding agent 里，一个"观察者"子 Agent 如果拿到了 shell 工具，它可以做任何事——**而这是正常的**，因为它的任务就是执行。

在机器人系统里，观察者拿到一个 `RobotClient` 字段就是**一次安全事故**——而这个项目用一个反射测试**让它在 CI 里失败**。

**"恢复 Agent 突然能动机器人了，必须是一次显式的、被评审的改动。"**

### 五道练习题

**题 1（"空列表"的歧义）**

> `RecoveryFacts` 把"确实没有未对账步骤"和"查不出来"拆成了两个字段（`UncertainSteps` + `ReconciliationUnavailable`）。
> 请说明在拆分之前，"空列表"意味着什么，以及为什么这个歧义会产生危险的后果。

<details>
<summary>答案要点</summary>

**拆分之前**：两者都产生**空列表**。

**危险的后果**（文档原话）：

> 于是执行存储不可达时，**调查看起来像世界状态已确认**，恢复计划照常给出。

**具体链条**：

1. 执行存储（SQLite）临时不可读；
2. `Uncertain` 查询失败 → 返回空列表；
3. 恢复 Agent 看到"没有未对账的步骤"；
4. 它认为世界状态是确定的；
5. **它给出一个包含物理动作的恢复计划**；
6. 而实际上**可能有未对账的步骤**——机器人可能已经动过；
7. 执行那个计划 → **在一个可能已经动过的世界上再动一次**。

**教学点**：**"没有"和"不知道"被压成同一个值，是类型设计的失败，不是文档能修的。**

修法必须是**类型层面**的：两个字段，或者一个三态枚举（`Known([]Step)` / `Empty` / `Unknown`）。

**同类例子（项目里真实的）**：

1. `OpsAgent.uncertainSteps` 在执行存储不可读时返回 `nil`——但规则**已经会报告"存储缺失"这件事**，所以编造一个空列表会被读成"没有任何不确定"。
2. 世界模型的三值逻辑（`TRUE`/`FALSE`/`UNKNOWN`）。
3. `Health()` 在"看不见"时返回 DEGRADED 而不是 HEALTHY。

**加分点**：指出这类 bug 的共同特征是**危险的失败是静默的**——它不产生错误，它产生一个看起来正常的空值。

</details>

**题 2（去重与重放）**

> `releaseDeferred` 释放一个被推迟的事件时必须给它**新的身份**（`released.ID = ""`）。
> 请解释为什么"原样重发"会导致事件丢失，并给出项目里一个同类的例子。

<details>
<summary>答案要点</summary>

**为什么原样重发会丢**：注释写得很直接——

> 原样重发会被当作**重复抑制**，提议就丢了而不是被推迟。

**机制**：去重表 `seen` 记得"这个事件身份见过"。原样重发时，`firstDelivery(event.ID)` 返回 false，事件被**静默丢弃**。

**结果是**：一个本该被推迟后交付的提议**永久丢失**，而系统认为它已经被处理过了。

**同类例子**：`RunControl.ObservationAttempt`（第 3 章）：

```go
// A new read identity prevents runtime idempotency caches from returning
// pre-interruption verification evidence during an explicit resume.
ObservationAttempt string
```

对账时必须用**新的读取身份**，否则运行时的幂等缓存会把**中断前的旧观测**当成新证据回放——于是系统会"确认"一个它根本没检查过的世界。

**共同模式**：

> **幂等与重试的交界处，必须显式地"换一个身份"。**

因为幂等机制的设计前提是"同一个身份 = 同一件事"。当你**故意要做第二遍**（推迟后释放、对账时重新读取）时，你必须告诉系统"**这是一次新的尝试**"。

**加分点**：指出这个陷阱在实现上非常隐蔽——代码看起来是"重新发布同一个事件"，而直觉上这是对的。

**"重新发布同一个事件"在幂等系统里是一个需要显式处理的特殊操作，不是一个默认行为。**

</details>

**题 3（为什么多 Agent）**

> 有人提议：既然 task / ops / recovery 三类 Agent 都通过事件通信，为什么不合成一个 Agent，内部调用三个函数？代码会少一半。
> 请用代码事实反驳，并指出这个提议会失去哪三种保证。

<details>
<summary>答案要点</summary>

**会失去的三种保证**：

**① "观察者碰不到机器人"不再是类型的性质。**

现在：`OpsAgent` **没有任何执行端口**，由字段白名单反射测试钉住。
合成后：一个 Agent 有了执行端口，于是"观察者不要用它"变成了一条**纪律**。

**② "恢复 Agent 不能自己动手"不再是类型性质。**

文档原话：

> "一个只做建议的 Agent"应当是**这个类型**的性质，而不是它当前配置的性质。

**③ 可丢弃性失去可验证性。**

现在：`TANGYING_AGENTS=task` 关掉观察者，**任务结果逐字节不变**——这是一个可执行的对照实验。
合成后：关掉"观察函数"意味着什么？没有对应的对照。

**代码事实**：

| 事实 | 位置 |
| --- | --- |
| `OpsAgent` 无执行端口 | `opsagent.go:20-27` |
| 字段白名单反射测试 | `opsagent_test.go:44-105` |
| `RecoveryAgent` 无执行端口 | `recoveryagent.go:17-41` |
| `recoveryagent_test.go:46-73` 白名单 | 同上 |
| 两类的 `Execute` 恒返回 `ErrNotExecutable` | `opsagent.go:209-211`；`recoveryagent.go:257-259` |
| `ExecutableConfig()` 只启用 task | `config.go:73-75` |

**加分点**：指出这个提议的**合理部分**——代码确实会少，而且"通过事件通信"在单进程里确实有开销。**反驳的关键不是"分层更好"，而是"分层的收益是可以被验证的"**（关掉观察者后任务结果不变）。

**再加分**：指出这与第 8 章 `Command` 无来源字段是**同一种手法**——

> **把约束实现为"结构上不可能"，而不是"检查后拒绝"。**

</details>

**题 4（第二道检查：什么时候该留）**

> 第 5 章里，`ScopeOf` 被保留为"第二道防线"，理由是"两者防的是不同的改动"。
> 而 TaskAgent 的 `RequiresApproval=false`，理由是"在 Agent 层再复制一遍要么冗余，要么成为以后有人放松的那一条"。
> 请说明这两个判断**不矛盾**，并给出判断"第二道检查该不该留"的标准。

<details>
<summary>答案要点</summary>

**为什么两个判断不矛盾**：

| | 第一道 | 第二道 | 防的是同一件事吗 |
| --- | --- | --- | --- |
| `ScopeOf` | 工具列表（决策者看不到就不能选） | 批准范围 | **不是**——前者防"这一次传了什么"，后者防"**当时批准了什么**" |
| TaskAgent 审批 | 执行路径里的 `Task.Approved` + 派发门 | Agent 层的 `RequiresApproval` | **是**——都是"物理工作要不要人批" |

**判断标准**：

> **如果两道检查防的是同一件事，第二道是冗余（且会漂移）；
> 如果防的是不同的改动，第二道是必要的。**

**`ScopeOf` 那段注释给出了标准的具体化**：

> 工具列表是**这个函数恰好传了什么**；scope 是**当时批准了什么**。
> 如果 `resolve` 被放宽——"让模型看到机器人提供的一切"是一个很可能出现的改动——**列表就不再约束任何东西**，而这个仍然成立。

**所以关键问题是**：

> **有没有一个合理的、可能会发生的改动，会让第一道失效但第二道仍然成立？**

有 → 留；没有 → 删（或者把第一道改成不会失效的形式）。

**TaskAgent 的情形**：没有这样的改动——因为"审批"这件事本来就只有一种做法（`Task.Approved` + 派发门）。**两边都做同一件事，所以其中一边会漂移。**

**加分点**：指出这个标准也可以用来**判断该不该有第一道**。如果第一道是"决策者看不到就不能选"，那么它其实是**最强的那一道**——因为它不依赖任何检查逻辑，只依赖"选择空间里没有它"。**这就是"结构性排除"比"事后过滤"强的地方**（第 3 章）。

</details>

**题 5（统计功效）**

> 第三轮实验报告自己算出：每环节 n=4 时双侧符号翻转的最小非零 p = 2/16 = 0.125，因此**本轮无法提供严格的逐环节优越性证明**；要让界 ≤ 5 pp 需要约 4,615 个独立族。
> 请说明：**为什么报告要把这个算出来？** 如果不算，会有什么后果？

<details>
<summary>答案要点</summary>

**为什么要算出来**：

1. **防止读者过度解读。** 报告里有一些 p 值接近显著（如确认集 +6.25 pp，Holm p=0.06552）。如果不说功效不足，读者可能把这些当作"趋势显著"。
2. **防止自己过度声称。** 研究者写下这个数字，等于给自己划了一条线：**"我不能声称逐环节优越性。"**
3. **给后来的人一个可执行的预算。** "需要 4,615 个族"是一个**可以据此设计下一个实验**的数字，而不是一句"样本不够"。

**如果不算的后果**：

| 后果 | 说明 |
| --- | --- |
| **虚假的显著性** | 在有多个环节、多种表达的组合里，总会有某个组合看起来显著——这是多重比较问题 |
| **无法复现的结论** | 后来的人不知道要多少样本才能验证，于是做一个小实验，得到相反结果，然后互相怀疑 |
| **"与基线持平"被当成"有效"** | 报告里确实有一条：规划候选的相对门禁"与零分基线持平"，而文档明确写"**不具备上线资格**" |

**教学点**：

> **一个诚实的实验报告，它的功效分析和方法学局限与它的结果同样重要。**

**加分点**：指出这个项目在别处也做了同类的事——

- 第 3 章：GVF 实验报告区分"实测"与"离线估计"，并明确写"不能当作九组自主机器人实测"；
- 第 10 章：覆盖率报告区分"同分母对比"与"两个分母不可比"；
- v0.7.0 发布说明："历史实验存在未通过结果，**不能因为代码发布而改称能力已通过**"。

**这是一以贯之的方法论纪律。**

</details>

### 学生最容易误解的四个点

| # | 误解 | 纠正 |
| --- | --- | --- |
| 1 | "Review Agent 是一个未实现的规划" | **Review Agent = `OpsAgent` 的产品名，已实现**。Go 里没有 `ReviewAgent` 标识符。真正未实现的是 `eval`/`experience`/`escalation` |
| 2 | "三个 Agent 通过事件通信，所以可以合成一个" | 合成会失去**三种类型保证**（观察者无执行端口、恢复者无执行端口、可丢弃性可验证） |
| 3 | "上下文表达方式（JSON vs 自然语言）是效果的关键" | **语法主效应在两个模型上都不显著**。**"删掉必要字段"是压倒性的**（+73.55 / +65.51）。**信息完整性比表达格式重要一个数量级** |
| 4 | "有 113 个运行时故障码" | **113 是历史值**（提交 `c8cae5af2` 时的清单条数）。今天：清单 **119 个唯一码**（123 条），分类表 **177 个唯一码**（179 条）。**三个数字互不等价** |

## 6.12 本章小结

1. **多 Agent 在这套系统里是权限与证据技术，不是上下文经济技术。** 通用 coding agent 的多智能体为了隔离上下文；这里为了让"观察者碰不到机器人"成为**类型的性质**。

2. **字段白名单反射测试**是一个可复用的强手段。它把"这个类型不应该拥有某种能力"从一句注释变成**一个会失败的 for 循环**。

3. **"空列表"不能同时表示"没有"和"不知道"。** 这是类型设计失败，不是文档能修的——修法必须是类型层面的（两个字段或三态枚举）。

4. **三轮上下文实验的真实结论**：第一轮 8.33% → 74.17%（p=0.000092）；第二轮 +22.19 pp 但 vs 统一策略仅 +2.19 pp 不显著；第三轮**语法主效应两模型均不显著，信息完整性 +73.55/+65.51 pp 压倒性**。**规划环节在所有候选上 0.00%，被禁止套用。**

5. **报告自己算出功效不足**（每环节 n=4，最小非零 p=0.125，需要约 4,615 个族）。**这比一个虚假的显著性更有价值。**

6. **"不能用最高候选分数掩盖这个负结果。"**
