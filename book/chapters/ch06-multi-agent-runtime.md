# 第 6 章 多 Agent 的职责、通讯与协作协议

**学习目标**：按责任划分Agent；解释事件投递与落盘；构造不可混用的故障因果链。

**先修知识**：第3、5章；发布订阅模型。

**关键术语**：Agent角色、事件信封、因果binding、持久账本、发布权限

## 6.1 角色划分的依据

Agent是带输入、状态、工具范围和决策规则的角色，可以由模型或确定性程序实现。划分依据应是权限、上下文、证据责任和失效隔离，不是为了增加模型数量。

| Local角色 | 当前责任 | 不持有的权力 |
| --- | --- | --- |
| task | 推进获批任务、执行与取证 | 绕过Runtime/审批 |
| ops | 读事件与摘要、异常分类和根因假设 | 直接改机器人/任务终态 |
| recovery | 从目录提出调查/恢复计划 | 自行执行恢复 |
| executor/verifier | 受控执行、独立复验与记录 | 用提案替代授权 |

当前Ops/Recovery主要是确定性角色；Fleet Worker也不天然装配这套Local拓扑。模型调用阶段、进程和角色是不同维度。

## 6.2 事件是受约束的消息

agent.event.v1信封含ID/topic、agent/version、task/revision/robot/step/command、causation/correlation、时间、优先级及payload。事件可以是事实、建议或回执，其含义由topic与发布者权限限定。

Orchestrator注入绑定注册身份的发布口。观察者不能发布动作已执行或任务已完成；ops.recovery_executed只由实际executor/verifier接线发布。该门禁约束受信组件误接线，不是恶意同进程插件隔离。

新事件用UUID，账本投影/镜像保留来源ID。同ID同内容去重，同ID不同身份、参数或fence记录冲突，不按“最后到达”覆盖。

## 6.3 实时通道与持久账本

EventBus按topic有界订阅，慢消费者可能丢消息并有计数。当前同步发布可能先投实时队列再调用sink，因此收到事件不等于持久化完成。

TaskEvent提供任务持久历史与回放。执行事实向总线投影，Agent诊断/计划再写回同一账本；关键恢复判断读取持久链，不依赖某个订阅者是否曾收到。运行时级无taskId广播也不等于任务持久记录。

不能同时承诺“订阅者不阻塞执行”和“每个实时订阅者永不丢事件”；可靠性来自有界通道、可检查计数、持久权威与恢复规则。

## 6.4 精确恢复binding

```text
原失败sourceId → Ops异常anomalyId → Recovery计划planId
       → 实际执行/独立复验 → 原等待器判断可继续
全链绑定：task / revision / robot / step / command
```

correlation目前按任务检索，不足以区分一次命令。causation指直接原因；source/anomaly/plan串起整段恢复。另一设备、旧版本或同工具另一步的计划不能解除原等待，缺字段保持未知。

## 6.5 调查与物理执行的协作关系

关键物理动作在途时，建议由Orchestrator延期到安全点。恢复建议不抢占动作，也不自行切换任务版本。只读瞬时故障可在完整持久binding、白名单调查、独立复验和预算匹配后一次重读；物理unknown保持对账。

新增Agent应明确订阅、权限、发布事实和退出条件。评测/经验/升级等接口存在，不等于对应Agent已经在生产启用。

### 协作推演：从告警到合法续跑

一次 navigation.status 只读查询失败后，Task 发布原失败，Ops 提取故障和派发阶段，Recovery 提出调查计划，executor 重新读取，verifier 核查结果。原等待器只在持久来源、完整身份和真实复验都满足时继续原命令。

设两个机器人均在任务 T 中执行相同工具，只有 taskId/topic 的事件会把 A 的恢复用在 B 上。增加 robot、revision、step、command 仍需检查原因链；只声明这些字段而不在消费者验证，不能防止串线。协议设计最终必须落到发布口、落盘和消费条件。

## 6.6 有界通讯的容量与生命周期

有界队列容量 K 限制内存。教学分析设平均到达速率 λ、处理速率 μ：长期 λ≥μ 时增大 K 只能推迟积压/丢弃；突发与耗时分布还会影响短时等待。这不是具体系统的性能测量。

可靠消息设计应说明：超额时丢弃、等待还是拒绝；是否有计数；消费者从哪份持久来源恢复；哪些事件影响执行。当前实时总线允许慢订阅者丢消息，自动恢复放行转而核查任务持久链。

Agent 生命周期同样是协议：启动时登记身份/版本/工具和权限；运行中处理取消/期限和健康；退出时释放订阅并留下未决工作。显示 enabled 不足以证明实际发布口和 executor 接通，需要组合根日志和整链测试。

扩展多角色时优先明确各自输入和可写内容，再决定是否调用模型。新增诊断角色可共享完整来源但用不同视图；它不能持有任务终态修改权，也不能靠发“已恢复”绕过原等待器。
