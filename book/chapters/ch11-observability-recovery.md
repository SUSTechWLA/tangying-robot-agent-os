# 第 11 章 可观测性、故障诊断与受控恢复

**学习目标**：形成从异常到原命令的证据链；区分只读恢复与物理处置；设计诊断闭环。

**先修知识**：第3、6、8、9章。

**关键术语**：派发状态、根因假设、独立复验、恢复预算、对账

## 11.1 可观测性服务于决策

日志、指标和事件用于回答：发生了什么、在哪里、是否已派发、影响哪条命令、依据什么继续。一个健康图标不能说明发布通道已接通，也不能说明当前设备ready。

| 材料 | 主要用途 |
| --- | --- |
| 任务/版本/事件 | 冻结定义、因果顺序与批准范围 |
| Runtime journal | 实际命令生命周期与终态 |
| 观测/制品 | 当前后置条件和来源 |
| 模型请求/拒绝trace | 当时所见信息和选择理由 |
| 服务/队列指标 | 识别慢消费者、超时与未收尾工作 |

材料需有共同身份，不能仅凭相似错误文本拼接。

## 11.2 故障分类与派发状态

准备失败、明确执行失败和结果未知是不同状态。策略准备尚未派发可以按准备问题处理；动作可能已生效则必须保留Unknown。

根因假设要引用证据和缺失信息。规则置信度或模型解释不是测量；诊断成功不能代替业务目标后置条件。

## 11.3 有界只读恢复

```text
持久恢复请求 + 原只读失败
 → Ops异常/假设
 → Recovery目录计划
 → executor白名单读取
 → verifier独立重读
 → 原等待器核对完整binding与预算
 → 同command一次重读，原计划继续
```

要求同task/revision/robot/step/command、正确source/anomaly/plan和因果顺序。旧版本、错工具、手动执行、未复验、超时或ESCALATE不能放行。先持久化恢复请求，等待器只接受对应之后的匹配链。

原只读故障和调查读取都不会制造物理重放权。bounded_write按审批与目录规则处理，never_automatic禁止自动执行，unknown不因更换错误分类而解除。

## 11.4 长历史下的调查

先读取有界摘要定位，再回查完整来源。大详情归档，热guard保留unknown/冲突/硬约束。context_read是历史工具，不是对机器人的独立复验。

调查有期限、轮数和持久预算；若长期故障或必保留状态超预算，结束自动循环并保留可定位资料，而非无限重试。

## 11.5 事故处理流程

识别影响范围→取得task/revision/robot/step/command→保存原证据→确定派发与物理未知→选择合法调查→独立复验/对账→记录允许下一步与批准→复查根因和回归。

未知持物、位置或停止不能用删除任务、重置世界或把ready强置true解决。若人工介入，记录操作者、条件、新命令与证据，不称自动恢复。

## 11.6 已验证案例与未覆盖范围

19分钟任务的一次navigation.status只读UNAVAILABLE经过完整链后原命令重读并完成原任务。暂停由操作员发起，抓放失败修复需要后续新运行验证；这些事实不构成自主物理维修或无限故障恢复。

## 11.7 诊断状态的演进与可解释界面

诊断可以按“发现异常→形成假设→提出计划→获得权限→执行调查→独立复验→记录结果”推进。每一步保存状态，避免把最后没有再告警称为已修复。

| 对外状态 | 需要表达 |
| --- | --- |
| 未检出/正常 | 已观察范围和来源健康；失明不能显示 HEALTHY |
| 已发现 | 原故障、影响任务/设备和派发阶段 |
| 待调查/待审批 | 合法读取或物理处置的提案与缺失条件 |
| 处理中 | 实际执行身份和预算，而非只有模型建议 |
| 复验通过/失败 | 独立读取/观测及原绑定 |
| 需对账/升级处理 | 未知边界、禁止动作与负责人 |

界面应让操作者从概览进入具体 task/step/command/制品，而不是只给“系统异常”横幅。只读观察者没有设备执行端口；实际执行回执还需 ran 与 verified 的区别。

对长期问题设置去重/冷却时，应按失败身份而不是只按工具名：A 的一次恢复不能压制 B 的另一次故障。告警解除也保留原记录，使故障和修复均可回溯。
