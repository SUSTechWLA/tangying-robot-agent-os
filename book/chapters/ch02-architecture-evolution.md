# 第 2 章 系统架构、职责与权威数据

**学习目标**：画出系统全貌；定位每类事实的所有者；理解架构演进如何改变边界。

**先修知识**：第1章；服务、接口与数据库的基本概念。

**关键术语**：权威状态、控制面、执行面、证据面、组合根

## 2.1 架构首先是一组责任

架构图需要同时表达调用关系、数据所有权和失效范围。只画“LLM→机器人”会隐藏批准、日志、资源和验证，也使异常无法定位。

| 对象 | 主要责任 | 权威内容 |
| --- | --- | --- |
| Task/Revision | 创建、批准、改版、状态 | 活动执行定义与不可变历史 |
| Planner/Harness | 模型循环、目录与参数约束 | 决策输入/候选/拒绝记录 |
| Coordinator | 认领、顺序、资源与收尾 | claim、owner/fence、意图状态 |
| Edge Worker | 本机物料化、执行与完成上报 | 本机checkpoint和回执 |
| Robot Runtime | 命令准入、设备调用、观测/停止 | 命令journal、实际设备身份 |
| World/Verifier | 来源投影与后置条件 | 带采集身份的事实和判定 |

权威并不表示绝对真理。例如World是观测投影，受来源质量与时效约束；Runtime回执也不是业务完成本身。

## 2.2 两种部署与同一边界

```text
Local：浏览器 → Local Agent + SQLite → Robot Runtime → Backend
                         └─ Task/Ops/Recovery

Fleet：浏览器 → Fleet API → Task/Coordinator/EventLog/Outbox
                                     │ 世界与资源
                           每机器人 Edge Worker + 执行库
                                     │
                                Robot Runtime → Backend
```

Local管理一台机器人；Fleet管理机群。两者共用能力与Runtime语义，不自动提供双主切换。同一Runtime切换控制端前应停止旧派发、闭合命令与持物状态，再建立新身份和资源权限。

原始SDK/ROS类型不进入任务层。底层差异由Backend转换，任务层关心“导航/抓取/验证”及其效果，而不是特定机器人有多少关节。

## 2.3 控制面、执行面与证据面

控制面保存意图、批准和资源；执行面接受具体命令并产生效果；证据面把实际采集与执行身份关联。三者共享标识符，但不同消息不能跨面冒充权限。

故障通常暴露在这些边界：中心批准内容与边缘快照不一致、工具回执与物理证据不一致、实时消息已收到但持久记录未写入。架构需要为每一处定义拒绝、等待或对账行为。

## 2.4 层间依赖与组合根

概念契约放在core；业务服务依赖语义接口；设备与存储适配器实现接口；cmd组合根决定实际装配。读源码时先看组合根再看接口，避免把“定义了Agent接口”误认为“生产已启用Agent”。

本项目的实际入口是[Local组合根](../../cmd/local-agent/main.go)与[Fleet组合根](../../cmd/fleet-control-plane/main.go)。模型路由、目录、数据库及角色权限在装配时选择。

## 2.5 用演进事件检验架构

从固定句式任务到能力目标，关键变化是目录、冻结计划和验证契约，不是提示词变长。增加Ops/Recovery后，需要发布权限和完整因果绑定；长历史增长后，需要无损归档和预算；加入机群后，需要claim、检查点和完成回执。

每次扩展都应回答：新增了哪个权威对象？旧消费者是否兼容？哪种中断会留下未知结果？有哪些跨存储窗口尚未闭合？旧统计和源码片段已保留在版本档案，正文按当前边界解释。

### 案例推演：一个任务的写路径与读路径

以“厨房放杯后返回”为例，任务服务保存完整目标与批准版本；Planner 读取目录和语义状态生成候选；执行器从批准定义生成 command；Runtime 保存准入/派发/回执；验证器关联动作后证据；任务服务据此推进。控制台通过查询与事件展示这些对象，不拥有第二份完成状态。

若控制台断线，执行是否继续由任务/设备合同决定；若 Planner 故障，已批准阶段与新提案要分别处理；若 Runtime 响应丢失，设备效果必须对账。单一“服务不可用”标签不能解释所有分支。

## 2.6 把架构图变成可以评审的接口

每条层间箭头至少有五项：请求/事实类型、身份、权限、持久责任和失效处理。将箭头写成表，比只列组件名更容易发现重复权威。

| 接口方向 | 语义 | 需要复核 |
| --- | --- | --- |
| 用户→任务服务 | 目标、草案、批准或取消 | 操作者与版本；取消不等于实体停止 |
| Planner→任务服务 | 候选计划和拒绝 trace | 完整目标覆盖；候选无执行权 |
| 协调器→边缘 | 唤醒、claim/Basis | 当前权威与设备/资源绑定 |
| 执行器→Runtime | 具体命令 | command、期限、目录、安全与资源 |
| Runtime/观测→验证 | 回执与采集来源 | 作用域、基线、frame、后置条件 |
| 事实→控制台/Agent | 查询与事件投影 | 投影不成为独立终态来源 |

例如“数据库故障”不必一律变成整机崩溃：新物理执行若需要先落盘，应拒绝开始；已有实体动作的停止仍需本机路径；回放查询可以显示不可取。组件恢复时核对原身份和未知状态，而不是生成一套新 ID 后继续。

阅读者可以先构造一个不使用模型的固定任务路径，验证职责与记录；再加入规划模型；最后扩展 Fleet。这样能够区分决策质量问题和执行基础设施问题。
