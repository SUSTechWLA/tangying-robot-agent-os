>
> 1. **讲清楚现在的形状**：这套系统由哪几层组成，每层放什么、谁绝对不能调谁。

### 一条关于数字的纪律

我实测这些数字时发现：**README 里的测试数字既不等于 HEAD，也不等于工作区。**

| 口径 | README | HEAD 实测 | 工作区实测 |
| --- | --- | --- | --- |
| Go 测试函数 | 1,079 | **1,040** | 1,183 |
| Python 测试函数 | 1,656 | **1,370** | 1,735 |

差异来自两处：**统计口径**（是否算 `Benchmark`、是否排除 `artifacts/` 下的代码快照）和**工作区是否有未提交的新测试**。

**教学要点**：在任何技术写作里，凡是引用一个"数量"的地方，都应该同时给出**测量它的命令**。否则那个数字在下一个提交后就开始腐烂——而读者会把"数不出来"归因于自己理解错了。

### 分层图

│     · 只呈现可信状态；断线/未知/急停/视觉降级必须可见            │
└───────────────────────────┬─────────────────────────────────┘
                            │ HTTP / WS
┌───────────────────────────▼─────────────────────────────────┐

═══════════════ 横切：共享内核（两条形态都用） ═══════════════
  agent/          意图：自然语言 → Intent

### 每层的职责与**依赖方向禁令**

| 层 | 代码目录 | 职责 | **绝对不能做的事** |
| --- | --- | --- | --- |
| **L7 前端** | `web/`、`console/` | 呈现可信状态 | 隐藏开发按钮**不是**服务端权限控制 |
| **L6 控制面** | `fleet/`、`cmd/fleet-control-plane` | 单写协调、多机派单、审计 | **不直接控制硬件** |
| **L5 边缘** | `edge/`、`cmd/edge-worker`、`cmd/local-agent`、`internal/` | 命令语义边界、计划重造、恢复 | 不信任云端给的安全字段 |
| **L4 网关** | `robot/gateway`（Python） | 安全监督、审批、急停、journal | 不实现限幅以外的业务逻辑 |
| **L3 本体** | `robot/ros2_ws/`、`sim/` | 硬件与仿真适配 | 不感知 agent 的存在 |
| **内核** | `core/`、`agent/`、`orchestration/`、`tasks/`、`middleware/` | 契约、语义、领域模型 | **不导入 SQL / Redis / gRPC / protobuf / 厂商 SDK** |

### 最后一行是硬约束，而且有机械检查

`docs/development/principles.md:12` 的原则 4：

> **核心依赖接口，适配器依赖 SDK。** 业务领域不导入 SQL、Redis、gRPC、protobuf 或机器人 SDK；在 `cmd/` / `internal/` 装配实现。`tests/architecture` 检查核心依赖方向。

**"在 `cmd/` / `internal/` 装配实现"** —— 这是一条被广泛使用但很少被写成硬规则的架构原则：**核心包只定义接口，具体实现由最外层的组合根注入。**

它的好处是可以验证的：`tests/architecture/dependencies_test.go` 是一个**会失败的测试**，不是一个约定。

（⚠️ 但这个测试的覆盖有缺口：它的被测包集合**不含 `./cmd/...` 与 `./internal/localapp/...`**，禁列表也不含 `fleet` / `cloudclient`。这就是第 9 章那个"0 处 vs 227 处"的成因。）

### 八条必须保持的原则

`docs/development/principles.md:5-18` 列了八条。我逐条标注它在哪一章展开：

| # | 原则 | 展开于 |
| --- | --- | --- |
| 1 | **模型只提出意图或候选动作。** LLM 不生成审批、期限、lease、幂等键、fencing 或 safety profile | 第 5 章 |
| 2 | **任务成功需要环境证据。** 陈旧、冲突或缺失时等待或失败关闭 | 第 3 章 |
| 3 | **同一 Runtime 契约贯穿仿真与实机** | 第 10 章 |
| 4 | **核心依赖接口，适配器依赖 SDK** | 本章 |
| 5 | **重试以物理结果为边界。** 队列可以至少一次交付，物理动作不能重复 | 第 5、10 章 |
| 6 | **版本与身份不能倒退。** 不通过重置数字或编辑历史解决冲突 | 第 8 章 |
| 7 | **界面只呈现可信状态** | 第 11 章 |
| 8 | **证据与结论绑定版本和环境** | 全书 |

**第 5 条有一个非常精确的表述值得单独抄下来：**

> **队列可以至少一次交付，物理动作不能重复。**

这十四个字概括了整个分布式设计的核心取舍。**消息系统的"至少一次"是特性；物理动作的"至少一次"是事故。**

### 两条部署形态：共享什么，独有什么

| | Cloud Fleet | Local Brain |
| --- | --- | --- |
| **Web Console** | ✅ | ✅ |
| `agent/`、`orchestration/`、`tasks/` | ✅ | ✅ |
| **`core/` 全部** | ✅ | ✅ |
| `edge/runtime`、`edge/robotclient` | ✅ | ✅ |
| `edge/agent`（执行与闭环） | ✅ | ✅ |
| `edge/worker`（**仅当作遥测映射器**） | ✅ 完整 | ✅ 部分（`Cloud`/`Source`/`Link` 全空） |
| **`fleet/coordinator`、`fleet/lease`、`fleet/redis`** | ✅ | ❌ **无调用** |
| **`fleet/worldhub`** | ✅ `NewPersistent` | ✅ **`New`**（内存） |
| **`fleet/eventlog` 的消费** | ✅ Outbox ticker | ❌ 建表不用 |
| `middleware/sqlite` | ❌ | ✅ |
| `fleet/mysql`、`fleet/redis` | ✅ | ❌ |

**这张表的结论**（第 9 章会展开）：

> **编译期共享，运行期可分。**

而它带来的一个陷阱是：**目录名不等于部署归属**。`fleet/` 里的东西不都是云端专属。用目录表达部署边界，随着代码复用会逐渐失真。

### 一个可执行的验证

原则 4 说"核心不导入具体实现"。**这句话可以被验证**，方法就是看依赖图：

```bash
# 核心包不应该导入这些
go list -deps ./core/... ./agent/... ./orchestration/... ./tasks/... \
  | grep -E 'database/sql|redis|grpc|protobuf|mysql' 
```

**教学要点**：一个好的架构原则，应该能变成一个**会失败的测试**。"我们遵守分层"是一个声明；`tests/architecture/dependencies_test.go` 是一个机制。

## 2.3 五个真实的岔路口

以下五处都是**真实的岔路口**：当时的文档里留下了被否决方案与理由，且今天仍能验证后果。

**这一节是本章最重要的部分。** 一个架构图告诉你"是什么"，一个岔路口告诉你"为什么不是别的样子"。

### 转折点一：不做「先单机再重构」，第一天就写分布式

**如果是另一条路**：会有一次"单机 → 分布式"的大爆炸式重写，`edge/runtime` 的语义命令边界、`world.snapshot.v1`、fencing token 都会是补丁。

**原始证据**：看阶段 A（08-17 那一天）的提交序列：

```
ed20bd310 chore: initialize robot agent repository
e0c801c66 feat: define robot and control plane protocols
0bae97a8d feat: add cloud task control plane
225463914 feat: add raspberry pi robot gateway and safety supervisor
b872c686f feat: add fail-closed xlerobot adapter
f885b141e release: complete robot agent v0.1 simulation baseline
```

**云控制面、Local Agent、机器人网关三个角色在同一天内一起出现**，没有任何"先写单机版再拆"的中间态。

两个细节值得注意：

| 提交 | 细节 |
| --- | --- |
| `225463914` | 安全监督从一开始就在**独立进程**里，不在 Agent 进程里 |
| `b872c686f` | 命名里第一个出现的形容词是 **fail-closed** |

而那份设计文档 `2026-08-17-role-based-installation-design.md` 的价值不在安装脚本，在于它**先把非目标写死了**：

> 「There is no STM32 installer.」
>
> 「It cannot safely automate mechanical assembly, servo ID assignment, 12 V wiring, calibration, physical emergency-stop installation, or the first motion test.」

以及：

> 「it is not a claim of unattended hardware commissioning」

**"这个项目从第一天起就把『软件发布』和『实机放行』当作两项独立结论。"** 之后每一版发布记录都重复这一条。

**取舍代价**：这个选择直接导致了 08-18 的两次重构（一天 17 提交）。作者接受了这个代价。

**31 天后的事后总结**（`docs/architecture/why-distributed.md` §1）：

> 分层是物理强加的，不是架构偏好。

但同一文档 1.3 也承认反面成立：

> 一台机器人 + 一个人看着 + 非安全关键 → 三层是过度设计。

**教学要点**：这是一个"**先立起完整形状，再收紧边界**"的路线。它的代价是立刻要还技术债；它的收益是**没有一次"把单机代码改成分布式"的大爆炸**。

### 转折点二：一次完整的方向往返

这是本章最值得单独讲的一个转折点，因为它**不是一次决策，是三次**。

```
08-18  local-first      ──┐
                          │  「删掉云控制面」
                          ▼
08-20  cloud-first      ──┐  「云端重新定为重点部署」
                          │
                          ▼
09-06  local 主线 +     ──┐  「单机器人 V1 主线接管，
       fleet 扩展路线      │    fleet 保留为扩展路线」
                          ▼
今天   README §二 两者并列，明确标注主次
```

**第一次（08-18，local-first）**

设计文档 `2026-08-18-local-first-runtime-design.md` §3 Non-Goals 明确写：

> Multi-tenant cloud accounts, hosted task history, remote fleet management, and public API exposure are not part of the first local-first release.

§11 给出删除清单：`cmd/cloud-control-plane`、PostgreSQL schema、Compose、`edge/cloudclient`、claim/lease 循环。

实际提交 `0cbfdc562 refactor: simplify deployment to local first` 一次性移除了这些。

**理由是一句产品判断**：

> a user can install on one laptop, configure with an OpenAI-compatible LLM API, pair with one Raspberry Pi robot, and operate without a hosted control plane or deployment middleware.

**值得注意的一点**：文档 §11 甚至规定了**哪些代码要被复用而不是丢弃**：

> The current uncommitted v1 work is treated as source material, not discarded wholesale.

**这是一次有考古自觉的重构**——作者明确知道自己删的是什么，以及哪些要留着。

**第二次（08-20，cloud-first）**

`2026-08-20-distributed-agentos-world-harness-design.md` 2.2 明确批评现状：

> 文档同时保留「本地优先、云端退出默认产品」和「Fleet 云端」两套产品叙述。

并把**云端重新定为重点部署**。

**第三次（09-06 起，local 主线 + fleet 扩展）**

提交 `c1cf62ccd`（09-06 22:32）是方向切换的那一笔。今天的 README §二 用一张表把两者并列，明确标注：

```
云端 Fleet（扩展路线）        本地 Local Brain（当前主线）
```

并给出边界声明：

> 不等于「单机开发栈已经具备跨地域生产级高可用」。

**取舍代价**：`docs/architecture/distributed-agentos.md` 开头就写着：

> 这是部署替换边界，**不是已经实现的云端/本地自动故障切换**。

**教学要点**：**方向的往返不是失败，是信息积累。** 第一次选择 local-first 时，作者不知道多机协调的真实代价；第二次选择 cloud-first 时，作者写出了 21.5 KB 的世界模型设计；第三次回到 local 主线时，作者已经有了完整的 Fleet 实现和一份诚实的"未验证清单"。

**三次选择留下的东西一件都没丢**：Fleet 代码还在、还有测试、还是"已实现的扩展路线"。**这正是"不重写历史"的仓库治理规则的收益。**

### 转折点三：工具层要标准化，而且不新增执行通道

**如果是另一条路**：为 LLM 直接暴露关节角与底盘坐标（最省事），或者新建一条"LLM 专用"执行总线（最"干净"）。

**原始论证**：`2026-09-11-standard-robot-tool-layer-adr.md` 是一份**先审计、后决策**的 ADR。它的背景章节先给出"审计到的既有事实"表（8 行），结论一句话：

> **不存在需要「另起炉灶」的缺口。**

然后：

| ADR | 决定 | 理由 |
| --- | --- | --- |
| **ADR-1** | 领域工具**编译成既有的 `ExecuteSkill`** | 「新开一条总线会立刻产生**两份租约、两份幂等和两份安全判定**」 |
| **ADR-2** | **能力集（LLM 可见）与动作集（适配器可见）分离**，翻译发生在 **gateway 层**而不是适配器层 | 「若把翻译放进适配器，每个型号适配器都要**重做一遍语义解析并各自犯错**；放在 gateway 侧可以单点测试、单点限制」 |
| **ADR-5** | **明确不宣称已对接 MoveIt 2 / Gazebo** | 可验证性：「仓库的 ROS 2 镜像只安装 `navigation2` 与 `ros-gz`，**没有 MoveIt 2**」 |

ADR-5 里有一句判据值得抄下来：

> **声称 MoveIt 2 可用却无法运行，会让整套工具层的可信度归零。**

**ADR-1 的理由是本章最有价值的一条工程论证**：

> 新开一条总线会立刻产生**两份**租约、**两份**幂等和**两份**安全判定。

**"两份"意味着两份会漂移。** 任何"为了干净而新建一条平行通道"的设计，都要回答一个问题：**这两条通道的一致性由谁保证？** 如果答案是"约定"，那它迟早不一致。

**取舍代价**：`move_arm_to_joints` 与 `navigate_to_pose` 被标为 `llm_visibility: "fallback"`，默认不提供给模型。

### 转折点四：把「会改变世界」变成契约字段

**如果是另一条路**：继续用"适配器自己声明验证步骤序列"的约定（参考场景能工作，异构型号不能）。

**原始论证**：`2026-09-10-closed-loop-semantic-upgrade-adr.md` 先列 7 项已有能力（保留，不替换），再列 **5 个真实缺口**。缺口 1 就是：

> **没有「读工具 / 写工具」的机器可判定标记。** `core/skills/manifest.go` 只有 `SafetyLevel`，它表达**危险级别**而不是"**这个工具会改变物理世界**"。

ADR-1 因此引入 `MutatesWorld bool`，并**显式否决了两个替代方案**：

| 被否决的方案 | 否决理由 |
| --- | --- |
| 用 `SafetyLevel` 新档位代替 | 会让**两个正交概念绑在一起**。反例：`emergency_stop` 是物理动作但**不需要场景证据** |
| 每个 adapter 自己声明步骤序列 | 异构型号无法保证 |

**第一个反例就是第 5 章讲的那个漂亮设计**：`emergency_stop` 的 `mutates_world=false` 而 `safety_level=4`。**ADR 里明确把它当成"两个概念不能合并"的证据。**

ADR-2 规定了失败关闭的方向：证据缺失 → 步骤保持 `STARTED` + 可恢复失败 + **不使用成功文案**。理由那句话是全书的核心命题之一：

> **证据缺失意味着「我们不知道世界是什么样」，验证失败意味着「世界看起来不对」——这是两类不同错误。**

**教学要点**：这是第 3 章那套设计在 ADR 层面的表述。**"不知道"和"不对"是两个答案**——这句话在 ADR、在世界模型的三值逻辑、在失败分类的兜底方向里，出现了三次。

### 转折点五：判卷的人不能是考生

这条原则在项目里反复出现：

> **不让 EvalAgent 或任何 Agent 拥有移动判据的能力。判卷的人不能改判据。**

落地为 `train/` 目录的定位（`docs/operations/deployment.md` 源码目录归属表）：

> 「`train/`｜离线｜训练**门禁**：`Compare`/`Gate`…**它不在任何部署目标里运行，也刻意不提供训练循环——判卷的人不能同时是考生。**」

**三条具体的落地**：

| 落地 | 内容 |
| --- | --- |
| `train/` 不在任何部署目标里运行 | 它是离线门禁 |
| **不提供训练循环** | 刻意——判卷的人不能同时是考生 |
| 训练只能读闭环门禁的结论，不能改它 | 「反过来就是本仓库一直在防的那种**自证**」 |

**这条原则的普适性很强**：它适用于任何"系统评价自己"的场景。**一个能修改自己评分标准的系统，它的分数没有意义。**

## 2.4 九个真实的缺陷修复

**这一节是本章对教学最有价值的部分。**

每个缺陷都按四段讲：**现象 → 根因 → 修法 → 留下的防线**。而最后一段最重要——**一个缺陷如果没有留下防线，它一定会复发。**

### 修复 1：两个「永远不可能成立」的检查

**现象**：在一台**已经测绘过房间**的机器人上，grounding 永远看到 **0 个物体**。每个任务都在 grounding 处失败，每次失败产生一条 anomaly——**这是后来那 139 项"发现"的总根源**。

**根因（两条互不相同的"永假条件"）**：

**① 一个文档不可能包含自己的哈希。**

仿真侧 `semantic_services._recall` 要求对象层文档里的 `mapId` / `mapRevision` / `calibrationRevision` 三项都与当前地图一致。但对象层**就是地图自己的产物**：它写在 `objects.json`，其字节参与哈希，哈希就是 `mapRevision`。

**一个文档不可能包含它自己的哈希。**（第 4 章 §4.4 详细讲了这个）

**② 「语法说『要澄清』」被当成终局答案。**

```go
if errors.Is(deterministicErr, intent.ErrClarificationRequired) {
    return manipulation.Intent{}, deterministicErr   // ← 直接返回，模型永不被咨询
}
```

**为什么一直没被发现**：

> 单元测试 `_layer()` 这个 helper **自己造了一个匹配的 `mapRevision`**。
> 「**在被检查的地方它永远存在，在被生产的地方它永远不存在。测试和自己的构造一致，于是全绿。**」

**修法**：

- 身份改用文档里**确实可能存在**的字段（`mapId` + `calibrationRevision`）+「读取者是从**这张**地图的目录里拿到它的」这一事实；
- 解析器改为「确定性成功就用它，其余一律交给模型」。

**留下的防线**：新增一个使用**真实产物形状**（没有 `mapRevision`）的测试，并**验证过「把旧检查加回去它就会红」**。

**教学要点**：这是全书最重要的一条测试失效模式。

> **当测试用手工构造的 fixture 替换真实生产者时，测试验证的是"消费者能处理这个 fixture"，而不是"消费者能处理真实生产者产出的东西"。**

而这类 bug 有极强的不对称性：**它在测试里永远绿，在生产里永远坏。**

**"验证过把旧检查加回去它就会红"** —— 这一步是整段的关键。**一个从没红过的测试，不是一个测试。**

### 修复 2：控制台卡死——轮询比端点响应还快

**现象**：用户报告 problems 页面"一点进去就卡死"。

作者第一次用 Node 测了渲染路径（12 ms）就判断"没复现"——**漏查了端点延迟**。

**根因（实测数据）**：

| 端点 | 耗时 | 控制台轮询间隔 |
| --- | --- | --- |
| `/v1/agent/alerts` | **16 s**（重启后冷启动 >60 s） | **5 s** |
| `/v1/tasks` | **40 s** | 按需 |
| `/healthz` | 0.0005 s | — |

`web/app.js` 里：

```javascript
setInterval(refreshAgentAlerts, 5000)
```

**每 5 秒发一个要 16 秒才回来的请求**，在途请求越堆越多，浏览器被自己的请求队列堵死。

**深层原因**：`task_events` 已 173,551 条、库 389 MB，**告警投影与任务列表都要读事件，成本随账本线性增长**。

**修法（只修了一半，且如实说明）**：把固定定时器换成**自调度、不重叠**的轮询——下一次在当前这次**结束之后**再排，间隔取 `max(5s, 本次耗时)`。

> 「慢账本让控制台更新变慢——**这是正确的降级**：数字旧了还能用，标签页卡死不能用。」

**作者明确写下没修的那一半**：

> 「服务端仍按全量账本计算，端点依旧 16–60 秒。**根治要做的是让投影不随账本线性增长**（增量读、或缓存投影结果），**我没有做**。所以现在的状态必须说清楚：**控制台不会再被自己堵死，但首屏仍然很慢。**」

**顺带发现的运维隐患**：同一数据目录上跑两个 agent（PID 34103 占 8897、35137 占 UDP 45871）会让 API 与告警行为不可预期——此前的 `database is locked` 就是它。

**留下的防线**：改用**受管后台任务**启动，不再用 `( ... &)` 子 shell。

**教学要点**：

1. **"我没复现"不等于"没有 bug"** —— 它只等于"我测的那条路径没问题"。作者测的是**渲染路径**，而 bug 在**端点延迟**。
2. **"没修的那一半"必须写出来。** 一个只说"已修复"的报告，会让下一个人以为首屏也快了。

### 修复 3：「没执行却报已执行」的假声称

**现象**：在真实接口上点"执行这一步"，得到：

```
executed: true, verified: true, verification: "地图已启用"
```

而实际上**一次工具都没调用**。

**根因**：`Result.Executed` 原本在 `loop.Run` 返回后**无条件置为 true**。而"没有配置决策器"时循环是 `BLOCKED` 收尾，什么都没做。控制台会把它画成"已执行并复验通过"，并把按钮锁成"已执行"。

**作者自己的定性**：

> **这是本仓库最不该出现的一类错误**：它把「我们什么都没做」说成「机器人动了，而且确认动对了」。

**修法（只改一处）**：让**唯一知道答案的那一层**开口。

```go
// actionloop.Outcome 增加 Calls
// 在唯一一处真正下发调用的地方自增：
outcome.Calls++          // 紧跟 l.call(...) 之后
// 执行器改为：
result.Executed = outcome.Calls > 0
```

**并且明确否决了另一条修法**：

> 为什么不在 `recoveryexec` 里从 verdict 字符串推断"哪些 verdict 意味着真的调用过"：**那是把派发规则抄第二遍，两份必然漂移。**

**留下的防线**：`TestABoundedWriteIsNeverRunUnattended` 覆盖目录里全部 **7 个** mutating 动作，并**验证过「把风险门去掉它就会红」**。

**教学要点**：这是一个关于"**谁能回答这个问题**"的漂亮例子。

"这一步执行了吗"这个问题的答案是 `Calls > 0`，而**只有真正下发调用的那一层知道 `Calls`**。任何在别处推断它的尝试，都是**把派发规则抄第二遍**。

而这与代码里的实际计数点完全一致（`internal/actionloop/loop.go:491-494`）：

```go
roundRecord, verdict := l.call(ctx, round, tool, decision)
// Counted here, at the one place a call is dispatched. Everything above
// this line is a decision *not* to call, and counting any of it would make
// "the loop did something" true for a run that only refused.
```

**"这一行上面的一切，都是『决定不调用』。数其中任何一个，都会让『循环做了事』对一次只拒绝的运行成立。"**

### 修复 4：故障丢弃整张地图

**现象**：一次空白视野（对着近墙、深度点不足）让一段探索在 **74% 覆盖率处崩掉，整张已测绘的地图完全没保存**。

**根因**：深度点不足（<100 点）**抛异常终止整段**。

**修法**：改为**跳过该帧并计数**；连续 25 帧才优雅结束该段（`stopReason="depth_starved"`）并**发布已测绘部分**。

**留下的防线**：`depth_starved` 成为一个显式的停止原因，而不是一个异常。

**教学要点**：**"部分结果"必须能被表达。** 一个只能返回"全部成功"或"抛异常"的接口，在长时程物理任务里必然丢数据——因为**物理世界不会配合你走到一个干净的终点**。

（这个缺陷在第 10 章的覆盖率实验里还会出现：`38.9% → 81%` 的四处改动之一就是它。）

### 修复 5：一次被数据推翻的优化方向

**现象**：想知道"为什么 SLAM 只能覆盖 62%"，第一直觉是**改进探索算法**。

**数据说了什么**：

| 指标 | 值 |
| --- | --- |
| 用理想真值跑 frontier 策略 | **覆盖 99.0%**，行程 61.6 m，23 段 |
| 真实地图 | **62%** |
| 真实失败栅格上，从轨迹上的姿态**能看到**但仍未知的格子 | **6511 格 = 真实未知的 44.3%** |
| 按"射线经过即自由"填上后 | 可知率可从 **62.1% 升到 78.9%**，**零额外行程** |

**结论**：**瓶颈不在探索层，在建图层**——`occupancy_from_points` 只有落进某格的 3-D 点才会让那格变已知，**没有射线投射**。

而对照被测试挡回的三处探索层改动（视点按可见性排序、簇上限 12→32、gain 语义改动）**净收益为 0** 或触发"房间测完还在跑"。

**报告结论**：

> **现阶段不要动探索算法**；探索层头部空间不到 1 个百分点；**最大单项收益在建图层 +16.8 pp。**

**方法论上的诚实记录同样值得教学**：`density=0.3` 得到 1.6%、`density=0.15` 得到 0.9%，作者判定：

> **这不是发现，是我的建模错误。**

（单帧伯努利模型让初始地图碎到 `min_frontier_cells=8` 以下，`explore_target` 第一次就返回 `None`，机器人一步没走。）

**教学要点**：**"先量化瓶颈在哪一层，再优化"** 这一条说起来容易，做起来需要两件事：**一个能分别测量各层的方法**，和**接受自己直觉错了的意愿**。

作者的定性是"**一次被数据推翻的优化方向**"——**这个标题本身就是一个好的科研态度。**

### 修复 6：硬件故障丢弃整张地图

**现象**：某类硬件故障发生时，**已测绘的地图被整体丢弃**。

**修法**：故障发布成**观测**，能力被摘掉；地图不受影响。

**留下的防线**：`docs/development/2026-09-16-faults-as-observations.md` 记录了完整链路，包括实测暴露的两个真问题（`occurrences` 单位错误、三项能力"不可用但没说原因"）。

**教学要点**：**"故障"和"数据"是两个不同的东西。** 一个硬件故障不应该让已经获得的观测失效——那些观测**仍然是有效的历史事实**，只是产生它们的能力现在不可用了。

这个区分在系统里有明确体现：世界模型里 `SourceState.Anomalies` 与 `EntityState` 是分开的（第 4 章）。

### 修复 7：解析失败静默降级

**现象**：一个已经**为模型付了钱**的部署，仍然对"把红色杯子放到桌上"回答：

> 请明确交接区、目标区或收纳盒

而模型对这句话**毫不犹豫地就能解对**。

**根因**：

> 「**语法表达不了**」和「**这句话本身有歧义**」曾被当成同一个答案。

**修法**（`agent/agent.go:84-91`）：只有 `errors.Is(deterministicErr, intent.ErrClarificationRequired)` 时才把模型错误**追加**在原错误之后；否则**原样返回 `deterministicErr`**。

注释解释了这个设计为什么必须这样写：

> 澄清文本保留在错误头部，因为那是**操作员能据以行动的部分**（"说清楚是哪个房间"）。
> **模型的失败是被追加而不是被替换**：一个模型够不到的部署，**不能看起来像一个语法很窄的部署**。

**留下的防线**：另一个"永远不可能成立的检查"。

**教学要点**：**"语法太窄"和"这句话有歧义"是两个不同的诊断。** 把它们合并成一个错误，就等于把一个可修的问题（配模型）伪装成一个不可修的问题（重新表述）。

**这与修复 4 的教训是同一条**：**两种不同的失败，必须能被区分地表达。**

### 修复 8：「模型不得执行批准时没出现过的物理动作」

**这条不是缺陷修复，是一道**新加的门**——但它值得放在这一节，因为它补的是一个真实的洞**。

**问题**：操作员批准了一个恢复计划。计划里写了"重新观测 + 重做 `pick` 步骤"。然后模型能不能在执行过程中**顺手**做一个计划里没写的 `place`？

**修法**：`internal/actionloop.Scope`（第 5 章 §5.9 详述）。

**留下的防线**：`Scope` 为 nil 时**拒绝一切物理调用**；且检查顺序在批准**之前**。

**教学要点**：**"批准"的粒度是一个必须显式回答的设计问题。**

| 语义 | 风险 |
| --- | --- |
| 批准一个**意图** | 模型可以在意图范围内做任何事 |
| 批准一个**动作集合** | 模型只能做这些 |

**这个系统选了后者。** 代价是恢复计划必须在批准前完整生成；收益是批准之后的任何偏差都会被拒绝。

### 修复 9：监督者的沉默被读成健康

**现象**：测试输出原文：

```
blind spot confirmed: 1 unconfirmed step(s) on disk, none reported
```

进程重启后，磁盘上躺着"可能已经动了但没人知道"的物理步骤，而监督 agent **报告一个干净、安静的机器人**。

**原话**：

> **这是监督者最糟的失效模式：沉默被读成健康。**

**根因**：`OpsAgent` **只订阅未来事件**，进程重启后崩溃前的失败完全看不见。

**修法三层**：

| 层 | 内容 |
| --- | --- |
| 1 | `agentcontract.TaskHistory`（新 port） |
| 2 | `OpsAgent.History` + `learnExistingTasks` **启动扫描** |
| 3 | `Finding.TaskID` |

**第三层是第一版漏掉的**，现象是"**诊断出来了但账本里没有**"，根因是 `taskID=""`。

**留下的防线**：7 条正向契约测试把"启动时必须扫描持久记录"钉死。

**教学要点**：**"我没收到消息"和"没有坏消息"是两件事。**

一个只订阅未来事件的观察者，在**它自己启动之前**发生的事情上一无所知。而这个盲区的危险在于：**它表现得像一个健康的系统。**

（第 11 章会展开：这类"沉默被读成健康"的失效，在监控系统里有一个专门的名字，而在机器人系统里它的后果是"一台可能握着杯子的机器人被报成空闲"。）

### 九个缺陷的共同结构

把它们放在一起看，会发现一个反复出现的模式：

| 修复 | 核心教训 |
| --- | --- |
| 1 | **测试用手工 fixture 替换真实生产者 → 永久绿** |
| 2 | **"我没复现" ≠ "没有 bug"；没修的那一半必须写出来** |
| 3 | **只有真正做那件事的那一层能回答"这件事做了吗"** |
| 4 | **"部分结果"必须能被表达** |
| 5 | **先量化瓶颈在哪一层，再优化** |
| 6 | **"故障"和"数据"是两个东西** |
| 7 | **两种不同的失败必须能被区分地表达** |
| 8 | **"批准"的粒度必须显式回答** |
| 9 | **"我没收到消息" ≠ "没有坏消息"** |

**六和七是同一条**（区分不同的东西），**四和九是同一条**（沉默与部分状态必须能被表达）。

**而"验证过把修复撤掉就会红"出现了三次**（修复 1、3、8）。

> **一个从没红过的测试，不是一个测试。**

## 2.5 六版发布：每一版都在收紧「什么叫完成」

| 版本 | 一句话定位 | 它收紧了什么 |
| --- | --- | --- |
| **v0.2.0** | 把单机器人自然语言任务做成一条能复现的闭环 | 任务能做完 → **但"做完"取决于计划里有没有恰好排进验证步骤** |
| **v0.3.0** | 把"物理写工具的完成判定"从约定变成契约 | 把判据**下沉到工具契约**（`core/closedloop`） |
| **v0.4.0** | 把机器人能力变成 LLM 能直接 function calling 的工具 | 造工具层 → **但历史任务在界面上不可达** |
| **v0.5.0** | 把回放补成"任何时候都能完整复盘" | 修可达性 → **但只对仿真里的"能跑的任务"有效** |
| **v0.6.0** | 从"能完成任务"到"能被非专家操作" | 让非专家能操作 → **但"工具说自己成功了"仍不等于"世界变了"** |
| **v0.7.0** | **给系统装上刻度与物理接地：先能证明，再谈变强** | **物理接地验证 + 评测底座** |

**一条贯穿六版的元规律**：

> **每一版的定位句都在收紧「什么叫完成」，而不是扩大功能面。**

这也是为什么这套系统可以被写成一本"原理"书——**它有一条一致的主线，而这条主线不是功能列表。**

### v0.7.0 的定位值得单独说

`docs/releases/v0.7.0.md` 的核心变化五项：

| # | 变化 | 关键事实 |
| --- | --- | --- |
| 1 | **机器人运行链** | Gazebo RGB-D 与位姿桥接；MuJoCo 和 Gazebo 复用相同机器人/服务边界 |
| 2 | **建图与标定** | 自然语言建图请求、地图库存与选择、手语标定求解与可视化引导 |
| 3 | **物理接地验证** | GCL、独立验证器、三值 verdict、证据引用。**默认关闭**（`TANGYING_GVF_ENABLED=1` 开启） |
| 4 | **Agent 上下文** | 版本化事实包、分阶段表达实验。**默认 `legacy`** |
| 5 | **系统 Eval** | 20 项能力、7 层评测、12 类公开工具、34 个基础指标、三态研究门禁 |

**注意每一项都带着"默认关闭"或"边界说明"**：

> 「本版提供离线评测底座，**尚未统一接入所有闭环和实机 runner**。」
>
> 「本版是有明确适用边界的软件版本，**不是实机安全认证**。」
>
> 「历史实验存在规划、恢复和部分验证器判定的**未通过结果**；这些结果完整保留在报告中，**不能因为代码发布而改称能力已通过**。」

**最后一句是全书最重要的一句发布说明。**

> **不能因为代码发布而改称能力已通过。**

**教学要点**：一个版本发布说明里出现"历史实验有未通过的结果，我们保留它，不因为发布而改称通过"——这是"证据与结论绑定版本和环境"这条原则（原则 8）在发布流程里的落地。

## 2.6 仓库治理：三条可以直接抄走的规定

这个仓库有三条治理规定，值得任何做长期项目的团队参考。

### 规定一：设计文档保留历史，不追改

`2026-08-18-local-first-runtime-design.md` §10 写了一条**元规则**：

> Future middleware adapters or Robot Runtime protocol changes must update the current architecture and link to a new decision record **rather than erasing prior design history**.

**落地证据**：`2026-09-10-closed-loop-semantic-upgrade-adr.md` 的 **ADR-10 段**（后来追加）明确写：

> 上述 ADR-4 的 `Track` 重试状态机**后来已移除**；当前 `core/closedloop` 只负责完成门禁、失败分类与恢复建议。

**它没有去改 ADR-4，而是追加了一段"现状校正"。**

**收益**：读这份 ADR 的人既能知道"当时为什么这么设计"，也能知道"后来为什么改了"。

**代价**：文档里会有过期的段落（第 3 章遇到过：`lifecycle-objects.md` 仍描述已删除的 `Track` 状态机）。

**这是一个真实的取舍**，而这个项目选了"保留历史 + 追加校正"。**它换来的东西是：任何人读 ADR 都能看到设计者的完整推理过程，而不是一个被追改得看不出犹豫的结论。**

### 规定二：`docs/superpowers/` 只保留 specs

提交 `cddb5bb46 chore: ship decision records, not agent scratch and plans`（09-12）删除了 `.superpowers/` 下 **8 份 agent 会话报告**与两份无人引用的产物。

提交信息里那句话是一条可迁移的仓库治理经验：

> **plans 是过程产物，不是产品的文档。**

**落地**：`docs/superpowers/` 只保留 `specs/`（决策记录）。

**教学要点**：一个仓库里放什么，比它不放什么更容易失控。**"过程产物"（计划、会话记录、临时报告）每一条单独看都有价值，合起来会把"什么是权威文档"这个问题淹掉。**

### 规定三：不能靠数字夸大覆盖率

`docs/production/v1-assessment-2026-09-05.md:89`：

> **专项结果是同一批代码的补充证据，不应与整套测试数量相加来夸大覆盖率。**

**这条规定防的是一种常见的自我欺骗**：跑了一个专项测试，报告"又通过了 200 个断言"，然后把它加到总数里。

**问题是它们测的是同一批代码。** 相加得到的数字看起来更大，但**没有增加任何新的保证**。

**教学要点**：**测试数量的意义在于覆盖了多少不同的假设，不在于跑了多少次。** 一个规定了这一点的仓库，它的测试数字是可以相信的。

### 五道练习题

**题 1（为什么不能新建执行通道）**

> ADR-1 拒绝为 LLM 新建一条执行总线，理由是新开一条会"立刻产生两份租约、两份幂等和两份安全判定"。
> 请展开这个论证：为什么"两份"比"一份复杂的"更糟？并给出一个你见过的同类例子。

<details>
<summary>答案要点</summary>

**为什么两份更糟**：

1. **两份会漂移。** 一份复杂的至少是自洽的；两份需要"保持同步"，而同步是一个持续的成本，且**失败是静默的**。
2. **认证与审计会分裂。** "这个命令经过安全检查了吗"会有两个答案，取决于走哪条总线。
3. **修 bug 要修两遍。** 而且第二遍很容易漏——因为开发者不知道有第二条路径。

**同类例子**（学生可能给出的）：

- 两个缓存层（内存 + Redis）没有统一的失效策略
- 前后端各自实现一份权限校验
- 有两套"是否已读"的标记（数据库字段 + 前端本地状态）
- 双写数据库（主库 + 搜索索引）没有事务保证

**加分点**：指出**正确的做法通常是"让新的东西编译成既有的东西"**（ADR-1 就是这么做的：领域工具编译成 `ExecuteSkill`），而不是"新建一条干净的"。

**关键判据**：如果你要新建一条通道，你必须回答"**这两条通道的一致性由谁保证**"。答案如果是"约定"，它迟早不一致。

</details>

**题 2（测试为什么会永远绿）**

> 修复 1 的根因之一是一个"永远不可能成立"的检查：`objects.json` 被要求包含自己的 `mapRevision`，而它是 manifest 哈希的一部分。
> 请解释：**为什么单元测试没有发现这个 bug？** 并给出一种能让这类 bug 暴露的测试设计方法。

<details>
<summary>答案要点</summary>

**为什么没发现**：单元测试的 helper `_layer()` **自己造了一个匹配的 `mapRevision`**。

于是：

> **在被检查的地方它永远存在，在被生产的地方它永远不存在。测试和自己的构造一致，于是全绿。**

**通用失效模式**：

> 当测试用手工构造的 fixture 替换真实生产者时，测试验证的是"消费者能处理这个 fixture"，而不是"消费者能处理真实生产者产出的东西"。

**这类 bug 的对称性**：**在测试里永远绿，在生产里永远坏。**

**能暴露它的测试设计方法**：

1. **契约测试跑真实生产者**：每次发布地图后，用**真实产物**重新加载一次，而不是用手工 fixture。
2. **产物形状断言**：测试断言"产出的对象层**没有** `mapRevision` 字段"——**把"不可能有"写成断言**。
3. **撤销验证**（这个项目用的）：把旧检查加回去，**断言测试会红**。

**加分点**：指出修复 1 的防线就是方法 3，而且项目里这个方法用了三次（修复 1、3、8）。

**一个从没红过的测试，不是一个测试。**

</details>

**题 3（谁能回答"执行了吗"）**

> 修复 3 里，`Result.Executed` 曾经无条件为 true。作者修的方式是"让唯一知道答案的那一层开口"（在 `l.call(...)` 之后 `outcome.Calls++`），并明确否决了"从 verdict 字符串推断"的做法。
> 请说明为什么"从 verdict 推断"是错的，并给出判断"某个信息应该从哪里取"的一般原则。

<details>
<summary>答案要点</summary>

**为什么从 verdict 推断是错的**：

> **那是把派发规则抄第二遍，两份必然漂移。**

具体的：verdict 值域会变（新增 verdict 类型），派发规则会变（什么算"调用过"），而"从 verdict 推断调用"的映射表**不会自动跟着变**。

**一般原则**（几种表述，任一对即可）：

1. **让唯一知道答案的那一层回答。** 信息应该在它**被产生**的地方被记录，而不是在被**需要**的地方被推断。
2. **不要重新推导已经被记录的事实。** 如果 `Calls` 已经存在，"它是否 > 0"是读取，不是推断。
3. **任何"规则的第二份拷贝"都是技术债。** 它会在两份漂移时静默失效。

**代码里的证据**（`internal/actionloop/loop.go:491-494`）：

```go
roundRecord, verdict := l.call(ctx, round, tool, decision)
// Counted here, at the one place a call is dispatched. Everything above
// this line is a decision *not* to call, and counting any of it would make
// "the loop did something" true for a run that only refused.
```

**加分点**：指出同一个模式在项目里出现多次——`Gate` 是完成判据的唯一入口、`SafetySupervisor.evaluate` 是唯一否决点、`Classify` 是失败语义的唯一映射。**"唯一入口"是一个反复出现的设计手法。**

</details>

**题 4（部分结果）**

> 修复 4 把一个"深度点不足就抛异常"的行为改成"跳过并计数，连续 25 帧才优雅结束并发布已测绘部分"。
> 请说明为什么在**机器人系统**里"部分结果必须能被表达"比在软件系统里更重要。

<details>
<summary>答案要点</summary>

**核心区别**：**物理世界不会配合你走到一个干净的终点。**

在软件系统里，一个操作要么完成要么失败——因为你可以重试，可以回滚。

在物理世界里：

- 机器人走到了客厅的一半，电池没电了
- 扫描扫到 74%，遇到一堵近墙
- 抓取抓到一半，力传感器报警

**这些都不是"失败"，是"部分完成"。** 而部分完成的**部分是有价值的**：

| 部分结果 | 价值 |
| --- | --- |
| 74% 的地图 | **可以用于导航**——比没有地图好得多 |
| 走到客厅的一半 | 记录了已经探索的区域，下次不用重扫 |
| 抓到一半 | 决定了"结果未知"，禁止重试（第 3 章） |

**如果不能表达部分结果**，系统就被迫在"全部成功"和"抛异常"之间二选一，而**物理任务几乎从不在第一个选项上结束**。

**加分点**：指出这与修复 9（沉默被读成健康）是同一条原则的两面：

- 修复 4：**部分状态必须能被表达**（否则丢失已有成果）
- 修复 9：**"没有消息"不能被读成"好消息"**（否则盲区被当成健康）

**共同点**：**系统必须能表达"我只做到这里"和"我不知道"。**

</details>

**题 5（两个"两份"）**

> 第 11 章会讲到：`GRASP_NOT_REACHED` 在 Go 侧被显式归为 `PERCEPTION`，但 Python 的 `FAMILIES` 八族**没有任何一族包含它**，所以巡检报"未归类"。
> 请说明这与 ADR-1 拒绝的"新开一条总线"是**同一个问题**，并给出一般化的检测方法。

<details>
<summary>答案要点</summary>

**同一个问题**：**同一个概念有两份词表。**

| | 一份 | 另一份 |
| --- | --- | --- |
| ADR-1 的情形 | 既有 `ExecuteSkill` 的租约/幂等/安全 | 新建总线的版本 |
| 本情形 | Go `core/closedloop` 的分类表 | Python `diagnose_task.py` 的故障族表 |

`commit 5dfa9728e` 修过 `tool_layer.py` 的**镜像表**，但 `diagnose_task.py` 的故障族表与 `closedloop` 分类表**仍是两套独立词表**。

**一般化的检测方法**（几种）

1. **覆盖守卫（项目已用）**：`TestEveryCodeTheRuntimeCanEmitIsClassified` 断言"运行时能发出的每个码都在表里"。**但它只检查一份表**——不能发现跨语言的不一致。
2. **跨语言契约测试**：从两份词表导出名字集合，断言它们的差集为空（或显式列出允许的差集）。
3. **单一真源 + 生成**：让一份词表是权威，另一份**生成**出来（就像 `tools.json` 从代码生成那样）。

**加分点**：指出**方法 3 是这个项目自己的既有解决方案**——`tools.json` 由代码生成，`--check` 断言逐字节相同，所以"模型看到的工具"与"运行时能执行的工具"不可能不一致。**同一手法应该被用到分类表上。**

**更深一层**：这是一个**跨语言**问题。Go 和 Python 各有一份词表，而**没有任何机制保证它们一致**。这正是为什么项目里有 `tests/contract/` 这一层——跨语言契约需要独立的测试，不能指望两边的单测。

</details>

### 学生最容易误解的四个点

| # | 误解 | 纠正 |
| --- | --- | --- |
| 1 | "方向来回切换说明团队没有定力" | **往返是信息积累。** local-first → cloud-first → local 主线 + fleet 扩展，三次选择留下的东西一件都没丢 |
| 2 | "文档里有过期内容说明文档没维护" | 这个项目**刻意不追改设计文档**（元规则：link to a new decision record rather than erasing prior design history）。过期段落是**有意的代价**，换来了完整的设计推理链 |
| 3 | "测试数量多说明质量高" | 项目自己规定："**专项结果不应与整套测试数量相加来夸大覆盖率**" |
| 4 | "新开一条干净的通道是更好的架构" | **"两份"比"一份复杂的"更糟**——两份会漂移，且漂移是静默的 |

## 2.8 本章小结

1. **36 天、328 个提交、约 23 万行代码。** 这个密度说明它是迭代出来的——而迭代出来的架构，只有从演进史里才能读懂。

2. **七层 + 一条横切**，横切内核有一条硬约束：**不导入 SQL / Redis / gRPC / protobuf / 厂商 SDK**，而且这条约束**有会失败的测试**。

3. **五个岔路口**，其中第二个是**一次完整的方向往返**（local-first → cloud-first → local 主线 + fleet 扩展）。三次选择留下的东西一件都没丢。

4. **九个真实缺陷**，共同结构是几条反复出现的教训：**测试用 fixture 替换生产者会永久绿**、**只有做那件事的那一层能回答"做了吗"**、**部分状态和"不知道"必须能被表达**。

5. **六版发布，每一版都在收紧"什么叫完成"，而不是扩大功能面。** 这是这套系统能被写成一本"原理"书的原因。

6. **"不能因为代码发布而改称能力已通过。"** —— v0.7.0 发布说明里的这句话，是全书最重要的一句。
