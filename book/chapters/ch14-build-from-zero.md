# 第 14 章 开发者上手与渐进建设方法

**学习目标**：在已有基础上定位全系统；按可验证增量开发；选择正确测试和扩展入口。

**先修知识**：第2、3、5–9章；Go/Python其一和命令行。

**关键术语**：组合根、增量建设、变更合同、故障矩阵、证据产物

## 14.1 新开发者的第一张图

先阅读组合根、任务/版本、能力目录、Runtime、观测/验证、事件账本和恢复链。将一个任务的ID在这些对象之间连起来，能够解释成功与未知，再开始增加功能。

```text
组合根 → Task/Revision/批准 → Local 或 Worker → 共享Edge Host
              ↑                                  ↓ 子计划/能力执行器
         回放/诊断 ← 父/子账本 ← Runtime/观测/验证
```

代码地图在附录A；实验分级在附录F。阅读书稿无需模型key和硬件，运行软件测试、仿真和实机分别有不同条件。

## 14.2 渐进建设顺序

| 阶段 | 交付对象 | 验收问题 |
| --- | --- | --- |
| 1 | 完成契约/失败分类 | 缺证据和unknown是否保留？ |
| 2 | Runtime/Backend/观测 | 身份、限位、停止和journal是否真实？ |
| 3 | Task/Revision/审批 | 冻结范围、并发更新和回放是否成立？ |
| 4 | 目录/规划 | 参数、效果、预算、拒绝trace是否受控？ |
| 5 | Agent/恢复 | 发布权限、完整因果与复验是否接通？ |
| 6 | 长上下文 | 热guard/冷原文/作用域是否精确？ |
| 7 | 目标委托/Fleet交接 | grant与持久预算、子证明、claim、CAS、outbox和v2收尾是否可恢复？ |
| 8 | 新本体/多机/长稳 | 现场和故障范围是否有独立证据？ |

这是依赖顺序，不是固定工期。增加并行度、模型规模或机器人数量之前，应先完成一个最小物理闭环。

## 14.3 三类常见变更

新增Agent：定义订阅、权限、发布事实和生命周期，验证组合根接线，不维护第二份任务终态。

新增能力：实现输入/效果/资源/operation/verification合同，增加规划、拒绝、unknown、取消/停止和回溯测试。

新增本体：实现实际Profile/Backend、规范观测、控制/停止/验证器；接Fleet时另核对设备/目录/世界坐标与资源。新工具名字或新提示词不能替代这三类实现。

## 14.4 故障驱动的测试策略

先选择该改动可能破坏的边界：错身份、旧版本、目录改变、预算超限、丢响应、落盘失败、持物中断等。测试应验证允许与禁止动作，而不是只复制实现步骤。

fixture用于协议和控制流；仿真用于指定物理环境；实机用于型号现场行为。报告必须标明这些级别。

## 14.5 一周上手计划

第一阶段画全图并追一个任务；第二阶段完成附录F实验1–4，解释日志与checkpoint；第三阶段在仿真观察目录、地图和回放；第四阶段提出一个小能力扩展并做评审。以产物通过为准，时间建议不替代熟练度。

提交应同时提供变更原因、接口/数据影响、测试、未覆盖窗口和更新文档，保留失败过程。不要通过改阈值、关碰撞、重置世界或删除历史让验收通过。

## 14.6 一个可审查增量的交付过程

教学例子增加只读“检查当前地图身份”的能力。第一步写合同：返回 mapId/revision/标定与设备身份，不启用地图、不改配置；第二步实现真实读路径和支持/不可用条件；第三步把最少 planningFields 提供给适用角色。

测试至少包括正常地图、未生成地图、错设备、版本/标定改变、读超时、返回缺字段和副作用拒绝。若读结果需要归档，补上下文预算和实际请求回溯。文档说明该能力不等于地图完成或导航可行。

评审者应能从需求看到契约、handler、实际组合根、测试与证据索引。新增读取工具可以小步交付，物理技能另需独立后置条件；不要为同一增量顺手引入新的全局状态源。

```text
小需求 → 接口/影响范围 → 实现 → 正例与关键反例
        → 回放/证据 → 文档/迁移 → 审查 → 有范围交付
```

阅读新目标通道时，从 `core/objective` 看批准范围，从 `tasks/objective.go` 看幂等创建，再跟 `internal/edgeagent` 的父检查点、子计划、监督、恢复与完成；最后追Local/Worker装配和Coordinator证明接收。先用软件fixture查协议，再做真实Local集成：Host合同测试通过仍可能遗漏复合Runner接线，最新实验已保留这一反例。

上手效率来自明确入口和小闭环，而不是第一天就遍历所有代码。遇到未知问题先按权威对象和执行阶段定位，再查实现；全系统的共同模型能减少跨团队沟通成本。

### 示例施工：接入另一种三维定位来源

先实现外部算法的同次位姿、光心和 world 点输出，再按 slam.registered-frame.v1 进入采集 Provider；地图发布后使用空间包加载器检查测量重放和摘要。不要把 SE3 塞入旧平面 RGB-D 会话。

下一步实现 spatial.localization.v1，测试错机器人/来源、地图修订变化、倒序、旧采集广播与 lost/方差超阈值；配置部署后，控制器按相同完整摘要接收路径并回传 planId。最后运行实际 DDS 接线，检查确切命令后观测、错误高度/姿态和停止。控制器的运动学、动态跟踪与实机误差另验收。模块源码与测试入口见附录 A，软件实验见附录 F。
