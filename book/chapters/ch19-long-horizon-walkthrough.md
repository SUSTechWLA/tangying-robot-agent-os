# 第 19 章 完整任务复盘：目标委托、异常与实验取证

**学习目标**：将前18章连成一条可核查任务链；区别当前目标Host、旧冻结计划与软件长链；用失败和证据限定结论。先修第3、6、7、17、18章。

**关键术语**：父目标、子计划、运行身份、证据索引、独立验收、实验单位

本章以2026-10-15真实Gazebo的 `host-inspection02` 为当前目标架构主线，并对照同日旧通道巡检、软件128能力长链和2026-10-10的历史七阶段任务。它们回答不同问题，不能拼成一条不存在的“最长完整成功轨迹”。出版更新不会重跑机器人或改写原始结果。

## 19.1 从原句到可批准目标合同

Host02的原始目标为：

```text
从客厅出发，巡检卧室和卫生间，最后回到客厅；执行前后读取导航
状态，最后读取地图状态。每次导航均通过闭环执行器确认抵达并
取得新鲜RGB-D观测。
```

场景是 `home_furnished`，单台地面移动操作机器人，实际使用Gazebo、ROS 2、Nav2、RTAB-Map、RGB-D和已有deepseek-flash模型路由。它不是实体机器人、无人机或足式任务，本轮也不含抓放。准备任务先完成标定、建图与地图启用，后续保留同一Runtime世界、地图、数据库及所有失败。

请求通过 `/v1/objectives` 创建未批准的 `edge.goal` 父节点。其grant只允许一次 `robot.task`，业务request被枚举固定为“从客厅出发，巡检卧室和卫生间，最后回到客厅”；另允许无参数的navigation.status、mapping.status和semantic.locations。资源只有robot，effects为READ/PHYSICAL_MOTION，预算为3代、10次子能力、120次Host业务读、1,200秒，另有绝对期限。

这使边缘可决定现场调用组织，却不能改去其他房间、增加物理技能或反复跑同一路线。若只传一段自然语言而不给这些限制，系统无法判断后续规划是否仍被授权。

## 19.3 一代子计划怎样执行原目标

```text
父目标创建 → 批准 → Host检查当前合同/目录
   → 本机Planner：navigation.status → robot.task → navigation.status → mapping.status
   → 子能力逐步执行/验证 → 完成条件读取 → 父目标证明 → SUCCEEDED
```

| 层次 | 本例记录 | 不应混用的单位 |
| --- | --- | --- |
| 父目标 | 1个批准目标、1代子计划 | 不等于1次运动 |
| 子能力 | 4次，含一个复合robot.task | 不等于4个物理步骤 |
| Runner/Runtime | 10个物理/验证子步骤 | 含观察、准备、导航与到达验证 |
| Host业务读 | 8次 | 不包含所有内部传感器帧/控制周期 |
| 到位确认 | 客厅→卧室→卫生间→客厅，共4次 | 含起点确认，不等于4次跨房移动 |

Planner只接收合同允许的目录和本机语义字段。Host保存每代完整上下文/trace，逐步预留预算、绑定子身份、派发与验证后确认检查点。固定路线进入原闭环Runner，每次到达都需要确切命令后的新鲜RGB-D和定位验证；主机界面显示成功不构成独立判据。

执行从15:25:58.599721至15:29:58.445870 UTC，为239.846秒；Harness总计250.158秒，计时范围不同。父账本112事件，4份实际模型输入快照；这些不是112个独立任务或4个独立Agent模型。

## 19.4 完成证明怎样接受审查

三个只读谓词分别要求navigation.status的mapId、mapRevision与准备地图一致，以及localizationState为localized。地图为 `scan-73e5d48169a5`，revision为 `830264795090367ed40379d1106d3d0eefd2a47690b07b4258c7ff32468fc076`。

谓词全真只说明地图/定位终态，不能单独证明巡检路线完成。独立验收还核对grant、父/子计划、逐步身份、命令后RGB-D、路线顺序、到位和无重放，覆盖287文件、16,955,159字节；冻结依赖复制到新scratch后的只读重验也通过。

最大到位观测残差为0.003145米/0.028505弧度，表示相对目标的观测残差，不是SLAM绝对定位精度。实际累计行驶里程没有测量，记录null/not_measured，不能拿准备阶段建图轨迹替代，也不能填0。

## 19.5 首个Host失败为什么必须保留

Host01使用同一精确巡检目标，但结果为RECOVERABLE_FAILURE，17.179秒，零物理派发、零观测。新Host设置合法子Pending后，复合Runner又进入父目标恢复，把当前Pending误判成重启未决。只做Host合同fixture没有覆盖这一真实Local装配路径。

处理顺序是保存原任务/检查点，只读核对Runtime命令journal中该任务没有物理派发，在无活动任务边界更新本轮Agent，再创建新的独立Host02实验。修复使已选定legacy路径只查物理步骤账本；外部父恢复、历史STARTED、审批与撤销门禁仍保留，没有增加SkipRecovery开关。

原Host01没有被自动重放、删除或改成成功。Host02是开发修复后的新任务验证，不是Agent在运动中自行修改代码。把这两个实验混写成“自动恢复完成原任务”，会错误扩大系统能力。

## 19.6 旧通道的一次真实多Agent读取恢复

同日 `inspection02` 仍走 `/v1/tasks` 冻结计划，原句要求两段完整路线：客厅→卧室→卫生间→客厅，以及客厅→厨房→客厅，前后读取导航/地图，每次导航到位并取新鲜RGB-D。Task为 `task-2e3c9aa3ef08e9fdefa41071`。

第一次创建 `inspection01` 在120秒HTTP等待结束时失败，确认没有Task、没有运动；9轮真实模型trace保存。随后同一原句使用独立planning-timeout 600，不延长运动预算，保留遗漏客厅路线的覆盖拒绝，没有缩减原句。

执行时首个navigation.status在转发前注入一次UNAVAILABLE：Task记录原失败，Ops定位只读故障，Recovery提出execution.read-history调查，受控执行/复验后原command只重读一次，异常清除、原revision继续，无人工resume。它说明Local完整因果链的实际接线，不等于Host完成条件的两次持久重试已在这条轨迹发生。

任务执行448.730秒，Harness528.093秒，7能力、18子步骤、7到位确认；其中两次为路线起点确认，实际跨房移动5次。20个观测、36张图像，独立验收覆盖519文件/433,521,317字节。最大到位残差0.004604米/0.028505弧度，同样不是SLAM绝对精度。

## 19.8 历史七阶段物理案例提供什么对照

2026-10-10 run-007是独立的旧版本Gazebo任务，Task `task-d65a1e20a528b66a4dc8e4bf`、revision 1、source017。其原句含标定、重建图启用、状态、卧室/卫生间巡检、厨房拿杯放盘返回和末尾报告；实际链为Console8897→Local task/ops/recovery→只读故障代理50162→Runtime50161→ROS/Nav2/RGB-D。原2.0.0复核11db0adb、2.1.0复核9e5aebae仅作历史身份，不替代source017。

| 七阶段 | 完成依据 |
| --- | --- |
| 标定读取 | 状态与版本绑定 |
| 巡检SLAM并启用 | operation、地图保存/激活与制品读回 |
| 导航状态读取 | 建图后的真实服务结果 |
| 房间巡检 | 客厅、卧室、卫生间、返回客厅的到位证据 |
| 厨房拿杯放盘并返回 | 同杯持有、稳定入盘、释放与返回 |
| 末尾地图读取 | mapId/revision仍一致 |
| 末尾导航报告 | 当时原始定位字段如实保留 |

该任务7能力、23子步骤、6抵达，1159.459秒。地图235帧/227注册/2闭环/72,972点、约23.458米；58个建图步骤记录最终零速，短时RGB-D等待不额外发非零脉冲。抓放验证为原ceramic-mug与kitchen-tray、5独立样本/200毫秒；10物理命令各一次SENDING，23条Runtime子命令SUCCEEDED。原nav.status只读故障沿seq34→37→39→40调查复验后续跑。

历史暂停seq49→52由操作员发起，65.580224秒，不是自动故障恢复。11个managed上下文、7模型请求、4次压缩、冷分页调用0；机制测试存在不能当现场分页发生。末尾localized且地图一致，但ready=false，定位年龄1078ms超过1000ms阈值；目标要求读取报告，所以保留原false，后采样ready=true不能覆盖它。

独立重验核对1171文件、约1.224GB，257事件和1不可变版本。备份18任务中12失败/6成功，失败没有删除。该案例补充抓放和历史上下文证据，不能把其抓放、当前Host和三维接口拼成一个已联调实机系统。详见[原报告](../../docs/experiments/2026-10-10-long-horizon-protocol.md)与[验收索引](../../docs/experiments/2026-10-10-long-horizon-acceptance.json)。

## 19.9 从证据索引到论文材料

审查按以下顺序进行，不从成功截图倒推事实：

1. 在任务CSV区分环境拒绝、创建失败、执行失败、成功及各二进制版本。
2. 对齐goal、批准、父/子身份、调用和command；核对步骤计量层次。
3. 读取原始trace、检查点、Runtime journal及命令后观测，检查未知/人工干预。
4. 用manifest确认字节与来源；只有SHA没有原制品不足以重验像素。
5. 分别报告业务完成、安全停止、未知待核对及排除项，保留未测量字段。

同日实际Gazebo的准备、创建超时、旧通道巡检、Host01、Host02不是同分布重复样本，不能计算3/5、3/6或100%可靠率。准备建图234采集帧、220注册、72,329点、23.4715516米是Provider报告；Agent observation index为0，与逐命令RGB-D的巡检证据粒度不同。地图资源不匹配的更早启动拒绝独立保存，零动作，未通过改名地图绕过。

2026-10-14 UGV/legged/UAV三类空间案例则为确定性规划、记录式位姿控制器、实际DDS/gRPC，无动力学或硬件。三类各11段支持空间协议身份与XYZ没有被压平；不与Gazebo或fixture合并成功率，不证明实际飞行、步态、ATE/RPE或无人值守。
