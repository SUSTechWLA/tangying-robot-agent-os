# 前言：这本书想解决的问题

## 一个让人不舒服的观察

2024 年以后，"大模型控制机器人"成了一件很容易演示的事。

你让模型调用一个 `pick()` 工具，工具返回 `{"success": true}`，你在屏幕上打一个绿色对勾，录一段视频，发出去。整个过程不超过一百行代码。

问题是：**杯子真的被拿起来了吗？**

可能拿起来了。可能夹爪合拢时滑了一下。可能夹的是旁边那个。可能夹到一半，机械臂在最后 3 度的时候卡住了，而工具层只判断"指令已下发"就乐观地返回了成功。

**这三种情况，从工具返回值上看一模一样。**

这就是这本书要解决的问题。而它带来的第一个、也是最不直观的结论是：

> **「工具返回成功」不是「世界已经按预期改变」的证据。它只是「去看一眼世界」的触发器。**

这个判断往下推，会推出一整套设计：证据门禁、失败分类、未知结果禁止重试、租约与 fencing token、多 Agent 的职责分离、世界模型的版本化。这些设计不是"更完整"，它们是**这一条假设的必然后果**。

---

## 为什么需要一整本书

因为当"证据"这个词被当真之后，系统会长得和你想的不一样。

一个普通的 Agent 系统大致是这样：

```
用户输入 → LLM → 工具调用 → 结果 → LLM → ... → 结束
```

一旦你要求"物理动作必须由动作之后的观测来确认"，这条链路里就必须插入新的东西：

```
用户输入 → LLM 选工具 → 审批 → 下发（带幂等键与 fencing）
                                    ↓
                              ┌─── 结果未知？ ───┐
                              ↓                  ↓
                     有新鲜观测确认         禁止自动重试
                              ↓                  ↓
                          完成           必须先去观测对账
```

而"必须先去观测对账"意味着：系统的状态机必须能表示"我下发了命令但我不知道结果"，而且这个状态必须**跨进程重启存活**。于是你需要持久化的步骤记录、需要世界版本号、需要区分"命令被拒绝"（可安全重试）和"命令可能已经生效"（绝对不可重试）。

再往下：如果有多台机器人，两个进程可能同时操作同一个杯子，于是你需要租约；租约到期后旧持有者的迟到命令可能在新持有者之后到达，于是你需要单调递增的 fencing token；那么多个进程各自以为任务完成了怎么办？于是你需要单写协调。

**这不是功能堆栈，这是同一条约束在七个层面上的投影。**

这本书的价值就在于：把这七层投影一条一条拆开讲清楚，让你不仅能复现，还能判断"什么时候这些复杂性是必要的，什么时候是过度设计"。

## 为什么用这个项目讲

因为它是**认真对待了这条约束**的少数系统之一，而且它的作者把"没做到的部分"也写进了文档。

### 一、它把边界划在了别处

市面上大多数机器人 Demo 的完成判据是工具返回值。这个项目的判据是：

```go
// core/closedloop/closedloop.go
// A tool result is a trigger to look at the world, never proof that the world
// changed as intended.
```

一句注释，决定了整个 `core/closedloop` 包的存在。

### 二、它区分了「已实现」和「已验证」

一个项目的诚实程度，最好的检验方式是看它有没有一份"我还没验证过的东西"的清单。这个项目有：

> 仍须独立验证的范围：
> - leader fencing 与所有业务提交的同存储原子校验；
> - MySQL、Redis、世界投影与物理结果之间可恢复的资源转移 saga；
> - 数据库/队列切主、网络重排和长期多进程故障验证；
> - 实机传感器质量、坐标标定、匹配策略、实体急停、停止响应和受限任务验收；
> - 目标终端可见帧率、现场容量、备份恢复和长期运维。
>
> —— `docs/architecture/distributed-agentos.md`

另一处：

> **返程导航（回到出发房间）**：⚠️ 受地图覆盖限制。参考地图上返程点未认证可通行，`navigation.navigate` 以 `GOAL_NOT_CLEAR` 结束。这是"不知道的地方不进去"，不是缺陷，但**在这一版上返程确实没走通**。
>
> —— `README.md`

一个项目主动说"这一版上这个功能确实没走通"，是它可以被用来写书的前提。

### 三、它记录了失败的发现过程

它的开发记录不只写"做了什么"，还写"怎么发现的、我犯了什么错"。比如和用户对话时的这一段：

> 仓库里现存的事故记录（`artifacts/incidents/`）**没有一条**真的走到 `uncertainStepIds` 非空——那 13 条都是 `NO_RECOVERY_REQUIRED` 或 `PAUSING`。上面这个断网场景是**根据代码语义构造的**，不是从真实事故里摘的。
>
> —— `docs/architecture/lifecycle-objects.md`

对教学来说，这比任何成功案例都更有价值。**工程师的核心能力是"知道自己在多大程度上不知道"。**

## 这本书的写作方法

这套方法本身也值得说明，因为它直接关系到你能不能在读完之后去做同样的事。

### 第一步：先派研究员逐个子系统读源码

写书之前，六个研究任务并行展开，分别深挖：闭环契约、工具层与安全、多 Agent 运行时、分布式控制面、世界模型与编排、仿真与 sim2real、运维与训练、架构演进史。

每个研究员的要求是：**给出真实的标识符（结构体字段名、函数名、错误变量名、状态名）、真实的 `文件:行号`、真实的实验数字**。凡推断标注「推断」，凡文档与代码冲突显式标注冲突。

这些笔记全部保留在 `research/` 目录。它们比章节更贴近源码，如果你要动手改代码，直接从它们入手比从章节入手更快。

### 第二步：只写能被源码支撑的句子

章节里出现的每个技术断言，都能在章节末尾的源码索引里找到出处。这不是学术规范洁癖，这是**让你能验证我**。

### 第三步：区分四种证据强度

这是整本书反复使用的一个判断框架，也是我认为这个项目最重要的方法论贡献：

| 证据等级 | 例子 | 它能证明什么 | 它**不能**证明什么 |
| --- | --- | --- | --- |
| **单元测试** | `make test` 全绿 | 某个函数在给定输入下行为正确 | 系统在真机上能跑 |
| **仿真闭环** | 五房间家居场景走完 12 步 | 契约、身份、停止、恢复、证据逻辑闭合 | 物理策略可用、标定正确 |
| **现场记录** | 真实机器人的一次受监护验收 | 这一次、这台机器、这个环境下成立 | 下一台机器也成立 |
| **实机放行** | 30 次受监护验收 + 实体急停 | 可以交给人用 | 可以无人值守 |

项目里的原话是：**"软件发布与实机放行是两项独立结论——仿真通过不等于实机可用，这是刻意的。"**

你在书里会反复看到这张表被使用。**如果你只从这本书里带走一样东西，我希望是它。**

## 你会读到什么，不会读到什么

### 会读到

- **从物理约束出发的架构推导**：不是"我们有三层"，而是"控制回路 100Hz–1kHz、急停毫秒级、感知每秒数十 MB，这三条决定了机器人端必须自治"。
- **完整的机制实现**：证据门禁的判定逻辑（精确到毫秒比较）、八类失败分类的完整码表、租约与 fencing 的时序、Outbox 的幂等键生成。
- **真实的对照实验**：SLAM 覆盖率 38.9% → 81% 的完整实验设计、语义地图四种表达方式的对照、Agent 上下文的三轮因子实验。
- **真实的缺陷修复史**：从"故障丢弃整张地图"到"没执行却报已执行"到"两个永远不成立的检查"——现象、根因、修法、留下的防线。
- **一个可以照着做的施工路径**：第 16 章是从零搭建的完整路线，分阶段、有验收标准、有"这一步做完了怎么证明"。

### 不会读到

- **性能基准**。项目作者自己说了："分层带来的延迟开销、跨层调用的 p99，本文没有数据。"这本书也不会替他编。第 17 章会说明这类实验怎么做。
- **多机压测结论**。"fencing / 租约的复杂度是设计论证，不是压测结论。"
- **"这套架构适用于所有人"的结论**。恰恰相反——第 1 章第 5 节会明确告诉你，**一台机器人 + 一个人看着 + 非安全关键的场景，三层架构是过度设计**。

## 关于术语的一个提醒

这个项目叫自己 "AgentOS"，但它的作者明确反对这个名字：

> **"OS"这个词用错了地方。** 这个项目是**机器人 Agent 运行时**，它结构上不保证实时性，也不该保证。
>
> 叫它 OS 会让人期待它保证实时性，而它保证不了——**期待错位比能力不足更危险**。

我在书中沿用 "AgentOS" 只在指代项目名时使用。在讨论架构时，我会用作者建议的命名：

| 层 | 本书使用的名字 |
| --- | --- |
| 电机 / 关节 / 安全监督 / 实时控制 | **机器人控制系统**（Robot Control System） |
| Agent 层（这个项目） | **机器人 Agent 运行时**（Robot Agent Runtime） |
| 多机编排 | **机队控制面**（Fleet Control Plane） |

## 一句给读者的话

这本书里没有魔法。你会看到一个团队（实际上主要是作者一个人）用两年时间，把"让机器人把活干完"这件事拆到能验证的粒度：**一个证据、一个失败码、一个租约、一个版本号地拆。**

读完之后，我希望你能获得两样东西：

1. **一套判断力**：看到一个机器人 agent 系统，能判断它是真的还是"有 agent 形状但没有 agent 实质"。
2. **一张施工图**：知道从零开始要按什么顺序建什么，每一步怎么验收。

至于未来——这本书的最后一章会告诉你，这套系统**自己承认**还有哪些没解决。那部分可能比前面十七章更重要。
