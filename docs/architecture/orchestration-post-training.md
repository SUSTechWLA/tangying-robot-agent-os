# 编排层的后训练：先量，再蒸，最后才谈强化学习

本文回答三件事：**小参数量模型自训编排层会不会更好**、**评测体系长什么样**（已实现）、
以及**后训练机制该怎么搭**（设计 + 现在就能做的那部分）。

配套：[LLM 驱动的执行](llm-driven-execution.md)、[多 Agent 运行时](multi-agent-runtime.md)、
[恢复 Agent](recovery-agent.md)。

---

## 一、先说结论：会更好，但不是在所有维度上

"小模型自己训编排层会不会更好"——**取决于比什么**。把可预期的收益和代价分开写：

| 维度 | 小模型自训 | 说明 |
| --- | --- | --- |
| 单位成本 | **显著更好** | 编排在每次任务创建时发生。一个 1–7B 的本地模型相对前沿 API 是数量级的差别 |
| 延迟 | **显著更好** | 本地推理省掉一次跨网往返；编排在交互路径上，用户能感觉到 |
| 格式遵从 | **通常更好** | 技能目录是固定的、输出 schema 是固定的。专门训过的模型在"永远返回合法技能图"上比通用模型稳 |
| 离线/隐私 | **更好** | 不依赖外网，任务文本不出机器 |
| 域内理解 | **可能相当** | 家庭取放的说法分布很窄，窄分布上小模型可以追平 |
| **域外/歧义处理** | **明显更差** | 这是最容易被忽略的一条。判别"这句话我做不到"需要世界知识，而世界知识正是小模型缺的 |
| **拒绝的准确性** | **风险最高** | 见下 |

### 拒绝比规划更难，而它更危险

评测已经量出了这个差别（见第三节）。当前的确定性语法：

```
planner=deterministic  6/10
  executable: 0/4      ← 一条都规划不出来
  refusals:   6/6      ← 但该拒的全拒了
```

前沿模型：

```
planner=deepseek-flash  9/10
  executable: 4/4       ← 全都能规划
  refusals:   5/6       ← 但把"红色和蓝色方块"一次性规划了 14 步
```

**两边失败的方向是相反的。** 语法的问题是"太保守"，模型的问题是"太配合"。
一个自训的小模型最可能继承的是**训练数据里出现最多的那个方向**——
如果我们用 API 模型的输出做蒸馏数据，它学到的是"总是给出计划"，
于是**"该拒绝时拒绝"这个能力会在蒸馏中丢掉**，而它恰好是最不能丢的一个。

所以后训练的顺序不是可选的：**先建评测（已做），再蒸馏，最后才是强化学习**。
跳过评测直接训，等于用一个没有刻度的尺子量一个还没有的东西。

### 另一个必须说清楚的现实

**当前仿真里任务跑不完。** grounding 仍然拿到 0 个物体（原因见 CHANGELOG 最近一条：
`Observe(streams=["entities"])` 这条流没有数据）。这意味着：

- **基于任务结果的奖励现在全是负的**，且与编排质量无关——再好的计划也过不了 grounding。
- 现在能做 RL 的奖励只能来自**过程信号**（计划是否合法、是否通过门禁、是否被拒绝），
  而不是**结果信号**（机器人有没有把事做完）。
- 过程信号可以训出"合法且守规矩的编排"，训不出"能做对事的编排"。

**结论：RL 可以搭，但在 grounding 修好之前不要指望它提升任务成功率。** 这句话写在这里，
是因为一个在坏环境上跑出来的 reward curve 看起来会很像学习，实际是在拟合环境噪声。

## 二、评测体系（已实现，可以直接用）

`orchestration/eval` + `cmd/nl-eval`。核心设计取舍：

### 只问一个问题：这个计划能不能跑

不评"模型好不好"，只评"给定这句话，产出的是不是一份会执行的计划、以及该不该拒绝"。
抽象的质量没有刻度，这一条有。

### 拒绝是独立维度，不和规划混算

报告永远分两半打印：

```
planner=<名字>  N/M cases
  executable: a/b
  refusals:   c/d
```

**一个什么都拒绝的系统在拒绝那一半满分。** 如果只报一个准确率，
"不敢做"和"做错了"会互相掩盖，而这两者需要完全相反的修法。

### 断言目标，不断言实现

用例断言的是"机器人去了厨房"，不是"计划里有 `navigate_route`"。
**这条规则是被一次真实失败教会的**：第一版 `navigate-kitchen` 用例断言了工具名
`navigate_route`，而计划里装的是技能 `navigation.navigate`——一个正确的导航计划被判为错误。
评测器自己踩了它在注释里警告的坑。

### 运行失败 ≠ 答错

模型不可达是 `Error`，不是 `Refused`。混起来会让"端点挂了"看起来像"模型判断力差"，
而训练循环会因此丢掉一个其实没被评估的 checkpoint。退出码也分开：0 全过 / 1 有错 / 2 跑不起来。

### 怎么用

```bash
make nl-eval                                   # 确定性基线
make nl-eval MODEL=... BASE_URL=... API_KEY=...   # 任意 OpenAI 兼容端点
./bin/nl-eval -json report.json                # 机器可读，喂给训练循环
```

**换一个端点就是全部的接口。** 一个 checkpoint 被接受，是因为它在这套用例上的数字更好，
不是因为它的样例读起来更顺。

## 三、后训练机制

三段式，**每一段都有明确的准入门槛**，不允许跳段。

### 第 0 段：数据（现在就能做）

数据来源已经在库里，不需要新采集：

| 来源 | 内容 | 用途 |
| --- | --- | --- |
| `task_events` | `TASK_CREATED` 的原始 request + `ops.recovery_plan` | 输入侧语料 |
| `task_revisions.content_json` | 分解出的步骤、postcondition、语义指纹 | 结果侧监督信号 |
| `step_runs` / `TOOL_ACTIVITY` | 每一步实际执行结果 | 结果信号 |
| `observation_evidence` | 动作后的新鲜观测，闭环门的判据 | **奖励的地基** |
| `ops.anomaly_detected` | 失败与失败分类 | 负样本 |

导出格式建议 **JSONL，一条一个 (request, plan, outcome) 三元组**，
`outcome` 里带 `verified` 与失败分类。这份导出是 SFT 和 RL 共用的同一份数据——
两份数据必然漂移。

### 第 1 段：SFT / 蒸馏（有卡就能跑）

用前沿模型的输出（或库里已有的成功计划）做监督，把"技能目录 + 请求 → 技能图"这个映射
教给小模型。这是**收益最确定的一段**：格式遵从、域内说法、成本，都能拿到。

**必须混入拒绝样本。** 训练集里只有"成功的计划"，模型就只会给计划。
拒绝样本从两个地方来：确定性语法判定的歧义/否定/条件句（免费、可靠），
以及 API 模型自己拒绝的请求。**比例不能太低**——这是最容易被蒸馏丢掉的能力。

准入门槛：`make nl-eval` 上 **executable 不低于基线，refusals 不允许下降**。
两个条件是 AND，不是加权和。

### 第 2 段：偏好优化 / RL（grounding 修好之后再谈）

**奖励从哪来**，按可信度从高到低：

1. **闭环证据（最强）**：动作是否被新鲜观测确认。这是库里已有的机制，不是为训练发明的。
   它同时是防 reward hacking 的关键：模型无法通过"看起来成功"骗过它。
2. **任务终态**：`SUCCEEDED` / 失败分类。稀疏但真实。
3. **过程合法性**：计划是否引用了目录里存在的技能、依赖是否成环、是否触碰被禁技能。
   稠密、便宜，但**可以刷**——单独用它训出来的策略会产出合法但无意义的计划。

**奖励设计的三条硬规则**：

- **拒绝必须能得分。** 一个只奖励"产生计划"的奖励函数，会把模型训成永远不拒绝——
  而拒绝是安全属性。拒绝样本进 RL 时，正确拒绝要给正奖励。
- **未知结果不能当成功**，也不能当失败。`UNKNOWN_OUTCOME` 在库里是一等公民，
  奖励函数里也必须是：既不给正分也不给负分，而是屏蔽该样本。把它算成成功，
  训出来的是"敢于制造未知结果"的策略。
- **闭环门禁不参与训练**。门禁是执行期的事实判定，训练只能读它的结论，不能改它。
  反过来（让策略影响自己奖励的判定）就是本仓库一直在防的那种自证。

### 第 3 段：持续更新的形态

```
线上任务 → 账本 → 导出 JSONL → SFT → nl-eval 门槛 → 影子编排 → 人工/自动放行 → 上线
                                   ↑                                    │
                                   └────────── 不达标就停在原地 ─────────┘
```

**影子编排**：新 checkpoint 与现役模型对同一批真实请求各出一份计划，
**只有现役的被执行**，两份都进评测。这是唯一能不拿真机冒险就拿到线上分布的做法。

## 四、必须防的退化

| 退化 | 表现 | 防线 |
| --- | --- | --- |
| 永不拒绝 | executable 涨、refusals 崩 | 两半分别设门槛，禁止互相抵扣 |
| 拒绝一切 | refusals 满分、executable 为 0 | 同上（这也是为什么门槛是 AND） |
| 计划膨胀 | 一句话产出 22 步 | 用例断言步数上限；`budget` 已在 schema 里 |
| 格式坍塌 | 输出不再是合法技能图 | 计划必须过目录校验；非法即 0 分，不是部分分 |
| 刷过程奖励 | 合法但无意义的计划 | 结果信号与过程信号同时在场；只信闭环证据 |
| 过拟合评测集 | 用例分数涨、线上失败率不降 | 影子编排 + 用例集只按"新失败原因"增长，不按同义句增长 |

## 五、现在该做什么（按顺序）

1. **修 grounding**（`Observe(streams=["entities"])` 无数据）。在那之前，结果信号不存在。
2. **补拒绝样本并导出 JSONL**。库里已有足够多的歧义/否定/条件请求。
3. **跑一次基线对照**：`make nl-eval` 分别打确定性、DeepSeek、以及将来的本地模型。
   三个数字放在一起，才知道自训到底有没有用。
4. **SFT 第一版**，只做格式与域内说法，不动拒绝策略——先看能不能追平。
5. **有卡之后再谈 RL。** 奖励从闭环证据取，拒绝样本给正分，未知结果屏蔽。

**一句话**：自训编排层值得做，收益主要在成本、延迟与格式稳定性；
但它**不会自动带来更好的判断力**，而判断力（尤其是"该不该做"）才是编排层最贵的部分。
评测体系已经建好了，先用它量出差距，再决定训什么。
