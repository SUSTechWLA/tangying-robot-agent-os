# LLM 驱动的执行：让模型在执行过程中选工具与编排

当前阅读范围（2026-11-02，`27cbbbaf9`）：本页先说明今天的决策位置，后半保留把旧 Runner 改为逐步模型决策的设计讨论。Local/Worker 已通过共享 Host 在批准目标包络内持续编排；这与“把每个低层 Runner 步骤都换成一次 LLM 调用”是不同改造，见[分层目标](hierarchical-edge-objectives.md)。

本文回答两件事：**当前每一步由谁决定**，以及**若继续改造旧执行图为逐步模型决策，需要保留哪些契约**。

配套阅读：[多 Agent 运行时](multi-agent-runtime.md)、[恢复 Agent](recovery-agent.md)、[生命周期对象](lifecycle-objects.md)。

## 一、当前每一步的决策者

| 层 | 谁决定 | 时机 | 硬编码？ |
| --- | --- | --- | --- |
| 用户输入 → 接收关联 | `internal/agentsession` 保存原句、session/turn 与候选 task ID | Local 创建任务前 | 确定性，不执行动作 |
| 原句 → legacy 意图/执行图 | `agent/intent` 规则优先、可选兼容模型；`orchestration.Planner` 形成旧图 | 创建任务时 | 规则与模型均有，按配置选择 |
| 自然语言 → 能力计划 | `capabilityagent.Planner` 读取受限语义字段，由 GOAL 模型提出候选并确定性 freeze | `/v1/tasks` 审批前；Host 获批目标每代子计划时 | 模型提出，代码校验 |
| 获批目标 → 剩余工作 | `internal/edgeagent.Host` 检查批准、目录、预算和持久回执，再决定是否生成下一代 | 目标执行与验证之间 | Host 决定准入，模型可规划 |
| 步骤 → 设备动作 | Runtime 与所配置控制器/Policy Provider | 每次已准入调用 | 具体机器人适配器负责；不要求强化学习 |
| 意外 → 调查/恢复 | Ops、Recovery、读复验与 Host 监督；未知物理效果停下对账 | 执行失败及恢复时 | 规则及可选模型，受预算与证据约束 |

Local 自动会话的历史以独立 reference 进入 GOAL，当前原句和任务批准仍独立；它不会让 legacy parser 自动理解跨轮“它”，也不会让模型续做 UNKNOWN 动作。含会话参考的 recipe 只能提供提示。各路径默认值、缓存与用量见[模型成本指南](../production/model-cost-and-recipes.md)。

旧 Runner 仍可以按冻结执行图运行；目标 Host 已提供另一层有界持续细化。因此不能再把“执行中没有人重新决定”当作整个系统的现状。以下第 2–10 节主要保留旧 Runner 改造的设计动机与当时恢复测试；其中默认 `PlanDecider`、接线进度和测试数量不是当前全部目标入口的统一配置或本轮新测试结果。

## 二、目标

```
        ┌──────────────────── 循环 ────────────────────┐
        │                                              │
  观测 ──▼── LLM 决策（选一个工具调用 / 或宣告完成 / 或宣告做不到）
              │
              ▼
         harness 校验（是不是清单里的技能？当前安全档位允许吗？）
              │
              ▼
         批准门 → 下发 → 证据门 → 复验 → 记录
              │
              └──────────── 新观测回到顶部 ────────────┘
```

与今天的区别只有一处：**步骤列表不再是输入，而是每轮决策的输出**。

## 三、信封：不需要新的策略，清单就是信封

`core/skills/manifest.go` 每个技能已经声明了约束字段：

| 字段 | 作用 |
| --- | --- |
| `SafetyLevel` | `read_only` / `local_side_effect` / `physical_motion` |
| `ApprovalPolicy` | 该技能需要什么批准 |
| `MutatesWorld` | 是否必须由动作后的新鲜观测确认 |
| `AllowedSafetyProfiles` | 哪些安全档位下允许调用 |

**LLM 的自由度就是"当前档位下清单里可用的技能集合"**，不需要发明第二套策略。模型选了什么，harness 就按这些字段照常执行——**校验不放松，只把"谁来选"从计划期搬到执行期**。

### 批准范围是独立于批准端口的一道检查（已决定：不能）

**决策：模型在执行期不得执行"批准时没在计划里出现过"的物理动作。**

理由是把两个不同的问题分开：

| 问题 | 谁回答 |
| --- | --- |
| "这一次调用可以发生吗" | `Approver`（批准端口） |
| "这类事情**当初**被批准过吗" | `Scope`（批准范围） |

把它们合成一个，等于"有人能批准"就是"授权无上限"——模型只要好好开口要一个操作者从没见过的动作，就能自己扩大授权范围。那样操作者的批准在任何重要时刻都不再意味着什么。

落到代码（`internal/actionloop`）：

- `Scope` 只约束 **`physical_motion`**。只读和 `local_side_effect` 不受约束——它们不改变世界，而循环不能"看"就没法决策；把"看"也纳入范围不是安全属性，是一次停机。
- 超出范围的物理调用**不执行、也不静默跳过**：记录 `OUTSIDE_APPROVED_SCOPE` 裁决，带上**工具名、参数、模型给的理由**，然后停机升级。对"机器人想做你没批准的事"，有用的回答是**那份提案**，不是沉默。
- **`Scope` 为 nil 时拒绝一切物理调用。** 没有声明批准范围的部署等于什么都没批准；把缺失读成"无上限"会让声明在最要紧的地方失效。空 `ScopeOf()` 同样什么都不放行。
- 范围内的物理调用**仍然需要批准**：范围说明"这件事被考虑过"，不等于"这一次被批准了"。
- 停机而不是换一个范围内的工具继续——换个工具做，就是绕过操作者的拒绝。

## 四、必须不变的东西（这是硬约束）

模型进入执行回路，**不改变任何一条既有安全不变量**。逐条对应到它今天守在哪：

| 不变量 | 今天守在哪 | 模型驱动后 |
| --- | --- | --- |
| 成功 ≠ 完成，物理写入必须有动作后的新鲜证据 | `closedloop.Gate`（`edge/agent/runner.go:453`） | **不变**：每个模型选的步骤照样过门 |
| 物理动作需要人工批准 | `runner.go:385` `physical && !task.Approved` | **不变**：任务级批准仍然前置 |
| 结果未知禁止自动重试 | `runner.go:189` `ErrPhysicalOutcomeUnknown`；观察者 `UNKNOWN_OUTCOME`；恢复 Agent `rule.reconcile-first` | **不变**：未知结果直接终止循环，且不是"换一个工具再试" |
| 每次尝试可回溯 | 任务事件账本 | **加强**：决策本身也要入账 |
| 有界 | 无（今天靠计划固定） | **新增**：决策轮数上限 |

## 五、循环的边界（必须定死，否则就是无限自主）

| 边界 | 值 | 触顶后 |
| --- | --- | --- |
| 单任务决策轮数 | 上限（配置，默认与计划步数量级相当） | 停止 → `RECOVERABLE_FAILURE`，交人 |
| 同一个技能连续失败 | 不许超过既有的分类结论：`UNKNOWN_OUTCOME` 立即停；`PERCEPTION` 允许重新观测后重选；`VALIDATION`/`FATAL` 立即停 | 立即转人工 |
| 模型连续给不出可执行决策 | 2 次 | 转人工 |
| 任何一步结果未知 | — | **立即停止**，不进下一次决策 |

## 六、决策必须可回溯（这是新增的账）

今天的回放能看到"执行了哪些步骤"。模型进入回路后，还必须能看到**"为什么走了这一步"**：

- 这一轮的观测是什么（引用 evidence id）；
- 模型看到的候选技能集合；
- 模型选了什么、理由是什么（`reason`）；
- 校验结果（通过 / 被哪条规则拒绝）；
- 与上一轮相比世界变了什么。

与恢复 Agent 的调查轨迹（`agentruntime/trail.go`）同构：**结论要能被人复核，推理过程就必须是结构化的记录，而不是散文**。

## 七、①（恢复计划的执行通道）复用同一条回路

用户要的"批准后执行恢复动作"，与这件事是**同一个机制**：都是"一个模型提议的动作，在 harness 门禁下被执行并复验"。所以只建一条路径：

```
恢复 Agent 提议 ─┐
                 ├─→ 待批准动作 ─→ 批准 ─→ 带门禁执行 ─→ 复验 ─→ 记录
LLM 执行期决策 ──┘
```

区别只在批准粒度：恢复计划是**逐步批准**（一步一个动作，因为它是从异常中恢复，风险更高），执行期决策在**任务级批准**的覆盖下（因为整件任务已经被人批过）。

**不做两条执行路径**——那正是本仓库反复出问题的地方（发现协议、分类表、重试策略都因为"两处实现"漂移过）。

## 八、迁移：可关、可对比

沿用本仓库既有的做法（`TANGYING_AGENTS=task` 关掉观察者以证明观测没改变行为）：

- **默认仍是固定计划**（`PlanDecider`），行为逐字节不变；
- LLM 驱动执行是**显式开启**；
- 两种模式跑同一批任务，**步骤序列应当可比较**——差异就是模型重新决策带来的价值（或风险）。

`observe.re-read` → 执行成功但 `verified=false`；`map.activate` → 轨迹含 `approval.operator`，执行体报
"没有配置决策器"。最后一条正是设计要的样子：**没有模型时它不编造调用**，而把缺决策器如实记进轨迹。
当次实测的复验端口未配置，因此该次结果为“未确认”；这不覆盖后来接入的能力只读复验和 Host 子步骤验证，见[长程协作](long-horizon-collaboration.md)。

**端到端实测**（新鲜任务）：自然语言 → 意图 → 分解 1 步 → 批准 → 下发 → 失败
→ `ANOMALY_ABNORMAL_TASK` → `ops.recovery_plan` → `ops.recovery_executed`，全程无人工介入。

读这一行时要知道它**证明了什么、没证明什么**：证明的是这条链通了；
**没有**证明"执行期由模型重新决策"——那正是上表第一行仍未做的那件事。
恢复通道走的是它自己的循环，不是 runner 的那条执行路径。

**现在可以确定的事**：这个机制是可用的——一个模型能驱动循环、它的选择会被 harness 照常门禁、未知结果会立刻终止、每一步都留下可复核的记录。
**该次旧通道测试不能说明的事**：它没有把旧 Runner 全部改成逐轮 LLM 调用。后来的 GOAL/Host 与 Gazebo 自然语言任务应按各自[实验报告](../experiments/README.md)判断，不能反过来把后来结果计入这次旧测试。

接进 runner 是下一步，也是风险最高的一步（物理执行路径）。它需要：
- `PlanDecider`（现有行为，默认）与 `LLMDecider` 共存，默认不变，可对比；
- 决策账写进任务事件账本，回放能看到"为什么走这一步"；
- 恢复计划的执行通道复用同一条循环，而不是另建一条路径。

## 十、不做什么

- **不放松门禁**：模型选的步骤和计划里的步骤走完全相同的检查。任何"因为模型选的所以跳过检查"都是错的。
- **不让模型直接写关节序列**：低层动作仍然来自 Policy Provider，模型选的是**工具**。
- **不给模型绕过审批的能力**：模型不能批准任何东西。
- **不把决策藏在提示词里**：决策记录是结构化数据，不是日志里的一段话。
