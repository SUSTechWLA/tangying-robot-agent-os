# Review Agent 运行原理：发现问题、定位问题、以及"不做什么"

**Review Agent** 是运行中的监督者。它在代码里的名字是 **OpsAgent**(`agentruntime/opsagent.go`),"ReviewAgent" 是它在产品里的角色名。这份文档讲它**怎么工作、为什么这样设计、以及边界在哪**。

## 一、两个 agent 的分工,一句话说清

| | TaskAgent(执行) | Review Agent(监督) |
| --- | --- | --- |
| 配置名 | `task` | `ops` |
| 回答的问题 | **"任务做完了吗"** | **"现在有什么不对劲"** |
| 权限 | 可改世界、可改任务状态 | **只读** |
| 输出 | 动作、证据、任务终态 | 结构化发现 + 分类 + 建议 |
| 失败了会怎样 | 任务停在某状态等处理 | **什么都不影响**——它是观察者 |

**关键区别不是"一个干活一个看",而是"一个能改、一个不能改"。** Review Agent 的只读不是一条纪律,是这个类型的性质:它没有执行端口、没有任务服务、没有总线句柄。有测试按字段白名单钉住,加任何字段都会失败并强制重新回答"观察者需不需要这个"。

## 二、原理:三条不可动摇的规则

### 规则 1:发现必须带证据,或者明说缺什么

一个 finding 要么给出证据链(`evidenceChain` + `evidenceIds`),要么给出 `missingEvidence` 说明**缺什么**。

为什么:没有证据的解释就是猜测。操作员看到"可能是电源问题"会去查电源;看到"我判断不了,因为没拿到 X"会去补 X。**后者比前者有用,而且不会误导。**

这条在实测里被验证过:机器人静默时,Review Agent 给的不是"疑似故障",而是

```
message: 还没有可用的机器人观测，当前无法判断机器人状态
missingEvidence: 缺少机器人观测：连接运行时并确认遥测在流动
```

它承认自己看不见,而不是报一个健康的沉默。**监督者最糟的失效模式是沉默被读成健康。**

### 规则 2:复用既有分类,不发明第二套

失败分类只有一套,在 `core/closedloop`:**七类**(`TRANSIENT`/`PERCEPTION`/`PLANNING`/`PERMISSION`/`RESOURCE`/`VALIDATION`/`UNKNOWN_OUTCOME`/`FATAL`),每一类对应**唯一一个安全恢复动作**。

Review Agent 不自己判断"这个失败能不能重试",它调 `closedloop.Classify`。

为什么:两套分类迟早会就"能不能重试"给出不同答案,而其中一套会做出物理动作。**这是安全属性,不是代码整洁问题。**

> **这条规则在实测中被打破过一次,代价很具体。** 运行时会产生 `GRASP_NOT_REACHED`(抓手够不到目标),但这个码**不在分类表里**,于是兜底到 `UNKNOWN_OUTCOME`——系统把"够不到,该重新观测后重试"报成"结果未知,**不要重试,先对账**"。给出的处置是错的。
>
> 修法是把它按 `PERCEPTION` 归入表中。更重要的修法是补上缺失的守卫:**此前只有"表内代码分类正确"的测试,没有测试断言"运行时会产生的码都在表里"**。详见[这轮怎么发现的](../development/2026-09-17-supervision-blind-spots.md)。

### 规则 3:建议必须可执行

每个 critical/warning 级发现**必须带 `recommendedActions`**——按顺序、具体到能照着做。

为什么:一个只报"出错了"的 finding 等于一行日志。它告诉操作员一件他本来就能看到的事,而不告诉他该做什么。这条以前**完全没有测试**,现在故障矩阵里每个场景都断言建议里必须出现具体内容(如 `VALIDATION` 类必须提"参数/版本",而不是"重试")。

**唯一的例外是"我什么都判断不了"**——那种情况下给的是 `missingEvidence`(缺什么),不是假装有建议。

## 三、运行:发现从哪来,结论到哪去

```
                    ┌── 实时事件 ──────────────────────────┐
机器人遥测 ──┤                                          ├──→ Review Agent ──→ 发现
                    └── 持久记录（重启后补读）──────────┘        │
                                                                  ├─ 任务级发现 → 任务账本 → 回放
                                                                  └─ 机器人级发现 → 运行级存储 → ⚠️ 告警横幅
```

### 输入有四路,缺一不可

| 输入 | 来源 | 缺了会怎样 |
| --- | --- | --- |
| 机器人遥测 + `robot.faults.v1` | 运行时观测 | 看不到硬件故障、急停、观测过期 |
| 实时任务事件 | 执行过程中发布 | 看不到正在发生的失败 |
| **持久执行记录** | 启动时补读 | **重启前发生的失败全部不可见** |
| **持久任务账本** | 启动时补读 | **说不出"哪一步失败了",只能说出"任务失败了"** |

后两路是实测逼出来的,不是设计时想到的。详见[发现记录](../development/2026-09-17-supervision-blind-spots.md)。

### 输出分两个作用域,这是刻意的

| 作用域 | 去哪 | 为什么 |
| --- | --- | --- |
| **任务级**(哪一步失败了、结果未知) | 任务事件账本 → 回放 | 它讲的是这个任务的故事,应该出现在该任务的回放里,挨着它描述的那些动作 |
| **机器人级**(急停、模块故障、观测过期) | 运行级存储 → ⚠️ 告警横幅 | **急停不是任务问题**,它在没有任务时也必须可见 |

早期版本只有第一条路径,于是机器人级发现因为没有 taskID 而被发到"没人"——**最该被看见的那一类反而进不了告警**。这是实测暴露的。

## 四、告警的生命周期:为什么会自己消失

告警**不是事件累积,是从当前状态投影**:

- 条件还在 → `active: true`
- 条件消除 → `active: false`,自动撤回

为什么不做"累积 + 手动关闭":那样需要一套关闭协议,而且**横幅会比它描述的问题活得更久**——操作员学会了忽略横幅,告警就失效了。

三种情况的判据不同:

| 发现 | 何时算已解决 |
| --- | --- |
| 结果未知(`ANOMALY_UNVERIFIED_MUTATION`) | 执行记录说该步骤不再悬着(**对账完成**) |
| 机器人级(急停/模块故障/观测) | 若干评估周期内不再被重报(条件真的不在了) |
| 其它任务级失败 | 任务记录了**成功**终态 |

**第三条是刻意保守的。** 规则无法判断"人手故障是否已被物理修好",所以它持续报告,直到有东西明确说好了。**在没有证据时声称已解决,和在没有证据时声称任务完成是同一个错误。**

## 五、明确不做的事(边界)

| 不做 | 为什么 |
| --- | --- |
| **不修改任务状态** | 它没有任务服务。状态权威仍是 `tasks.Service` |
| **不动机器人** | 它没有执行端口。结构层保证,有测试 |
| **不自动恢复** | 第一版对任何建议恒为 `advisory` + `requiresApproval`。**建议是给人做的** |
| **不重新推导安全** | 只回答"提出请求的 agent 是不是那种可以做这件事的 agent" |
| **不猜根因** | 确定性规则;证据不足输出 `missingEvidence` |
| **不代按急停、不代插拔线缆、不代改标定** | 这三件的正确反应是**把人叫来**,而不是把软件写得更勇敢 |

最后一条的实测证据:**急停没有解除 RPC**。我写故障注入器时想让脚本自己清理,发现根本没有这个接口——这是设计的直接后果,不是遗漏。

## 六、恢复闭环的全貌,以及当前只走到哪一步

完整闭环是五段,其中两段**尚未实现**:

```
① 检测 ──→ ② 定位 ──→ ③ 决定 ──→ ④ 执行 ──→ ⑤ 验证
   ✅         ✅         ⚠️          ❌          ❌
```

| 段 | 状态 | 说明 |
| --- | --- | --- |
| ① 检测 | ✅ 已实现并实测 | 遥测、故障台账、任务事件、持久记录 |
| ② 定位 | ✅ 已实现并实测 | 复用 `closedloop.Classify`,输出分类 + 证据 + 建议 |
| ③ 决定 | ⚠️ 半实现 | **机器人侧**的处置阶梯已实现(`self_recover`/`operator_assist`/`service_required` + 复发升级);Go 侧只输出 `advisory` 建议 |
| ④ 执行 | ❌ **未接线** | `FaultRemedyEngine` 有完整四条约束和测试,但**生产路径里 0 个调用者** |
| ⑤ 验证 | ❌ 未接线 | 判据已定(复查台账、故障消失才算成功),但没人执行 |

**所以当前能自动做的是"发现并说清楚",不能自动"动手修"。** 这是有意的第一版边界,不是完成态。

第 ④ 段的规矩已经写在[模块故障与自愈](module-health-and-faults.md):只跑故障自己声明的 `self_recover`、`robot_can_move=False` 时不跑会动机器人的动作、单故障最多 2 次、复发 5 次升级、**成功判据是故障消失而不是动作返回成功**。

## 七、这一层为什么值得单独存在

三个理由,都不是"架构好看":

1. **沉默必须被区分于健康。** 没有 review 层时,"机器人没报错"和"机器人没事"在界面上完全一样。加上它之后,前者会明确说出"我看不见"。
2. **失败必须能在没有原进程的情况下被复核。** 值得复核的失败,恰恰是活得比产生它的进程更久的那些。所以它读持久记录,不只读实时事件。
3. **自动化运维的前提是"问题被结构化地描述过"。** `category` + `evidenceChain` + `recommendedActions` 是机器可消费的;一段日志不是。

而它**不能**取代人的地方同样清楚:判断一次修复是否安全、是否值得做,仍然是人或既有权限系统的事。Review Agent 的产出是**更快的定位**,不是**更快的行动**。

## 八、一个尚未接线的能力：`closedloop.Track`

查证监督分类的实际影响面时发现的，如实记在这里。

`core/closedloop` 有两个入口，但生产路径**只用了其中一个**：

| 入口 | 用途 | 生产调用点 |
| --- | --- | --- |
| `Gate` | 动作后的证据门：成功不算完成，必须有新鲜证据 | ✅ `edge/agent/runner.go` |
| `Classify` | 失败码 → 七类 → 唯一安全恢复动作 | ✅ `agentruntime/opsrules.go` |
| **`Track`** | 单次物理写入的状态机：尝试预算、退避 `NextAttemptAt`、`Policy` | ❌ **只在测试里** |

`NewTrack` 在仓库里**只出现在 `closedloop_test.go`**。也就是说：**闭环契约的证据要求是生效的（靠 `Gate` + runner 的步骤状态处理），但 `Track` 那套"有界自动重试"策略从未被驱动。**

两个后果，方向相反：

1. **好的一面**：分类改动（第七节的审计）**不会改变机器人的重试行为**。`Classify` 目前只喂给监督层，而监督层是只读的。这是安全的。
2. **需要知道的一面**：`Track` 已有的能力——尝试预算、确定性退避、`NextAttemptAt`——**没有在生产中生效**。实际的"重试"发生在宿主层：失败 → 任务进入 `RECOVERABLE_FAILURE` → 操作员 resume → 重新执行到该步骤。

**这不是缺陷，是一个未被声明的状态。** 系统的重试语义目前由宿主与操作员决定，`Track` 是一份实现好、测试过、但没有接入的设计。要么接上它（让重试策略真正生效），要么删掉它（避免读代码的人以为它生效）——但**不该继续以"已实现"的样子留在那里**。

这一条是查"我的分类改动会不会导致危险重试"时顺带查出来的，而不是主动审计的结果。**它值得一次专门的决策。**
