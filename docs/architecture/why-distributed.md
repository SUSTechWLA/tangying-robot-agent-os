# 为什么是分层的，以及"分布式"不是重点

本文回答两个反复被问到的问题：**分布式机器人 Agent OS 合不合理**，以及**它和 Codex / Claude Code
那类 agent 到底差在哪**。结论写在最前面，理由在后面。

配套：[多 Agent 运行时](multi-agent-runtime.md)、[恢复 Agent](recovery-agent.md)、
[闭环契约与失败分类](lifecycle-objects.md)、[部署](../operations/deployment.md)。

---

## 0. 三句话

1. **分层是物理强加的，不是架构偏好。** 控制回路、急停、感知带宽三条硬约束决定了机器人端必须自治。
2. **"分布式"不是这个系统的价值所在。** 真正的价值是闭环契约、失败分类、证据与回放——
   这三样在单机上同样需要，而它们都不是分布式带来的。
3. **"OS"这个词用错了地方。** 这个项目是**机器人 Agent 运行时**，它结构上不保证实时性，也不该保证。

---

## 1. 分层是物理决定的

### 1.1 三条硬约束

| 约束 | 数量级 | 后果 |
| --- | --- | --- |
| 控制回路 | 100 Hz – 1 kHz | **不能**穿过一次网络往返，更不可能穿过一次 LLM 推理 |
| 急停 | 毫秒级 | **不能**等网络——等得到的那不叫急停 |
| 感知带宽 | 点云 / 图像，每秒数十 MB | **不能**原样上传 |

这三条决定了：**机器人端必须对一切时间敏感的事情自治。** 不是"分布式更好"，是"不这么做就不成立"。

**推论：任何把 LLM 放进控制回路的架构都是错的。** 本仓库里模型选的是**工具**，
低层动作来自 Policy Provider（VLA / 模仿学习 / RL），这段边界见
[LLM 驱动的执行](llm-driven-execution.md)。

### 1.2 每一层存在的理由（都不是"规模"）

| 层 | 存在的理由 | 不是什么 |
| --- | --- | --- |
| **机器人端** | 实时与安全必须在本地闭环 | 不是"边缘计算省流量" |
| **本地 Agent（边缘）** | **断网可用**——连不上云就不干活的机器人不是机器人，是终端 | 不是缓存层 |
| **云端** | **多机**：机队派单、跨机审计、跨机学习 | 不是"算力更大"；云端**不直接控制硬件** |

### 1.3 反面同样成立

**一台机器人 + 一个人看着 + 非安全关键 → 三层是过度设计。** 直接一个进程更简单，
而且没有分布式一致性问题。

这个仓库之所以需要 fencing token、租约、版本不匹配检测（`internal/discovery` 里真有这个），
是因为它选了多机路线。**这些复杂度是那条路线的真实代价，不是可以省的**——
它们是"部分失败成为常态"的直接后果。

## 2. 和 Codex / Claude Code 类比：表面像，底子不同

### 2.1 像的部分（本仓库确实借了）

- observe → decide → act → verify 的循环
- 工具调用作为动作接口
- **LLM 选工具，而不是硬编码编排**
- 结构化上下文与回放

### 2.2 不像的部分

| | Codex / Claude Code | 机器人 Agent 运行时 |
| --- | --- | --- |
| 世界 | 文本文件 | 物理世界 |
| 观测成本 | 免费，想要多少次都行 | 昂贵，**有时不可观测** |
| 动作可逆 | 几乎总是 | 常常**不可逆** |
| 失败代价 | 重跑一次 | 撞坏东西 / 伤人 |
| **重试** | 默认安全 | **结果未知时禁止重试** |
| 验证 | 跑测试 | 新鲜证据 + 闭环门禁 |
| 真相在哪 | 文件系统即真相 | 世界是真相，**只能被观测** |
| 会话长度 | 分钟到小时 | **年** |
| 人在不在 | 一直在 | **常常不在** |

### 2.3 最关键的一条：**重试的代价**

Codex 的"重试"是免费的——重跑一次测试而已。

机器人的"重试"可能是**把一件已经做过的事再做一遍**：杯子已经拿起来了，再拿一次就是撞。

这一条差异派生出整个系统里最不直观的那些设计：

```
动作下发 → 结果未知（UNKNOWN_OUTCOME）
         → 禁止自动重试
         → 必须先用新鲜观测对账（待取证）
         → 对账之后才允许决定下一步
```

**Codex 不需要这套东西。机器人 Agent 运行时是被这套东西定义的。**

## 3. 真正有价值的三样东西（与分布式无关）

| 机制 | 实现 | 解决的问题 |
| --- | --- | --- |
| **闭环契约** | `core/closedloop` 的 `Gate`：`mutates_world=True` 必须有**动作之后**的新鲜证据，否则 `ErrEvidenceRequired` / `ErrEvidenceStale` | "工具说自己成功了"不是证据 |
| **失败分类** | 8 类：`TRANSIENT` / `PERCEPTION` / `PLANNING` / `PERMISSION` / `RESOURCE` / `VALIDATION` / `UNKNOWN_OUTCOME` / `FATAL`；**只有 Transient 与 Perception 可重试** | 决定"能不能重试"的是一个分类表，不是某个 if |
| **证据与回放** | 任务账本：每一步的工具调用、观测证据、失败分类、恢复动作 | 结论可复核；没有这条就没有"事后追责" |

**这三样是物理世界强加的。** 所以：

> **去掉分布式，这三样依然需要**——单机机器人同样会出现"动作发出去了但不知道成没成"。
>
> **去掉这三样，分布式机器人 Agent OS 就只是个很慢的遥控器**——它有 agent 的形状，
> 没有 agent 的实质。

判断一个"机器人 agent 系统"是不是真的，看它有没有这三样，而不是看它有几个进程。

---

## 4. 优劣对照

### 4.1 分布式机器人 Agent 运行时

**优势**

- **断网可用**：本地 agent + 本地执行，云不可达不影响单机作业
- **安全本地闭环**：急停不等网络
- 多机协同、跨机学习（A 机解决的故障 B 机受益）
- 数据留在本地

**代价**

- **部分失败成为常态**：网络分区、时钟漂移、状态分歧
- **一致性成本**：谁说了算？本仓库用 fencing token + 租约回答——那是真复杂度
- **调试跨多层**：一个动作横跨 robot → edge → cloud
- **版本漂移**：机器人固件与 agent 版本不一致（本仓库为此专门做了检测）
- 每个跨层交互都要写契约测试

### 4.2 类 Codex 架构

**用在机器人上的优势**

- 极简：一个进程，工具是 shell，没有一致性问题
- 开发快几个数量级
- **适合**：单机、有人盯着、非安全关键的场景（实验室里调一台机械臂）
- **更适合**：作为机器人系统里的**一层**——让 LLM 选工具、写编排，而不是让它控制电机。
  这正是本仓库在做的事

**直接当机器人 OS 的问题**

- 网络一断就停
- 没有物理动作的证据语义（"我以为我做完了"）
- 一个 agent 进程控一台机器，无法多机
- 没有安全门禁的位置

## 5. 本地部署：能，而且是首选

**单台机器人、不需要云端调度 → 本地单机。** 这是文档里就写明的一条路线，不是附加能力。

| 检查 | 结论 |
| --- | --- |
| `cmd/local-agent` 引用云端 / fleet | **0 处** |
| 运行所需进程 | 机器人运行时（真机网关或仿真）+ `local-agent`，**仅此** |
| MySQL / Redis / fleet-control-plane | 不需要 |
| 服务化封装 | `deploy/local/` 提供 systemd unit 与 launchd plist |
| 安装入口 | `./install.sh local`；见[部署](../operations/deployment.md) §1 |

### 5.1 三个必须说清的前提

**① "本地"不等于"离线"——模型是出网的。**

编排、自然语言解析、恢复决策都调外部 OpenAI 兼容端点。要真离线，需要**本地推理服务**：
代码侧不用改（换个 `AGENT_BASE_URL` 指向 `127.0.0.1:8000` 即可），但那是要单独准备的一件事。

**② 没有模型时优雅降级，不是不能用。**

确定性语法负责解析；**只读动作照跑，改动机器人的动作停住等人**。
所以"断网"的后果是**能力变窄**，不是**系统挂掉**。

**③ 机器人端是 Python。** 真机需要 Python 3.11 与 `robot/gateway`，平台限定
**Ubuntu 24.04 arm64**。仿真不需要任何硬件。

### 5.2 端口的坑

本地单机文档写的是 `8787`，而 `home-furnished` 显式传 `8897`。**两个都对**——
前者是 `sim-stack.sh` 的默认，后者是家庭场景目标的显式选择。照文档敲
`127.0.0.1:8787` 打不开不是 bug，是文档里已标注的差异。

## 6. 关于"OS"这个词

这个项目实际是 **Agent Runtime + 任务账本 + 安全门禁**。

操作系统要管**调度、内存、驱动、实时性**。而**实时性恰恰必须在 gateway / controller 里，
不能在 agent 层**——本仓库从结构上就保证不了它，也不该保证：一个会被 LLM 推理延迟影响的
控制回路是危险的设计。

**建议的命名**：

| 层 | 名字 |
| --- | --- |
| 电机 / 关节 / 安全监督 / 实时控制 | **机器人控制系统**（Robot Control System） |
| Agent 层（本仓库） | **机器人 Agent 运行时**（Robot Agent Runtime） |
| 多机编排 | 机队控制面（Fleet Control Plane） |

叫它 OS 会让人期待它保证实时性，而它保证不了——**期待错位比能力不足更危险**。

## 7. 判断表

| 你的情况 | 选择 |
| --- | --- |
| 一台机器人，有人在现场 | **本地单机**。少一层，少一类故障 |
| 一台机器人，但要远程运维 | 本地单机 + 出网（注意 §5.1①） |
| 多台机器人，统一派单与审计 | 云端 + 机器人端。**云端不直接控制硬件** |
| 实验室调一台机械臂，非安全关键 | 类 Codex 的单进程架构可能完全够用，而且更简单 |
| 安全关键 / 无人值守 | 必须有闭环契约、失败分类、证据与回放——**与几层无关** |

---

## 8. 这份文档没证明的事

- **没有做过性能基准。** 分层带来的延迟开销、跨层调用的 p99，本文没有数据。
- **没有多机实测。** fencing / 租约的复杂度是设计论证，不是压测结论。
- **"类 Codex 架构更简单"是定性判断**，没有对照实现。

写在这里而不是省略，是因为这三条恰好是本文论证里最容易被当成结论的部分。
