# 可用性自检：机器现在到底能不能用

本文说明 `GET /v1/readiness` 回答什么问题、每个检查项依据什么、以及为什么它**不是** `/healthz`。

---

## 1. 之前的问题：两个端点都不回答这个问题

| 端点 | 之前返回 | 它真正回答的问题 |
| --- | --- | --- |
| `GET /healthz` | 恒为 `{"status":"ok"}` | 进程活着吗 |
| `GET /v1/runtime` | 快照或连接错误 | socket 通不通 |

一台**急停锁存、没有启用地图、还有一步物理动作结果未知**的机器人，在这两个端点上都是 `ok`。业主读到 `ok`，合理地认为机器人没问题。这是本节要修的东西：系统从来没有对"我能不能用"给出过结论。

## 2. 为什么不是把 `/healthz` 改成严格模式

两个问题由不同的机器消费，动作也相反：

- **存活**问"要不要重启这个进程"。一台急停中的机器人是**一个正在正常工作的进程**——重启它等于因为安全功能生效而造成一次事故。
- **可用**问"要不要把它交给用户"。正在急停恰恰是不能交付的理由。

把两者合并，就是"因为机器人安全地停着，所以容器进入重启循环"的标准事故。所以 `/healthz` 保持存活语义（并保持恒为 `ok`），`/v1/readiness` 才是控制台和业主读的那个。

> 代码里有一段注释专门写这件事，因为它看起来像"只差把 healthz 改严一点"，而那样改是错的。

## 3. 报告长什么样

```json
{
  "ready": false,
  "summary": "机器人还不能用：还没有启用的地图，需要移动的任务会失败。",
  "nextId": "map",
  "checks": [
    {"id":"map","title":"场景地图","state":"action","blocking":true,
     "situation":"还没有启用的地图，需要移动的任务会失败。",
     "action":"让机器人完成一次巡检建图，然后在控制台启用地图。",
     "detail":"chassis:NAV_MAP_NOT_READY"}
  ],
  "unresolvedOutcome": 0,
  "language": {
    "provider": "deterministic", "modelConfigured": false,
    "vocabulary": "颜色（红/蓝/绿）+ 物品（杯子/水瓶/方块）+ 位置（收纳盒/托盘/交接区），中英文皆可",
    "note": "还没有配置模型，只认固定词表；超出词表的说法会被拒绝。"
  }
}
```

三种状态，**不是两种**：

| 状态 | 含义 |
| --- | --- |
| `ready` | 有证据地通过 |
| `action` | 有可以动手解决的东西挡着 |
| `unknown` | **没查成** |

`unknown` 刻意不是 `ready` 的一种。"我查不出来"和"这是好的"是两个答案，把前者报成后者正是这个仓库一路在拒绝的错误。

`ready` 只有在**每一个 blocking 检查都有证据地通过**时才为真。

## 4. 七个检查项与它们的依据

| ID | 依据 | 阻塞 |
| --- | --- | --- |
| `supervision` | 编排器的 `SupervisionStatus` | 是 |
| `robot` | `runtime.Info()` 是否回答 | 是 |
| `safety` | 机器人自报的 blocker 里有没有 `EMERGENCY_STOP` | 是 |
| `faults` | 机器人自己的 `robot.faults.v1` 故障台账 | 是 |
| `map` | 机器人自报的能力可用性（`navigation.navigate` 是否因 `NAV_MAP_NOT_READY` 被摘掉） | 是 |
| `reconciliation` | 执行记录里有没有结果未知的物理步骤 | 是 |
| （语言能力） | `ConfigStatus` | 否，单独展示 |

三条设计约束：

1. **能由机器人回答的，不问第二个人**。故障、地图、急停都取自机器人自报的 `Blockers` / 故障台账——在 Agent 侧重算一遍会制造"关于机器人自己硬件的第二种意见"，而两者分歧的时刻恰好是最需要一致的时刻。
2. **故障处理的句子用机器人自己写的**。`FaultReport` 里的 `userInstruction` 是控制台、模型和事故记录**共同引用**的那一句；在这里改写会成为同一建议的第四个版本。取不到时才退回一句"下一步做什么"（记录故障码并联系支持），而且那句**不假装知道故障含义**。
3. **没有软件路径能解除急停**，所以 `safety` 的行动项写的是物理动作，而不是给一个并不存在的按钮。

## 5. "没有模型"必须看得见

语言能力不阻塞——固定词表也能用。但它必须展示，因为从用户视角看：

> "它没听懂我" 和 "它没有配置模型" 长得一模一样，而只有后者是用户能修的。

在只有确定性解析器时，报告里直接写明**现在能听懂什么**（颜色 + 物品 + 位置，中英文），而不是让用户面对一句 `unsupported intent`。

## 6. 控制台怎么用

`web/onboarding.js` 的检查清单**只在浏览器算不出的地方**采用服务端的行（`CLIENT_CHECK_IDS` 之外的行：故障、结果未知、监督），并按 id 去重。理由和上面第 1 条一样：同一个问题不能有两个来源，否则清单会在服务端说有阻塞故障时显示"可以直接下指令"。

服务端报告一到就重渲染；**取不到时保留上一次的结论**而不是清空——因为"没查"本身也是一个新断言，而且是假的。
