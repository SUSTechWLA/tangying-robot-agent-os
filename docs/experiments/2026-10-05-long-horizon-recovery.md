# Gazebo 长程任务、多 Agent 诊断与续跑实测（2026-10-05）

## 被测问题

一条由真实模型编排、跨建图与操作的家庭任务，在执行中遇到一次只读服务通信失败后，能否由 Task、Ops、Recovery 协作定位到具体任务/步骤，完成限定范围的诊断与独立复验，再继续原批准计划？同时检验超过一分钟的安全暂停是否保留已完成进度。

本次是工程闭环实验，不是成功率统计。无故障基线、修复前的故障样本和修复后的故障运行分别保留。机器可读摘要见[证据清单](2026-10-05-long-horizon-acceptance.json)，代码因果链见[开发记录](../development/2026-10-05-long-horizon-recovery.md)，从启动到验收的完整命令见[脚本操作说明](long-horizon-harness.md)。

## 环境与自然语言输入

- 基础提交 `4b881a23a`，工作分支 `codex/gazebo-long-horizon-recovery`；运行二进制与修改源文件 SHA-256 在证据清单中固定。
- Gazebo `home_furnished`、同源 XLeRobot、ROS 2 / Nav2 / RGB-D；Robot ID `gazebo-home_furnished`。
- GOAL 使用配置的 OpenAI-compatible `deepseek-flash` 实际模型服务。Task 执行冻结计划，Ops 使用证据规则分类，Recovery 的无参数单工具只读调查采用确定性执行。三个 Agent 均有实际事件，不声称是三个独立模型。
- HTTP `127.0.0.1:8897` → Local Agent → 只读故障代理 `50162` → 真 Gazebo Runtime `50161`。模型密钥在主机私有配置中，不进入制品或 Git。
- 已有地图与标定是前置条件，任务本身重新移动建图并激活新地图；不是无图冷启动实验。

完整原句如下，四次完整运行使用同一句输入，保留各自模型生成的冻结计划：

> 依次执行以下完整家庭任务：读取整机标定状态；重新按家庭巡检路线完成SLAM建图并启用新地图；读取导航定位状态；从客厅出发，巡检卧室和卫生间，最后回到客厅；再从客厅出发，去厨房拿杯子，放进收纳盘，然后回到客厅；最后读取并报告当前地图和导航定位状态。每个地点都确认抵达，抓取和放置分别验证。

首次运行新建 `scan-45e7b02e0ec7`：226 帧、211 次配准、2 次回环、累计移动 23.466 米。事件 41 请求恢复、42 记录服务失败、46 Ops 定位、48 Recovery 计划、50 执行历史读取。事件 50 的 `executed=true, verified=false` 不能充当任务恢复成功；事件 51 保留最终失败。根因是恢复模型把原始家庭任务当成本轮诊断目标，认为巡检抓放尚未完成，因此拒绝结束诊断。

修复将恢复动作摘要设为当前目标，原任务只作上下文；单工具、无参数、目录与工具均为只读时稳定调用并结束，然后独立重读复验。带参数、多工具及写动作仍经过原有模型/审批机制。没有把“调查完成”改写为“物理任务完成”。

第二次运行新建 `scan-9297c28906a0`：233 帧、222 次配准、2 次回环、23.468 米。第 4 步恢复链已通过（事件 46/48/49/50/54 分别为 Ops、计划、已复验调查、重读、能力复验），但第 7 步返回客厅时在子动作派发前停止。Ground 将“没有导航能力”与“已声明但此刻不可用”合并为同一错误，并先于 Runner 原有的就绪等待返回；错误文本丢失了 blocker。事后 60 次只读采样有 2 次 `JOINT_FEEDBACK_STALE`、58 次可用，说明存在短暂反馈抖动；失败瞬间的具体 blocker 未保存，不能断言就是该码。修复保持传感器新鲜度门槛，只在物理派发前有界等待新能力快照，并保留真实 blocker。

第三次运行说明了固定测绘路线的起点限制：Gazebo 家庭 `survey` 按既定门中心序列分段直线采集，第一站是走廊；从卫生间直接切入该段会被障碍包络阻止。它不等同于在已保存地图上运行的全局导航。本轮通过正式 `robot.task` 返回客厅恢复路线前置条件，不改保护阈值，也不把这次失败归为通信问题。任意位置自主选取测绘路线入口仍是未覆盖能力。

历史部署另有 33 条结果未知的物理执行记录，其就绪门禁正确拒绝新任务。保留原目录与 `historical-readiness.json`，为实验建立独立 episode，只复制停止写入的同场景地图；未删除或伪造历史执行结果。无故障基线结束后，为完整故障运行显式初始化一次新世界。此后的四次完整运行及返回起点任务共用该世界，期间仅更新 Local Agent 与故障代理，**没有重置 Gazebo、手动移动杯子或改写任务记录**。返回起点属于操作员准备，不计入最终完整任务的自动恢复。

## 验收方法

脚本通过生产 Console API 创建、保存草案、批准、暂停及继续。故障代理仅在已启用故障标记且 `requestId` 以 `task-` 开头的指定只读服务调用中，在转发前返回一次 `UNAVAILABLE`；规划读取与物理技能不受注入。日志保留 `forwarded=false` 和原请求身份。

通过条件包括：真实 LLM 计划；终态成功；每个能力步骤有 receipt 与 verification；子物理步骤有命令后的观测和匹配原图摘要；导航 XY 误差不超过 0.08 米、偏航不超过 0.15 弧度；抓取、放置分别通过物理稳定证据；暂停持续超过 60 秒后续跑；恢复链中的 taskId、stepId、tool、planId、commandId 及事件顺序全部匹配。

只有以下完整链条和原任务成功同时存在，才将 `automaticTaskRecoveryObserved` 记为真：失败只读 → Ops 定位 → 新 Recovery 计划 → 自动历史调查且独立复验 → 相同命令身份的一次重读 → 能力复验通过 → 原计划完成。假 Runtime 的本地 gRPC 转发测试与本次真实 Gazebo 分开计数。

## 适用范围

本次不保证任意自然语言、任意故障、实机或机群均能自动完成。自动重试仅适用于冻结目录声明的只读能力，以及可分类的瞬时通信失败，每步骤最多一次且预算落盘。目录变化、持续故障、取消、未知物理结果均停止；恢复过程跨进程中断后要求审阅，不凭重启增加预算。需要新物理动作的恢复继续走审批和物理复验。

原始响应、图像、任务数据库、地图与运行日志保存在本机 `artifacts/acceptance/long-horizon-20261005/` 和对应 `artifacts/sim-stack/` 目录；它们未随 Git 上传。提交的摘要、失败摘录、相对路径与 SHA-256 支持核对本机制品，远端摘要不能替代缺失的原始图像或数据库。
