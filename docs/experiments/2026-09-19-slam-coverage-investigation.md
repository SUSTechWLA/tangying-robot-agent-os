# SLAM 地图覆盖率：一次被数据推翻的优化方向

**日期**：2026-09-19
**触发问题**：当前 SLAM 无法覆盖全部地图，探索常常以 `no_reachable_frontier` 结束，希望升级探索算法、把探索封装成工具类、对比多种实验，尽可能提升覆盖率。

**结论先说**：探索算法**不是**覆盖率的瓶颈。我用一个独立的闭环评测台测出，现有策略在理想执行下已能覆盖可覆盖区域的 **99%**；而真实地图只到 **62%**，缺口来自**建图层**——`occupancy_from_points` 只把"有点落进去"的格子标为已知，于是机器人早就看过去的空地因为中间没有落点而永远保持未知。在真实数据上量化：**44.3% 的未知格是机器人从自己走过的位姿就能看到的**，按"射线经过即自由"填上，可知率可从 **62.1% 升到 78.9%**，且不需要多走一米。

因此本文没有交付一个"更好的探索算法"，而是交付了**支持这个结论的实验台与证据**，以及被它拦下的三处错误改动。把一个已经 99% 的指标再优化一遍，是这个项目里最容易做、也最没有用的事。

## 一、先造尺子：闭环评测台

### 1.1 为什么单次决策的对比不够

`explore_target` 一次只选一个目标。此前所有改进都是从**一张冻结栅格上的单次决策**论证的，而这回答不了唯一重要的问题：*让机器人按这个策略一直跑下去，房子最后有多少进了地图？* 探索是闭环的——下一步去哪取决于已经看到了什么，而一栋房子的最后 20% 只能通过"先测完前 80%"才存在的路线抵达。

新增 `scripts/exploration_survey_benchmark.py`：

- **真值**：MuJoCo 房子的几何直接栅格化（`build_truth`），不依赖任何策略产出的扫描。
- **闭环仿真**：前向 60° 半角、3 m 半径、射线投射遮挡（墙后面看不见）；走过的地方按规划余量认证为自由（对应真实的 `_observed_travel`，没有它稀疏传感器下机器人连动都动不了）。
- **指标**：`mapped / coverable`。分母不是"所有格子"——封在柜子里的地板对任何可达位姿都不可见，不该由策略背锅。`coverable` 是"某个合法位姿能看到的真值格"的并集，只算一次。
- 同时记录行程、段数、决策次数：**用距离买来的覆盖率不是免费的**。

### 1.2 真值：两个必须先修掉的坑

**第一个坑**：一开始我用 8 份真实扫描求并集当真值，得到 25347 个占用格——而单次扫描只有 2756 个。原因是不同扫描的 SLAM 世界帧不同（`slam-session.json` 里的 `mapFromWorld`），直接叠加把墙糊成了一片。**并集是错的，必须按各自的世界帧对齐**，而我没有可靠的对齐信息，于是改用 MuJoCo 几何作为独立真值。

**第二个坑**：栅格化后起点不可达。原因是**机器人自己的底盘在同一份模型里**（`geom 1 BOX body=chassis`），被当成障碍物栅格化，把起点整个 7×7 邻域填死了。仓库里已有识别机器人本体的规则（chassis 及其所有子体），复用它。

修完：可达地面 12043 格，任何策略的上限 13916 格。

## 二、第一个实验结果：现有策略已经接近最优

```
baseline   覆盖  99.0%  行程 61.6 m  23 段  23 次决策
```

**98.7%–99.0%。** 这与我预期的"探索算法有缺陷"完全相反，也与实机 62% 相差甚远。

这个结果本身就是一个发现：**在理想执行下，frontier 策略几乎不会漏掉任何可覆盖的空间**。那么实机丢掉的三分之一，必然来自执行或建图，而不是目标选择。

### 2.1 排除"扫视不足"

我怀疑过是回头看的次数不够（真实 workflow 只在局部未知比例超过 0.25 时才扫视，且有上限）。加了真实度开关后：

```
realism=real   覆盖 98.7%   行程 61.6 m
realism=ideal  覆盖 98.7%   行程 61.0 m
```

两者一样。**扫视策略也不是瓶颈。**

### 2.2 传感器稀疏度：一个被我做错的实验

真机那次的点云只有 2255 个点。我加了每射线格以概率 p 被标记的模型，想复现 62%：

```
density=1.0   覆盖 99.0%
density=0.3   覆盖  1.6%   行程 0.0 m
density=0.15  覆盖  0.9%   行程 0.0 m
```

**这不是发现，是我的建模错误。** 单帧伯努利模型让初始地图碎到 `min_frontier_cells=8` 以下，`explore_target` 第一次就返回 `None`，机器人一步没走。真实地图是 167 帧累积的，不是单帧抽样。**这一组数字不能用来支持任何结论**，我把它留在这里是为了说明它为什么无效。

## 三、真正的瓶颈：建图层

停下来看地图是怎么写出来的。`robot/gateway/tangying_robot_gateway/map_pipeline.py:260` `occupancy_from_points`：

> Nav2 publishes the authoritative grid; this is the fallback for a map that has only a point cloud, and **it is honest about ignorance: a cell with no points at all stays unknown rather than being called free.**

实现确实如此：`columns/rows = floor((xyz - low)/resolution)`，**只有落进某格的 3-D 点才会让那格变成已知**。没有射线投射，没有"从传感器到回波之间的空白其实是自由空间"这一步。

后果正是覆盖率天花板：深度点云在远场和掠射角上是稀疏的，于是**两串点之间的地面永远保持未知**，无论探索策略多好。

### 3.1 在真实数据上量化这个修复的余量

取失败那次的终局栅格 `artifacts/maps/furnished-home/scan-6974b8f937e9`（未知 37.9%）和它的真实轨迹，沿轨迹每 0.1 m 取一个位姿，全向投射 3 m 射线（机器人会转头），统计：

```
真实地图 218x178，未知 14712 格（37.9%）
从轨迹上的姿态能看到的格子: 25011
其中仍然未知的: 6511 格 = 真实未知的 44.3%，全图的 16.8%
→ 按"射线经过即自由"填上，可知率可从 62.1% 升到 78.9%
```

**+16.8 个百分点，零额外行程。** 这些格子机器人**早就看过去了**，只是中间没有落点。

对照同期被测试挡回的探索策略改动：

| 改动 | 覆盖率收益 | 代价 |
| --- | --- | --- |
| 视点搜索 0.6 m → 传感器可达 3 m | +2.4%（frontier 格） | 无（决策 39 ms → 24 ms） |
| 簇上限 12 → 32 | A/B 中为 0，且让"已测完的房间"报告未完成 | 被回退 |
| 视点按可见性排序 | 无独立收益 | 被回退 |
| **建图射线填充自由空间** | **+16.8 pp（真实数据实测）** | 需改 `occupancy_from_points` |

方向是清楚的：**该修的是建图层，不是探索层。**

## 四、被测试拦下的三处改动（这一节比结论更重要）

我确实动手改了探索算法，三次，三次都被现有测试挡回来。记下来：

### 4.1 `gain` 从窗口和改成可见性计数 —— 回退

`test_of_two_equally_far_frontiers_the_one_that_hides_more_wins` 变红。那个 `FAR_REGION_FACTOR = 2.5` 是针对一次**真实失败**标定的（走廊尽头的浴室没建到图），改 `gain` 的语义会静默推翻那个结论。**收窄为只改视点选择。**

### 4.2 视点按可见性排序 —— 回退

`test_exploration_drives_at_the_frontier_until_the_room_is_measured` 变红：**已测完的房间仍报告有未完成的前沿**。说明多出来的簇不是更多覆盖，而是收工之后更多可去的地方。删除随之变成死代码的可见性原语（`_ray_index_table` / `_visible_unknown`）。

### 4.3 簇上限 12 → 32 —— 回退

诊断显示 16 个可达簇里有 12 个排在前 12 名之外，看起来"白捡"。实测 A/B 数字不变，且触发同一个"房间测完还在跑"的失败。**回退**，并在常量注释里写明为什么留着 12 以及需要什么样的测量才能重开这个决定。

### 4.4 唯一发布的探索层改动

**视点搜索从 0.6 m 扩到传感器可达距离**（`_nearest_via_tree`）。原来 `_nearest_traversable(..., radius_m=0.6)` 返回 `None` 就 `continue`，整簇被丢掉——而传感器能看 3 m。收益 +2.4%，决策耗时从 39 ms 降到 **24 ms**（k-d 树替代了每样本 625 次 Python 循环）。

## 五、效率与覆盖率的最终取舍

**结论：现阶段不要动探索算法。**

理由是有数字的：

1. 现有策略在理想执行下覆盖 **99%** 的可覆盖空间。探索层的头部空间不到 1 个百分点。
2. 数据里最大的单项收益在**建图层**：+16.8 pp，零额外行程。
3. 探索层改动尝试了三次，三次被测试证明是"收工后更多可去的地方"而不是更多覆盖。

**推荐的下一个动作**（按性价比排序）：

1. **`occupancy_from_points` 增加自由空间射线投射**：对每个回波，把传感器与回波之间的格子标为自由，回波所在格标为占据。预期可知率 62.1% → 78.9%（真实数据实测上限）。风险低、改动局部、有评测台可立即验证。
2. **重新评测后再看探索层**：建图变稠密后，连通分量会合并（我在真实终局栅格上测到 28 个连通分量、机器人只在其中一个里），那时 `no_reachable_frontier` 的触发条件会完全不同，探索层的取舍需要重新做一遍。
3. **不要**在覆盖率数字上继续用"未知格占比"这种口径——它把墙外、柜子内、传感器盲区都算进分母。本评测台的 `coverable` 分母才是可被问责的那个数。

## 七、我没有做完的部分

诚实列出，避免这份文档被当成比它实际更完整的东西：

- **没有交付"探索工具类"**。用户要求把 SLAM 探索封装成工具类。在测出探索层不是瓶颈之后，我认为先封装一个需要被替换的接口是错的投资顺序——但这是我单方面的判断，如果封装本身有独立价值（可测试性、可插拔），它仍然值得做。**未做。**
- **没有跑完多种策略的完整矩阵**。真正想验证的策略——连通分量感知（优先探索能合并连通分量的前沿）、乐观穿过未知以抵达孤岛——都**没有实现**。前者被建图层的发现降级（连通分量本身就是建图稀疏的产物），后者会推翻一条有测试钉住的安全不变式（"未知格永不作为可通行"），需要产品决策。
- **传感器稀疏度模型是错的**（§2.2），所以"建图射线填充"的收益目前只有**离线几何计算**的支持（§3.1），没有在闭环评测台里端到端验证过。要端到端验证，评测台需要按 `occupancy_from_points` 的真实规则（角度栅格 + 点泼溅）建模，而不是逐格伯努利。
- **真值仍是仿真的房子**，不是客户现场。链路长度、家具位置都是仿真单元的。
