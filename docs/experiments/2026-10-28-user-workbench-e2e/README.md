## 第一条用户任务与环境故障

浏览器输入：

> 先到卧室看看，再检查卫生间，结束后请回到客厅。每到一处都确认到位。

任务 ID：`task-e133310fd2f0b570d65e4dce`。真实模型生成 `robot.task`（路线 `卧室 → 卫生间 → 客厅`）及 `navigation.status`。草案冻结后由本次仿真测试在工作台批准。

`observe_scene` 完成并保存新鲜 RGB-D；`navigation.pre_position` 等待约 180 秒后收到导航 HTTP 503 / `NAVIGATION_NOT_READY`。任务终态为 `RECOVERABLE_FAILURE`，不是路线完成。系统将物理结果标为 `UNKNOWN_OUTCOME`，禁止自动重放，并通过运维/恢复读取诊断信息。

实际故障链：持久化 RTAB-Map SQLite 数据库损坏，启动报 `database disk image is malformed`；定位进程退出，缺少 map TF，Nav2 lifecycle 启动失败。此前 `navigation.status` 只凭已激活的 workflow 地图和里程计状态返回就绪，未覆盖真正导航依赖。设备故障与“错误显示就绪”的软件缺陷分别处理，损坏数据库和启动日志保留用于追溯。

随后还确认了另一处误判：Nav2 action 接口存在时，planner 与 bt_navigator 仍可能是 INACTIVE。驱动现在要求 controller、planner、bt_navigator 的新鲜 ACTIVE 状态；迟到的生命周期响应也不能刷新健康状态。

第一条任务供应商返回用量为输入 46,135、输出 1,503，总计 **47,638 tokens**。cached 输入 20,352 属于输入的子集，不重复相加；四次记录请求均 HTTP 200，其中一次模型决策被拒绝。批准至执行失败约 181.599 秒，主要消耗在导航就绪等待；模型四次记录时长合计约 11.647 秒。完整推导及口径见[独立审计](metrics-audit/README.md)。

## 维护、扫描与版本一致性

实验跨至 2026-10-29。损坏数据库约 26.94 GB，保留原件与 APFS 克隆；隔离副本恢复达到约十分钟预算后停止，存在未提交 journal，**不算修复成功**。后续另建 RTABMap 历元，保留 Gazebo 世界、里程计、原有 DenseMap 与标定。新图与旧语义坐标相容仍不代表覆盖相同：新图最初 9,537 个 known cells，卧室目标未知、卫生间在图外，整条路线因此尚未放行。

在原任务执行前的观测与事后记录中，底盘位置一致、双臂已接近收拢状态。但旧执行器可能先处理机械臂再请求导航，缺少完整 actuator 分支记录，不能推断 `NEVER_ACTED`。恢复后的 3.22 秒采样包含 53 个 odom、53 个 joint 和 37 个 suction 消息，线/角速度最大均为零、未抓持物体。按用户授权的**仿真维护测试**记录 `ABANDONED`，明确不恢复旧路径；再在工作台取消旧任务，保存 69 事件快照。首次执行失败仍保留在样本中；这不是自主恢复或实机操作员认证。

第一次工作台恢复扫描 `2d595bdf69824a8db8d965e4a041e961` 采集 25 帧、32,381 点和约一整圈转向，随后因 `'minStepM'` 失败。它来自本轮部署失误：新版 workflow 与旧版 survey 配置混用，不归为原始产品运行错误。真实里程近零，没有完成平移探索；配准轨迹折线约 0.0787m 不能当作实际移动距离。

修正部署方式为：备份完整已安装包、暂存当前 gateway/navigation 包、检查依赖与源码集合，在 Runtime/HTTP 停止期间安装并核对全部 114 个源文件，再启动消费者。Docker overlayfs 不支持本次目录交换，不能把服务停止窗口的完整安装说成文件系统级原子交换。整包回归首次 374/376，通过隔离测试中的场景环境变量后 376/376；保留原始两项失败，不修改断言。

第二次扫描 `1ba72d23a2f74a679aec11285775f2d4` 第一段采集 40 帧、56,210 点，实际平移约 0.566m，保存部分地图后续段因 `no_frames` 停止。第一段以 `no_reachable_frontier` 结束，尚有 712 个 frontier；末次受控旋转返回 `NAV_ENVELOPE`。续段唯一一次首采抛出 `InsufficientDepthError`，随后跳过初始扫描、读取空栅格而立即退出。不能将剩余 frontier 或没有首帧解释成全场景探索完成。设备最终线/角速度为零；未采集独立 contact 流，不能宣称零碰撞。

## 只读自然语言任务完整收尾

输入“查看当前机器人导航状态与已保存地图信息，不移动机器人。”，任务 `task-472131e5530f56e8b6ddd152`。模型一次决策冻结 `navigation.status → mapping.inventory → mapping.status`；工作台批准后各派发一次，约 309.779ms 后转为成功。SQLite 在线备份与 API 的 41 条事件逐条一致：39 为成功状态，40 为 `LOCAL_RUN_SUCCEEDED`，41 为匹配状态和版本的 `LOCAL_RUN_FINISHED`。三条 stepRun 均完成，调用、回执与复验身份一致。

供应商返回输入 9,956、输出 322、总计 10,278 tokens，调用记录时长 2.226 秒。本次查询返回的建图状态仍为失败；“成功读到失败状态”是正确查询结果，不是建图恢复成功。浏览器还发现只读工具误套搬运文案，已修正后重载核对。

三条实际创建任务共记录八次模型调用，供应商用量合计 91,557 tokens；其中首次任务的四次以 trace 为证据，启用独立日志后另四次 start/result 与 trace 逐 call 匹配。两条取消加一条成功是**最终状态分布**，历史仍有一次实际执行失败。物理任务成功为 0/1，只读任务成功为 1/1；样本数量不足以估计可靠性、延迟分位数或缓存优化收益。

## 当前桌边阻塞与后续验收边界

机器人最终底盘位置约 `[0.4324,-1.5948]`。同一停止姿态的新鲜点云中，底盘相机五个点进入 0.355m 保护圆，最近点 0.352190m，对应客厅桌南边；双臂已收拢。该采样是事后同姿态测量，不能冒充触发拒绝瞬间的点云。保护停止不等于发生接触，本轮缺少独立 contact 记录。

进一步发现探索规划使用 0.32m 足迹，运行控制检查 0.355m，存在 35mm 不一致。统一到更严格的操作包络后，旧图仍须按当前半径复验，不能沿用旧认证结果。这项修复避免继续选择净空不足的目标，不能改变过去轨迹或自动解除当前阻塞。

现有 `mapping.move` 包含起点完整保护圈，当前任意非零移动都会被拒绝；`recover_to_safe_pose` 只处理机械臂，Nav2 使用另一套足迹，不能作为等价的退让通道。当前保持停止，没有缩安全圈、清除实测障碍或在任务之间重置世界。后续需要独立设计并验收受控退让，再补齐卫生间的观测覆盖，按原始请求重做巡检和抓放。此前不能声明全流程稳定或实机放行。

## 统计与解释规则

1. 用户任务计数包括实际失败，不能用重测成功覆盖失败。尚未批准的草案与拒绝的规划独立统计。
2. 模型 trace 的调用尝试、实际 HTTP 请求、供应商返回的 token 用量不是同一指标。缺失用量标未知，不能补零；估计 token 不能作为账单。
3. 完整收尾检查持久化终态事件；只观察到 HTTP API 的 `SUCCEEDED` 不足以证明后续收尾事件已经落盘。
4. 物理指标校验有限数值、机器人/时钟/坐标系身份、命令与观测时间先后。缺失证据明确标记未验证，不能把 NaN、错误身份或缺失传感器当成通过。
5. 本次是已知家庭场景单机器人任务；地图恢复、控制器状态及定位来源须随结果记录，不外推为陌生环境、多机无线协同或厂商实机验收。
