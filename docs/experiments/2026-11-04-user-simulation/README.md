# 2026-11-04：工作台自然语言四房间巡检

本报告区分实际 Gazebo 执行、软件回归与实验者修复。原始数据位于 `artifacts/acceptance/user-sim-20261104-001/`；私有配置、会话凭据、二进制和整库不提交。此实验使用已建地图，不是陌生环境探索、实机验证或多机器人协作验证。

可提交且已逐文件校验的[完整证据包](evidence/README.md)约 8.6 MB，包含四轮原始审计无损归档、[量化指标 CSV](evidence/campaign-metrics.csv)、执行期轨迹、72 张原始 RGB/深度图、版本与测试日志。包清单为 `evidence/PACKAGE.json`，独立复核结果为 `evidence/VERIFICATION.json`。图像来自原捕获存储，没有重新拍摄或补造。

## 任务与预先确定的验收条件

通过 Chromium 浏览器在工作台填入原句并点击“生成任务”，核对计划后点击“批准物理动作”：

> 先检查标定，再依次到厨房、卧室、卫生间巡检，每到一处都确认到位，最后返回客厅并确认任务完成。

必须有 `calibration.get` 成功；路线保持 `kitchen → bedroom → bathroom → living_room`；每站导航和独立 `verify_arrival` 均有自己的命令与新观测；任务成功和 `LOCAL_RUN_FINISHED` 持久收尾；API、SQLite、trace 和观测身份一致。逐站观测相对已登记目标的位置误差不超过 0.08 m、偏航不超过 0.15 rad。全部快照与已声明图像逐字节校验。指标以 [只读审计工具](tools/README.md) 为准，未报告 token 不填零。

“巡检”在此指到达指定房间观察位、获取新观测和核对位姿；不代表已完成语义异常识别。里程计是系统测量，不是独立真值。没有连续接触传感器证据时，不宣称全程无碰撞。

## 首轮失败：语义地图与导航地图恢复不完整

任务 `task-3b03351306d5b7df4835f7be6e69d577`：模型生成 9 项能力计划，标定检查成功，首次厨房导航失败，任务进入 `RECOVERABLE_FAILURE`。`audit-001/` 在后续操作前冻结 64 条事件与 3 份采集；原始请求、API/SQLite 事件与捕获身份核对一致，任务验收失败。

精确路径为 `rev-1-cap-02-navigate_00`：`navigation.pre_position` 成功后，导航在约 0.924 s 返回 `NAV2_ACTION_ENDED`。Nav2 日志显示无法从约 `(0, -1.25)` 规划到厨房 `(2.05, 3)`。实验启动只复制了 workflow 语义地图，没有恢复 RTAB-Map 原生库；导航库仅 3 个工作节点。语义地点存在不意味着 Nav2 已经拥有可达路径。

系统没有继续余下动作。运维 agent 记录异常、提出只读调查并禁止自动重试。首次“取消任务”被 `LOCAL_CANCEL_BLOCKED` 拒绝：未知结果必须先对账。禁止通过清库、改任务版本或直接重新批准绕过这一边界。

恢复时备份新库，复制经过资源/传感器版本核对的 10-30 原生库，通过 RTAB-Map `load_database` 服务加载，不重置世界、机器人或家具。恢复后 856 个工作节点、96,045 个已知栅格；只读 `ComputePathToPose` 到厨房得到成功状态和约 6.059 m 的路径。模式切换也暴露了启动配置与真实 ROS 参数不同步的问题，随后恢复 mapping 并增加实测模式报告。恢复命令、失败的参数设置和前后快照均保留在 `slam-recovery/`。

独立 ROS 采样首点晚于首任务收尾约 1.126 s，因此不能估计首任务行程或声称失败过程中零运动。之后 UTC 05:16:59.309–05:17:09.049 的 20 个不同时间戳样本报告零速度、位姿不变；这是当时记录的静止状态，不是独立物理急停认证。

UTC 05:28:12 通过新增工作台表单记录 `ABANDONED`，明确注明 Codex 仿真核查、命令终态/资源授权和采样依据。恢复接口返回 `STEP_ABANDONED / canResume=false / requiresReconciliation=false`，随后通过 UI 取消旧任务。原 `STARTED` 执行状态、失败事件及首次被拒绝的取消请求仍保留。新 trace 的对账列表与摘要包含后续结论，旧未知结果诊断不消失。

## 第二轮失败：运行中的管理状态查询过期

任务 `task-a0fc09863e3a4be4f14ef61945b72877` 使用同一原句，重新生成并批准 9 项计划。模型前三站使用中文房间名，按预先已有的语义别名规则规范化后顺序完全相同；本轮不是路线解析错误。

第一段导航 UTC 05:29:55.883–05:30:31.883 后返回 `NAVIGATION_OBSERVATION_LOST`，任务再次进入 `RECOVERABLE_FAILURE`。`audit-002` 保存 64 条事件、3 份采集和明确失败收尾。标定前置成功，但 8 项导航/到位确认尚无确认，严格验收失败。

新增诊断在事件 41/42 已完整贯穿 Nav2、gateway、gRPC 和 Go：当时相机年龄约 600 ms、位姿约 37 ms、RTAB-Map 约 2124 ms，SLAM 模式及三个生命周期查询过期；约 201 ms 后这些查询恢复。代码和并发实验确认管理查询共用默认 ROS 回调组存在阻塞风险；现场未逐个测量回调时长，不能断言所有延迟都由同一回调引起。修复隔离回调组、区分过期与明确停用，并沿用有界零速度等待；不增大新鲜度阈值，不让终态失败自动重放。

相比首轮，工具效果声明缺口已消失，trace 仅保留真实的 `STEP_OUTCOME_UNKNOWN`。7 个唯一模型调用报告合计 91,005 tokens（输入 85,653、输出 5,352，缓存输入 47,744 已包含在输入中）。首轮对应 6 个调用、75,146 tokens；失败成本同样保留，不计入成功任务成本后再隐藏。

本轮独立采样覆盖 39.559 s 执行窗口，76 个不同时间戳样本、最大间隔 0.648 s，采样 XY 折线长 3.4943 m，最大报告速度约 0.200 m/s；结束位置约 `(0.249, 2.229)`。之后 9.789 s/20 点报告静止，Nav2 另有取消成功/停止日志，Runtime journal 无活动资源授权。通过 UI 明确记录 `ABANDONED` 后取消；不把这次移动解释为“从未执行”。

软件修复将管理轮询和 ROS 客户端放入独立回调组，过期状态标为 STALE、真实非激活状态标为 INACTIVE。原 3 s 新鲜度和 2 s 零速度等待上限未增加。并发测试实际堵塞默认回调组，确认独立参数查询仍可完成；另验证明确停用立即失败及终态命令不能复活。

- 前端最终 599 项通过，`go test ./web` 通过；独立 Chromium 验证对账控件标签/可访问名称及输入，不提交额外对账。
- ROS 导航最终 66 项通过，含真实 ROS callback-group 并发测试；gateway/HTTP 103 项、service 37 项及失败日志重启重放用例通过，部分测试范围重叠，不相加当独立实验次数。
- 审计工具 39 个合成回归通过；文档/教材 68 项通过。软件 fixture、实际模型调用、实际 Gazebo 运动分别统计。

## 本轮发现和修复

授课可配合[双地图、未知结果与对账案例](../../../book/updates/2026-11-04-gazebo-failure-and-reconciliation.md)，逐项区分设计意图、软件证明和实际物理证据。该补充不覆盖已发布教材 3.3.0 的冻结内容。

| 问题 | 处理与权威边界 |
| --- | --- |
| 顶栏永久显示“正在读取”，失败后仍提示批准 | 按真实连接、服务目录与任务状态显示，不把“连上”当作运动就绪 |
| 任务规划等待无解释 | 等待说明、`aria-busy` 与防重复提交；不编造模型进度 |
| 未知动作只有阻止提示，无可操作的对账入口 | 恢复卡片逐步选择结论并填写核查者/依据；不默认成功，不自动恢复或批准 |
| 对账可针对非未知或活动步骤 | App 在锁内拒绝 active/queued/只读/完成/已对账步骤；SQLite 原子条件仅接受 STARTED，保留原状态 |
| 对账依据在普通恢复视图不可见 | 返回原步骤状态、结论、认证来源、时间与依据；结论不替代完成证据 |
| 执行事件缺少 `mutatesWorld` | 两条事件发布路径都从可信目录保存副作用与安全等级；未知扩展保持未知，旧事件不补造声明 |
| Nav2 只返回泛化错误 | 保留 Nav2 原始状态、错误码/消息及命令身份；跨 Python/gRPC/Go 有界传递诊断，失败仍为失败 |
| RTAB-Map 运行模式与启动字段可能不符 | 只读查询实际 ROS 参数，未知/过期时阻止运动，不把旧配置当实时事实 |

## 可复现采集

详见 [工具说明](tools/README.md)。每轮批准前保存显式 `adapter=gazebo` 的遥测；任务结束后以未存在的新目录运行 `collect_task_audit.py`，同时指定四站与 `--required-capability calibration.get`。采集器只 GET 和只读 SQLite，不执行机器人动作，保留自己的代码副本和文件 manifest。

不得覆盖 `audit-001`、`audit-002` 原始失败。代码与界面变更分别见[导航恢复记录](navigation-recovery.md)、[工作台状态与对账入口](ui-recovery-notes.md)和[回溯合同](../../architecture/task-traceability.md)。
