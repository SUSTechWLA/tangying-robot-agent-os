# 躺营 v0.5.0

> 2026-09-11。标签、最终提交、逐项 CI 结果和制品校验值见本版 [GitHub Release](https://github.com/SUSTechWLA/tangying-robot-agent-os/releases/tag/v0.5.0) 的 `release-manifest.json`。

v0.4.0 交付了任务全过程回放，但它只覆盖**能选中**的那些任务。本版把回放补成"任何时候都能完整复盘"：任意历史任务都能打开，空缺处给出原因而不是留白，并且修掉了三处会让验收脚本误判的缺陷。

软件版本与实机放行仍是两项独立结论。`v0.5.0` 不代表已完成真实 XLeRobot 的现场验收，也不替代现场 `PHYSICAL_GO`。

## 获取准确版本

```bash
git clone --branch v0.5.0 https://github.com/SUSTechWLA/tangying-robot-agent-os.git
cd tangying-robot-agent-os
make setup
make build
./bin/robot-agent version
```

`VERSION`、Python 项目、内置 Runtime、MuJoCo 运行时、ROS 包与适配器运行时均为 `0.5.0`，由 `tests/test_repository.py::test_release_version_matches_distributed_components` 逐处校验。线协议版本 `1.0`、MCP 工具集与 `robot.profile.v1` 不随软件版本改动。

## 本版范围

### 1. 任意任务都能到达

回放的入口此前只有任务记录列表，而列表**只显示最近 50 条、且不显示任务编号**。结果是：更早的任务在界面上完全无法到达，而需要追查的失败任务恰恰常常已经落到窗口之外。开发人员手里即使有编号（来自日志、工单或另一台机器）也没有地方输入。

| 入口 | 行为 | 解决什么 |
| --- | --- | --- |
| 记录列表 | 按更新时间倒序，每条都带可复制的任务编号 | 编号是日志、工单与回放标题共同的锚点，没有它就无法把界面里的记录和日志里的编号对上 |
| 按任务编号回放 | 粘贴任意 `task-…` 编号直接打开 | 窗口之外的任务只有一个入口，就是编号；服务端 `GET /v1/tasks/{id}` 本来就能取到任意单条记录 |
| 只看 | 全部 / 失败或中断 / 已取消 / 成功 / 进行中 | 失败任务占比高时，先筛出问题任务再逐条复盘 |
| 显示更多 | 每次再展开 50 条 | 超出部分继续展开，不静默丢弃 |

"找不到任务编号"（记录已被保留策略清理）与"服务暂时无法读取"（连接问题）是两条不同的提示：前者说明这个编号不存在，后者说明稍后重试有意义。打开失败不会把面板留在上一个任务上。

### 2. 空缺处说明原因，而不是留白

回放面板的每一段在数据缺失时都可能变成空白或 `—`，而空白无法区分"没问题"和"没查到"。本版把这几处改成明确的解释：

- **执行链路为空**时按任务状态给出不同结论：`CREATED`/`READY`/`AWAITING_APPROVAL` 等尚未开始的状态显示"任务尚未开始执行"，而不是此前一律显示的"失败发生在任务分解或目标绑定阶段"。把等待批准的任务报成分解失败，会把开发人员引向一个不存在的缺陷。已取消、已成功却无调用记录、正在执行、终态失败各有对应说明。
- **没有任务说明记录**时（该任务早于说明记录功能，或记录已按保留策略清理）直接说明原因，不再显示 `—`。
- **回放标题列出任务编号**，否则一张截图无法对回它们属于哪个任务。

### 3. 不再为空缺记录反复请求

任务没有说明记录时 `/experience` 会一直返回 404，而轮询每轮都重新请求，网络日志里堆满同一个永远不会成功的请求。现在终态任务得到 404 后会记住这个结论并停止重试；点"重新读取"仍然可以强制重新请求，因为部署升级后记录可能出现。

## 修复

- `scripts/check-task-replay.cjs` 有三处会误判健康系统的缺陷：
  1. **单击滚动到底部不会加载视口之外的缩略图。** 证据缩略图按 `loading="lazy"` 懒加载，一次跳到底部会让中间跳过的图片永远不进入视口，脚本随后在"等待全部图片解码"上超时——而图片本身完全正常。现在逐步滚动后再等待。
  2. **`REPLAY_TASK` 按列表可见文本查找。** 窗口之外的任务永远选不中，于是"验证历史失败任务"这件事本身无法执行。现在通过编号查找框打开，并断言回放标题里的编号与请求的一致。
  3. **把"必须有工具步骤"当作通用契约。** 在分解阶段就失败、确实没有任何工具调用的任务是合法结果，却会被判为失败。现在要求面板解释这种空缺；需要强制断言有步骤时用 `REPLAY_EXPECT_STEPS=1`。
- `page.waitForFunction(fn, { timeout })` 的第二个参数是**传给页面函数的实参**，不是选项对象。两处等待因此一直落在 30 秒默认值上，超时配置从未生效；已改为三参数形式。

## 发布身份与本轮验证

```bash
make build && make lint && make test
```

- Go：全部测试包通过，`gofmt` 无输出；`make generate-check` 确认生成物未漂移。
- Python：**1393 passed、35 skipped**（跳过为主环境缺少可选 RoboCasa 依赖）。
- Web：**270 passed**，含新增的历史窗口筛选、编号查找、缺记录不再重试、回放编号与状态化空缺说明的单测。筛选按四个互斥类别划分全部状态，并有测试断言四类合起来覆盖所有任务，不会有任务落在类别之间的空隙里。
- 浏览器验收：`node scripts/check-task-replay.cjs` 在四类真实任务上断言通过——最新的未开始任务、窗口之外的失败任务、窗口之外的成功任务、以及分解阶段就失败因而没有任何工具调用的任务。以其中一个任务为例，面板列出 3 个工具步骤、15 条事件并在回放里直接给出失败原因与错误码；另一个任务的回放给出 18 项严重不一致（14 个写步骤没有任何采集可以证明），这正是排查需要的结论。

所有结果来自软件仿真与隔离进程，**没有实机、现场制动距离、标定精度或长期可靠性结论**。

## 升级与回滚

- 从 v0.4.0 升级无需数据迁移：本版只改控制台前端与验收脚本，任务、事件、观测与恢复状态的存储格式未变。
- 本版不新增接口，只使用既有的 `GET /v1/tasks`、`GET /v1/tasks/{id}`、`/experience`、`/observations`、`/recovery`。
- 回滚到 v0.4.0 会失去编号查找、状态筛选与新增的解释文案，已有任务的执行语义不变。
