# 长程任务与多 Agent 故障闭环更新（2026-10-05）

## 目标与版本

基于 `4b881a23a`，在 Gazebo `home_furnished` 跑模型编排的建图、巡检、抓放与返回任务；同时验证暂停恢复、故障调查和原任务继续。分支为 `codex/gazebo-long-horizon-recovery`。实际任务、结果和制品摘要见[实测报告](../experiments/2026-10-05-long-horizon-recovery.md)。本文记录代码因果链与边界，历史失败不会改写成成功。

## 发现与修复

| 问题 | 根因 | 更新与回归 |
| --- | --- | --- |
| 能力任务失败，监督 Agent 收不到实时工具事件 | `tasks.AppendEvent` 只通知状态变迁；Capability Executor 依赖账本桥接 | 通知 `TOOL_ACTIVITY`；legacy 直接发布与账本桥接共享 `eventId`，live/replay 均去重 |
| Provider 调用、等待或完成复验出错，回放缺具体原因 | 只有 legacy 子任务写 `CAPABILITY_FAILED` | 所有执行错误写工具、步骤、命令、阶段、错误码、是否写世界及未知结果标记；取消后仍限时保存失败证据 |
| 相同 stepId 的不同任务故障串线 | 累加键不带 taskId，诊断落到“最近任务” | 累加、finding 和恢复计划保留 taskId；同任务不同步骤的同名工具各有调查身份 |
| 自动诊断只有“已执行”，没有独立复验 | 生产 `recoveryExecutor.Verify` 未接线 | 仅目录 `read_only` 且实际成功完成的诊断，可独立重读最后成功工具；保持任务上下文。只证明诊断读取可用 |
| 真仿真中读完历史后仍拒绝结束诊断 | 恢复观察继承完整家庭任务目标；配置的模型把“诊断完成”误当作“原任务完成”，因后续巡检未执行而停止 | 当前恢复目标改为目录动作摘要，原任务仅作背景；单个无参数、安全只读工具使用确定性调用与结束，其他动作保留模型。独立复验仍必需；三种上下文模式、带参数工具和共享数据保护均有回归 |
| 短暂读取中断使长任务中止 | Capability 执行器没有可核对的恢复等待路径 | 执行 Agent 等待同任务、同工具、同步骤的新 Ops 诊断与 Recovery 调查，独立读复验后只重试该读取一次 |
| 进程重启能获得额外读重试机会 | 初版只在失败之后检查预算 | 派发前查询持久恢复标记；恢复中断后保守停止并要求审阅，不凭新进程重置预算 |
| 故障调查或目录读取可能长期占用恢复消费者 | RPC 缺 deadline，调查使用进程生命周期 | 目录读取最多 30 秒；单轮诊断最多 45 秒；执行侧等待最多 60 秒。取消之后只读调查可能持续到该上限，不能产生写动作 |
| 相对 `--data-dir` 启动失败 | SQLite 把 `file://artifacts/...` 当作 URI authority | 普通路径先绝对化再转义；真实 SQLite 覆盖相对多层目录、空格和 `?/#/%`、关闭重开、独立内存库 |
| 只读断连在问题列表仍显示 `UNKNOWN_OUTCOME` | Ops 在只读分支修正了重试权限，但沿用了面向物理动作的默认分类文案 | 只在已知只读域将通信失败细化为 `TRANSIENT`、其余未分类读取设为 `READ_ONLY_FAILURE`；全局物理分类不变，新增 11 个分类案例 |
| 回放把九分钟建图显示为“只读、派发 0 次、耗时 0” | 回放只理解旧子步骤事件，未读取 `CAPABILITY_*` 生命周期 | 按冻结调用身份投影能力事件、receipt 与契约复验，镜像活动不重复计数；物理子步骤继续检查 RGB-D，未知能力显示“效果未声明”；真实失败样本与 7 个新增前端测试验证 |
| 后台诊断让已停止任务的总耗时和结束时间持续增长 | 回放使用 `updatedAt`，其包含终态后的 Ops 事件 | 耗时和两处起止渲染共用最后一次真实终态转换时刻；保留原始更新时间，覆盖恢复后再次终态、旧历史回退与仍在执行任务 |
| 任务记录页运行中误报新观测不在历史中 | 事件持续轮询，但观测索引只在工作台轮询；手动重新读取也没有刷新索引 | 两个回放页面按原 2 秒周期更新索引，手动刷新等待观测读取；保留隐藏页限流、旧请求和任务切换保护，未放宽证据缺失检查 |
| 到达卫生间后准备返程，Ground 报“没有移动能力” | 单次 `Available=false` 被等同于能力未声明，早于 Runner 的就绪等待退出且丢失 blocker | 已声明能力最多 2 秒只读刷新（100ms 间隔），保留阻塞原因；缺失能力、取消、协议/profile/机器人/目录变化仍拒绝；保持 Runtime 反馈新鲜度阈值与物理派发门禁 |

## 自动恢复契约

只对冻结目录声明不改变世界的能力调用，以及 gRPC `UNAVAILABLE` / `DEADLINE_EXCEEDED` 开启此通道。参数错误、权限拒绝、任意未分类错误、物理写、物理复验失败均不进入它。每个持久步骤最多一次恢复重试。

```text
CAPABILITY_CALL
  → CAPABILITY_READ_RECOVERY_REQUESTED（预算先落盘）
  → CAPABILITY_FAILED（只读、结果非物理未知）
  → ops.anomaly_detected（ops，taskId/stepId/tool 绑定）
  → ops.recovery_plan（recovery，新 planId，调查轨迹含 stepId）
  → ops.recovery_executed（execution.read-history，自动、执行且独立复验通过）
  → 重新核对机器人和冻结目录
  → CAPABILITY_READ_RETRY（原 requestId，attempt=2）
  → CAPABILITY_RECEIPT → CAPABILITY_VERIFIED
  → 原计划下一步
```

恢复 Agent 仍不持有物理执行端口。继续原计划的权限来自此前批准的冻结计划，不来自恢复模型。任务侧等待不到匹配诊断、诊断失败、目录改变、取消或预算耗尽，就停止；不会创建替代任务或重跑已完成的物理步骤。只读调查成功不能清除未知物理动作，也不能代替物理对账。

`TANGYING_AGENTS=task` 可关闭监督：正常执行和物理门禁不变，但此依赖 Ops/Recovery 的读故障恢复不启用。GOAL 使用配置的真实模型，Ops 分类与 Recovery 单工具调查可以是确定性的；三个 Agent 参与不等于三个独立 LLM 调用。

## 复现工具

- `scripts/evaluate_long_horizon.py`：仅经 Console API 创建/批准/暂停/继续任务，保留原始响应和 SHA-256；独立核查能力契约、RGB-D 摘要、导航误差、抓放物理复验及自动恢复事件的严格顺序。
- `scripts/gazebo_read_fault_proxy.py`：只允许 loopback Gazebo；查询目录确认服务只读；只在带 `task-...` requestId 的指定服务调用转发前注入一次断连，不影响规划期读取和物理技能。
- `tests/install/test_long_horizon_eval.py`、`test_gazebo_read_fault_proxy.py`：验证误报成功、跨步骤/旧计划证据、超时清理、暂停继续、并发故障次数、流式取消和大图像转发。

验收器额外经过反例审查：拒绝同一步成功后又失败、恢复后新确认引用旧版本/旧时刻证据、抓取与放置验证不同物体、跨任务的恢复事件。冻结房间序列逐段匹配导航/到达目标；单纯到达次数不足以通过。普通只读观察允许传感器声明范围内的新鲜缓存，物理动作及其新完成验证必须使用派发后的证据。旧完成步骤跨暂停保留其原证据，不强制重做动作。

手动部署另发现 Console 本地地图根目录没有随 Runtime 自动继承：机器人服务仍正确使用当前地图，但网页列出默认目录里的旧场景。交付配置显式设置 `TANGYING_MAP_ROOT`，与标准启动器保持一致；任务期间不为刷新页面而重启仿真。

## 验证范围

真实 Gazebo 与本地 gRPC 假 Runtime 测试分开计数。成功是指定场景、指定任务和一次瞬时只读故障的结果；没有认证任意自然语言、任意故障、真机或跨主机自主修复。持续通信故障、未知物理结果、急停和需要新物理动作的恢复仍保持停止/审批边界。
