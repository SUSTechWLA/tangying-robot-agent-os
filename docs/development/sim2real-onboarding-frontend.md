# 实机前置工作：标定与建图的前端方案

用户要在真机上跑通自然语言任务。在那之前有一串前置工作，目前大多只能靠命令行和文档完成。本文给出这些前置工作的前端方案，并回答相机部署与标定策略的问题。

**状态：本文是方案，不是已完成功能的说明。** 文中标注了哪些数据是实测的、哪些是待实现的。

## 1. 两个 RGB-D 到底有没有相交区域（按当前模型实测）

先纠正一个前提。用当前模型实测两台相机在机器人周围 2.0 × 2.5 × 1.2 m 体积内的可见性（按 `cam_fovy` 与相机世界位姿计算视锥，相机沿 −Z 观察，已用 `overview` 相机反向验证约定）：

| 相机 | 安装位置 | 观察方向 | fovy | 可见采样点 |
| --- | --- | --- | --- | --- |
| `head_depth`（头部） | `head_tilt_link`，世界 z=1.185 | 工作区前下方 | 70° | 由当前模型计算 |
| `base_depth`（底盘） | `chassis`，世界 z=0.195 | 前下方 15° | 58° | 由当前模型计算 |
| **默认姿态两者同时可见** | — | — | — | **0（0%）** |

当前装修家庭默认安装没有共同可见体积。两路相机的外参标定走注册服务提供的已知底盘运动法；相机仍分别承担工作区感知和前向足迹/障碍感知。

> 修正记录（2026-09-13）：底盘相机为家庭导航重新安装到低位前视，当前默认姿态的 `shared_view_volume()` 结果为 0。没有把旧安装的共享视野数字继续套用到新模型。

**当前模型两个 RGB-D 没有相交区域是预期结果**：

- 真机安装如果有不同高度和俯角，应重新计算交集并选择靶标法或运动法；
- 默认家庭模型不放共同靶标，使用已知底盘运动解决双 RGB-D 外参；
- 两条臂的末端与相机之间没有共同视野仍属于手眼标定问题，不是双 RGB-D 外参问题。

这三种情况的处理方式不同，因此前端第一步应该是**把几何事实显示给用户**，而不是先改硬件。

### 1.1 建议的部署策略

不要为了让两台相机互相看见而牺牲各自的本职视野。分别对待两种标定：

| 标定 | 目的 | 需要什么视野 |
| --- | --- | --- |
| **手眼标定**（相机 ↔ 末端/夹爪） | 抓取：把"看到的物体"变成"手臂能到的位姿" | 头部相机必须能看到夹爪夹持点附近的区域。这是抓取精度的**决定性环节** |
| **双 RGB-D 外参** | 融合两路点云、统一到同一坐标系 | 两者需要共同可见的**标定靶**，而不是共同可见的工作区 |

部署建议：

1. **头部相机保持工作区视角**（抓取主力），手眼标定需要夹爪附近可见靶标。
2. **底盘相机保持低位前视**，服务于足迹和障碍观测；当前家庭模型为 z=0.195、前下方 15°、58° fovy。
3. 若改用共同靶标安装，必须重新计算 `shared_view_volume()`，并把可用交集、靶标尺寸和重投影残差写入该型号的标定验收。
4. 默认家庭模型使用运动法：让底盘执行已知直线和旋转，利用两路点云与里程计求解外参，并以残差门禁判断结果。

第 4 条是关键备选：**手眼标定 + 运动法外参**可以在没有共同视野的情况下完成两机标定，代价是依赖里程计精度。

## 2. 建图覆盖指标与补拍指引

用户第一次建图时最需要的是"我拍够了吗？哪里还缺？"这需要一个可计算的指标，而不是让人凭感觉走。

建议的指标集（全部可以从 RTAB-Map 的占据栅格与位姿轨迹算出）：

| 指标 | 定义 | 给用户的话 |
| --- | --- | --- |
| **已覆盖面积占比** | 已观测自由栅格 / 该房间可通行区域估计 | "厨房已覆盖 78%" |
| **未知边界数（frontier）** | 已知自由区与未知区相邻的栅格簇数量 | "还有 3 处没走过" |
| **位姿覆盖均匀度** | 轨迹点在房间内的分布，识别"只在门口转了一圈" | "厨房只走到门口，请再往里走 2 米" |
| **回环确认** | RTAB-Map 是否检测到回环、地图是否收敛 | "已识别回环，地图已闭合" |
| **深度有效率** | 深度图有效像素占比（玻璃、反光、过近过远都会掉） | "这一段的深度数据不足，请放慢速度重拍" |
| **运动模糊/过快** | 相邻帧位姿跳变超过阈值 | "刚才移动太快，这一段需要重拍" |

**补拍指引**就是把这些指标反解成动作：给出**下一个该去的位姿**（最近的 frontier 中心）和**怎么去**（"从当前位置向前 2 米，转右 90°，慢速通过"），而不是只报一个百分比。

前端应当：

1. 顶部一条**总进度**：五个房间各自百分比 + 整体是否可以进入任务阶段；
2. 三维地图上把**未知区域**画成半透明灰、**已覆盖**画成实体、**待补拍区**高亮描边；
3. 每次停下时给一句**下一步动作**，并允许"跳过这个房间"；
4. 结束时给**就绪判定**：覆盖达标 + 回环闭合 + 深度有效 → "可以开始执行任务了"。

## 3. 稠密地图用 WebGL / three.js 展示：可以，而且已经是现有技术栈

**结论：可以，而且不需要引入新框架。**

- `web/package.json` 已经依赖 `three@0.180.0`，`web/webgl_scene.js` 就是打包后的 three.js 场景（console 的三维视图、数字孪生、构件边界都在用它）；
- 控制台**已经会渲染观测点云**（`pointCloudViewData()`、`#view-cloud` 按钮、`drawObservedCloud()`），数据来自 `scene.reconstruction.v1` 的 `points`/`entities`；
- 因此稠密 SLAM 地图展示是**在既有渲染管线里增加一种图层**，不是新建一套。

建议的渲染方案：

| 图层 | 数据 | three.js 实现 |
| --- | --- | --- |
| 稠密点云 | RTAB-Map 导出的点云（或 RTAB-Map 数据库导出的 PLY） | `THREE.Points` + `BufferGeometry`，按高度或来源着色；分块加载避免一次上传几十万点 |
| 占据栅格 | Nav2 代价地图 / RTAB-Map 栅格 | 一层贴地的 `THREE.Mesh` + 半透明纹理，未知区域用单独一层灰 |
| 机器人轨迹 | 位姿序列 | `THREE.Line`，回环处加标记 |
| 待补拍区 | frontier 簇 | 高亮描边或呼吸色块 |
| 房间标签 | 语义位置表 | `CSS2DRenderer` 或已有标签层 |

性能上要注意三点（现有场景已经踩过）：

1. **点数分级**：在线预览用降采样点云（几万点），需要细节时再加载全量；
2. **不要每帧重建**：地图是增量到达的，按块 append 到既有 `BufferGeometry`，避免整块重传；
3. **控制台受严格 CSP**，脚本必须是 classic script（不能有 `export`），新增渲染代码要沿用 `webgl_scene.js` 的打包方式。

## 4. 还需要哪些前置工作的前端

按"用户必须在真机上完成、且现在只能靠命令行"的顺序：

| # | 前置工作 | 为什么需要前端 | 建议交互 |
| --- | --- | --- | --- |
| 1 | **设备连接与自检** | 用户要知道"线插对了没、两个串口认到没、相机出图没" | 一屏四张卡：左臂总线、右臂总线、头部相机、底盘相机，各自"已识别/未识别"+ 重试 |
| 2 | **安全确认** | 标定与建图都会让机器人动 | 勾选式清单 + 实体急停位置示意；未确认不允许继续 |
| 3 | **整机标定**（舵机） | 已在 `scripts/calibrate_guided.py` 实现，20 步 | 把该脚本的 `status()` 负载直接渲染成卡片流：进度条、当前步骤、示意图、上一步/跳过 |
| 4 | **手眼标定** | 决定抓取精度，用户必须摆靶 | 摄像头实时画面 + 靶心检测框 + "请把标定板放在夹爪正前方 30 cm"，自动采 15–20 个位姿 |
| 5 | **双 RGB-D 外参** | 融合两路点云 | 同上；若无共同视野则走运动法："请让机器人慢速前进 1 米并转 90°" |
| 6 | **SLAM 建图** | 本文第 2 节的指标与补拍 | 三维地图 + 覆盖率 + 下一个该去的位置 |
| 7 | **地图管理** | 多张地图要选、要删、要看是哪次采的 | 地图列表：名称、创建时间、覆盖率、回环状态、缩略图；设为当前 |
| 8 | **任务就绪检查** | 让用户明确知道"现在可以下指令了" | 一张总清单：连接 ✓ 标定 ✓ 地图 ✓ 安全 ✓ → "可以开始"；缺项直接跳到对应页面 |
| 9 | **紧急停止入口** | 前端操作期间随时可用 | 常驻按钮 + 键盘快捷键；调用的仍是后端急停，不是前端的"停止按钮" |

第 8 项是把前面所有工作串起来的那一屏，也是用户最终判断"前置工作做完了没有"的唯一依据，建议优先做。

## 5. 第一版前端已实现：开始使用前

`web/onboarding.js` + 工作台顶部的“开始使用前”面板已经上线，是本方案的第 1 号和第 8 号两项目标。它把运行时的现有数据翻译成**一张按阻塞程度排序的清单**：

- 顶部一句话就是**下一步该做什么**："下一步：安全确认 —— 确认机器人一个手臂范围内没有人、没有杂物，实体急停开关在手边。"
- 进度条显示 `1 / 5 项已完成`；
- 每项给三行：**情况**（现在怎么了）、**要做什么**（一句可执行的话）、可选按钮“去处理”跳到对应页面；
- 状态分成"需要处理 / 状态未知 / 已完成"三档并配颜色，**急停排在最前**。

五项目标与判定来源：

| 项 | 判定来源 |
| --- | --- |
| 连接机器人 | 控制台已有的连接状态 |
| 安全确认 | 急停状态 + 操作员的明确确认（**不假设**） |
| 整机标定 | **优先**读注册标定服务 `calibration.get` 的结果（`revision` / `document.cameras` / `cameraCount` / `camerasMeasured`）；读不到时回落到运行时发布的 `calibration_revision` / `calibration_source`，`simulation` 来源会被明确指出"不是这台机器测出来的" |
| 相机标定 | 标定文档里的相机数量与是否实测 |
| 场景地图 | 建图覆盖报告（覆盖率、逐房间、回环、深度有效率） |

两条硬规则写在代码注释与测试里：

1. **没有观测到的状态一律报"状态未知"，绝不默认正常。** 对一台物理机器人说错"可以开始"是这块屏幕唯一不能犯的错——有一条测试专门断言空输入永远不会被读成 ready。
2. **不把不同问题混为一谈。** 地图读不到时不会说"请先连上机器人"（机器可能已经连上了，只是没有导航栈），而是让用户点重新检查或去开发诊断。有一条测试守着这条文案。

页面加载**不发起任何 API 请求**（控制台对 `file://` 页面有"零请求"契约，测试会数请求数），地图状态由“重新检查”按钮读取；这也是当前唯一的已知取舍。

## 6. 建议的实施顺序

1. **任务就绪检查页 + 设备连接自检**（第 1、8 项）：先把"缺什么"显示出来，后面每一项才有落点；
2. **整机标定向导接前端**（第 3 项）：后端已完成并测试，只差渲染 `status()`；
3. **SLAM 建图页 + 覆盖指标**（第 6 项）：需要先实现覆盖指标计算；
4. **手眼标定与外参标定**（第 4、5 项）：需要先确定相机部署（第 1 节），并且**必须真机验证**；
5. **稠密地图图层**（第 3 节）：在既有 three.js 场景里加点云与栅格图层。

## 7. 需要真机才能确定的事

以下三点在仿真里无法定论，需要你在真机上确认后我再据此实现：

1. 真机上两台相机的实际安装位置、俯角与视场（决定第 1 节的部署调整方案）；
2. 底盘里程计的精度（决定第 4 条"运动法外参"是否可行）；
3. 深度相机在桌面工作距离上的有效像素占比（决定覆盖指标的阈值）。
