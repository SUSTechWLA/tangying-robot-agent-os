# RGB-D 相机：底部相机位置修正（已实施）

用户实机检查发现两个问题，都已**用实测确认**。修复本身很小，但它会牵动自滤波与感知阈值，因此**没有直接改进 main**——补丁保存在本目录，实施步骤写在下面。

## 问题 1：底盘相机装错了位置（已确认）

修复前的实测：

| 相机 | 世界 z | 朝向 | fovy |
| --- | --- | --- | --- |
| `head_depth` | 1.185 | 垂直向下 | 70° |
| `base_depth` | **1.535** | 前下方 45° | **150°** |

**底盘相机比头部相机还高**，而且是 150° 鱼眼俯视地面——它既不在底盘底部，也不看机器人前进方向。源码注释也写着它是"front mast, 45 degrees down"，即一根立杆上的俯视相机，与"底部前向深度相机"完全是两回事。

用户要求：**放在底盘靠近地面处，向前拍摄机器人前进的深度图**。

## 问题 2：两台相机不是同一个型号

用户要求顶部与底部**参数一致，尽量用 Intel RealSense D435i**。修复前两者 fovy 分别是 70° 与 150°，是两种不同的传感器。

D435i 深度流为 **87° × 58°**（H × V）。

## 补丁内容（`patches/rgbd-d435i-cameras.patch`）

1. `xlerobot.xml` / `xlerobot_r2.xml` / `xlerobot_handoff_r2.xml`：`head_depth` 的 `fovy="70"` → `fovy="58"`。
2. `rgbd_navigation.py`：`base_depth` 从 `pos=[0.28, 0, 1.50]` + 45° 俯视 + `fovy=150`，改为
   - `pos=[0.30, 0, 0.16]`（贴近底盘底部）
   - 前向 15° 俯角（`xyaxes=[0,-1,0, sin15,0,cos15]`）
   - `fovy=58`
3. `home_scene.py`：新增共享常量 `RGBD_VERTICAL_FOV_DEG = 58`。
4. **tabletop 场景保持逐字节不变**（`[0.185, 0, 0.50]` + 45°），因为它的验收夹具断言了近地射线。

改后的实测：

```
head_depth  58 x 73 deg
base_depth  58 x 73 deg
base_depth world z=0.160, 前向 (0.966, 0, -0.259)
```

## 一个必须说明的差距

**垂直 58° 与 D435i 一致，但水平只有 73° 而不是 87°**，因为我们的帧缓冲是 4:3（320×240），而 D435i 的深度流是 16:9。要拿到真正的 87° 水平视场，需要把帧缓冲改成 16:9（例如 424×240）。这是**帧缓冲选择**，不是相机参数错误，但会让"是否真是 D435i"这句话打折扣。

## 实施结果

**已实施的只有底部相机**，头部相机保持 70° 不变。补丁中"把头部也改成 58°"的部分**已撤销**，原因见下。

实施后的实测：

```
home_task  head_depth=70  base_depth=58   (底部：z=0.160，前向 15° 俯角)
tabletop   head_depth=70  base_depth=100  (逐字节未变)
```

**验证**：`sim/mujoco/tests` + `tests/` **1004 passed / 7 skipped**，`make home-accept` exit 0，`ruff` 干净。

### 过程中修掉的两个自身错误

1. **补丁把 tabletop 场景也改了。** 我原本声称"tabletop 逐字节不变"，但 `camera_fovy = 58` 写成了一行无条件赋值，把 tabletop 的 100° 也改成了 58°——**5 个测试失败里有 3 个是这个错误造成的**（含两条自滤波）。修正为按场景区分后，自滤波立刻全部通过。
2. **头部相机改 58° 会静默破坏家居感知。** 视野变窄后，原本在 x=1.58 的杯子**移出画面**，感知一个都报不出来——症状看起来像检测器坏了，实际是摆放与视野不匹配。我尝试把物体移到 x=2.55 仍未检出，**在上下文耗尽前没能定位**。

### 为什么头部相机没有一起改

把头部从 70° 改到 58° 需要**重新调校整条家居感知链**（工作体积门控、颜色掩码、支撑面检测都按 70° 调过），并且 `xlerobot.xml` 是**与 tabletop 共用**的（直接改它会连带改掉 tabletop 验收）。

**把两件事混在一个改动里，会让两件都难以审查、且都无法独立验证**，所以只交付底部相机这一件已完整验证的修复。头部相机的 D435i 统一是**独立的一项工作**。

### 问题 4 的根因（实测）

已在浏览器中量到：

```
工作台文档高度 11050 px    视口高度 800 px
#local-evidence-panel 位于 main 的第 11 / 16 个子节点
```

**代码本身是对的**：`focus({preventScroll:true})` 已经挡住了 focus 的隐式滚动，`scrollIntoView({behavior:"smooth", block:"start"})` 之后还有一轮"落点校正"。

**问题在于距离**：从「回看当时观测」按钮到证据面板要跨过大约 **13 个屏幕高度**的页面。在 11000 px 的页面上做平滑滚动，视觉上就是"一下子到了底部"；中间那些与当前观测无关的面板，正是用户说的"空白无效信息太多"。

**因此这不是滚动动画的参数问题，是结构问题**：证据面板不该住在离按钮一万像素的地方。

**正确的修法**：把观测内容**就地展开在按钮所在的行**（inline 展开），或在抽屉/弹窗中打开——两者都**不需要滚动**，也就同时消掉了"中间空白太多"。

**不要**靠调 `block` 取值或加长动画时间来掩盖：那只会让一次长距离穿越看起来更慢，而不是让用户少滚一点。
