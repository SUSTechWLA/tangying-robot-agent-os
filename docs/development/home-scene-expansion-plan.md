# 家居场景扩充：从 1 个物体到完整任务（实施方案）

把现在的家居场景从**只有 1 个可操作物体**扩充到能支撑一次完整、自然的自然语言任务。方案是按实际代码结构写的——每一处都标到函数，因为改动点集中在四个地方，彼此耦合。

## 0. 现状（已核实）

| 事实 | 位置 |
| --- | --- |
| 5 房间家居（客厅/走廊/厨房/卧室/浴室），有墙、沙发、床、灶台、岛台 | `sim/mujoco/assets/xlerobot_home.xml`（66 行） |
| 任务夹具**不是 XML 里写的**，而是运行时按代码构建 | `sim/mujoco/tangying_sim/rgbd_navigation.py::_extend_home_task_spec()` |
| 现有夹具：任务台、蓝色收纳盒（含无材质颜色的接料底板）、红杯子 | 同上 |
| 可操作物体目录只有 1 项 | `home_scene.py::HOME_TASK_OBJECTS` |
| 感知是**颜色分割**（红掩码 + 蓝掩码），限制在一个固定的厨房工作体积内 | `sim/mujoco/tangying_sim/rgbd_perception.py::HomeTaskRgbdPerception._detect()` |
| 物体初始位置在运行时设置 | `rgbd_runtime.py::_configure_home_task_scene()` |
| 校验 | `home_scene.py::validate_home_task_model()`、`validate_home_task_navigation_model()` |

**感知刻意不读仿真真值**：它只用 RGB-D 契约（颜色掩码 + 反投影点 + 标定的工件体积）。这条设计不能破坏，否则"仿真里能过"就不再说明真机上有意义。

## 1. 改动点（四处，必须同步）

### 1.1 场景：`_extend_home_task_spec()`

在现有台面/收纳盒之外，增加 15–20 个物体。每个物体需要：

```python
body = spec.worldbody.add_body(name="<slug>", pos=[x, y, z])
body.add_geom(name="<slug>_geom", type=mujoco.mjtGeom.mjGEOM_BOX,   # 或 CYLINDER/SPHERE
              size=[...], rgba=[r, g, b, 1.0], contype=1, conaffinity=1)
body.add_free_joint(name="<slug>_free")   # 与 red_cup_free 同构
```

**为什么用自由关节**：抓取是物理过程，物体必须真的能被夹起、能掉、能被验证放置。固定几何体会让"抓取成功"变成一句无法证伪的话。

建议物体（**按颜色可分割性挑选**，见 1.2）：

| 类别 | 物体 | 建议颜色 |
| --- | --- | --- |
| 杯子/瓶子 | 蓝杯、绿杯、白瓶 | 高饱和纯色，彼此区分度高 |
| 碗/盘 | 橙色碗、黄色盘 | |
| 水果 | 红苹果、黄香蕉（用胶囊体近似） | |
| 日用品 | 蓝色书本、绿色盒子、红色罐子 | |
| 干扰物 | 若干灰色/棕色物体 | **故意用低饱和色**：感知应当忽略它们，这本身是一个可测的性质 |

**台面尺寸要复核**：现有 `home_task_table_top` 是 `size=[0.75, 0.25, 0.33]`，即 1.5m × 0.5m 的台面。摆放 15–20 个物体需要**加长台面或增设第二层置物架**，否则物体初始位置会互相穿透。

### 1.2 感知：`HomeTaskRgbdPerception._detect()`

当前只有 `red` 与 `blue` 两个掩码。扩充方式：

1. **抽出颜色表**，不要在函数里堆 if：

```python
COLOUR_MASKS = {
    "red":    lambda r, g, b: (r > 1.55*g) & (r > 1.55*b) & (r > 45),
    "blue":   lambda r, g, b: (b > 1.25*r) & (b > 1.12*g) & (b > 35),
    "green":  ...,
    "yellow": ...,
}
```

2. **每个掩码做连通域聚类**（现有 `colour_clusters()` 已可用），把簇的质心投到 `_support_z` 之上。
3. **保留工作体积门控** `(x∈[1.05,3.10], y∈[3.15,4.65], z∈[0.62,1.30])`——物体必须摆在这个体积内才可被感知，这是"commissioning limit"，不是语义查询。
4. **类别判定只靠颜色 + 尺寸档位**（如"小而圆 = 杯子"），**不要**引入形状分类模型：真实 RGB-D 适配器之后要用学习到的检测器实现同一接口，现在引入过强的形状假设会让接口失真。

**关键测试**：加一个"干扰物不可见"的用例——灰色/棕色物体**不应**产生任何观测。这证明感知不是"看见什么就报什么"。

### 1.3 目录：`HOME_TASK_OBJECTS`

现在是 `(("red-cup", "red_cup", "red_cup_free", "cup", "red"),)`，格式为 `(语义 ID, body 名, free joint 名, 类别, 颜色)`。逐个补齐。

**语义 ID 是适配器面向的目录项，位姿仍在执行时从任务 RGB-D 帧发现**——这条注释在源码里，扩充时不要违反。

### 1.4 运行时：`_configure_home_task_scene()`

现在只摆 `red_cup_free`。改为**从一个位置表批量设置**：

```python
TASK_OBJECT_PLACEMENTS = {
    "red_cup_free":  (1.82, 3.68, 0.85),
    "blue_cup_free": (1.95, 3.72, 0.85),
    ...
}
```

位置要用 `_set_free_body_position()` 统一设置，并在 `mujoco.mj_forward` 之后确认**没有互相穿透**（加一条断言：任意两个物体初始距离 > 各自半径之和）。

## 2. 自然语言任务

现在 README 的任务是单物体闭环：`从客厅出发，去厨房拿红色杯子，放进蓝色收纳盒，然后回到客厅`。

扩充后建议给出**同样自然、但需要多物体推理**的任务，例如：

> 从客厅出发，去厨房把红色杯子和蓝色瓶子都放进收纳盒，再把黄色盘子放到台面右边，最后回客厅。

拆成的工具步骤应当覆盖：`navigate_to`（跨房间×3）→ `observe`（识别多个目标）→ `pick`（×2）→ `place`（×2）→ `verify`（每个放置一次）→ `return`。

**不要**为了好过而把任务写成工具的逐条翻译；任务描述要自然，步骤由 Agent 自己拆——这才是在测链路而不是测脚本。

## 3. 验收顺序（每步都要能独立失败）

1. **场景自检**：物体数、无穿透、都在工作体积内 → `validate_home_task_model()` 扩展
2. **感知自检**：每个彩色物体各被检出一次，干扰物零检出
3. **单物体回归**：现有红杯子闭环**必须仍然通过**（防止扩充破坏已有行为）
4. **多物体任务**：完整 NL 任务跑通，工具调用序列与观测/证据数量符合预期
5. **失败路径**：故意把某物体放到工作体积之外，Agent 应当报告"看不到"而不是失败重试到超时

## 3.5 第一次实施尝试的结果（重要，下次从这里开始）

按本方案写的第一版代码**已回滚**，但过程中的发现必须保留——它们把下一次的工作量缩小了很多。

### 已验证可用的部分

1. **一张权威物品表是可行的**：把「语义 ID / slug / 类别 / 颜色 / 几何 / 尺寸 / rgba / 质量 / 初始位置 / 是否干扰物」放进 `home_scene.py` 的单张表，由场景构建、目录、运行时摆放、测试四处共同读取。这条结构没问题，值得照做。
2. **净空检查立刻抓到了真实缺陷**：13 个物体里 `red_cup` 与 `olive_tray` 的间隙是 **−3.5 mm**（互相穿透）。这正是方案预测的失败模式——**这类检查必须写，不能靠目测**。调整托盘位置后间隙变为 **+13 mm**。
3. **工作体积检查通过**：全部物体都在 `x∈[1.05,3.10], y∈[3.15,4.65], z∈[0.62,1.30]` 内。
4. **加宽台面是必需的**：原台面 1.5×0.5 m 放不下这些物体，扩到 **1.9×0.64 m**（`HOME_TASK_TABLE_SIZE = (0.95, 0.32, 0.33)`）后坐标仍然落在工作体积内。
5. 模型能正常构建：**13 个物体 body** 全部进入 MuJoCo 模型。

### 未解决：改完之后感知一个物体都看不到

`test_home_task_runtime_observes_only_rgbd_task_fixtures` 从"能看见 red-cup 与 kitchen-bin"变成**观测为空集**。连**未改动的静态 `kitchen_bin` 也看不见了**，说明这不是新物体的颜色或位置问题，而是**场景改动影响了感知链路**。

已经排除的：导航本身成功（`navigate(kitchen) == True`）。

**下一步应当从这里查**（按嫌疑排序）：

1. **台面加宽后相机视野/支撑面提取的变化**：`_detect()` 里 `_support_z` 由"木质水平面"的深度直方图众数决定，台面从 1.5×0.5 变成 1.9×0.64 会改变这个分布，`red = red & (z > support_z + 0.075)` 这条门控可能整体失效。
2. **机器人是否与加宽后的台面发生碰撞**：厨房 waypoint 是 `(2.20, 3.35)`，台面 y 范围变成 `[3.53, 4.17]`，机器人与台面边缘只差 0.18 m，可能挤压了相机与工件之间的视线。
3. **加宽台面是否与既有家具/墙体相交**，导致仿真状态异常。

**调试入口**：`HomeTaskRgbdPerception._detect()` 接收 `RgbdFrame`；直接打印 `valid` 掩码数量、工作体积内的点数、`red`/`blue` 掩码数量与 `_support_z`，就能区分是"看不到"还是"看到了但被支撑面门控滤掉"。

## 3.6 多物体自然语言任务：实测结果（重要）

场景已扩到 4 个可观测物体（红杯/蓝杯/绿杯/黄盘），但**多物体自然语言任务目前跑不通**，而且有两种不同的失败方式。以下都是实测。

### 失败方式一：指令被静默截断（最危险）

请求：

> 从客厅出发，去厨房拿红色杯子放进蓝色收纳盒，**再拿蓝色杯子放进蓝色收纳盒**，然后回到客厅

结果：**任务报告成功，但只搬了红杯子**。实测证据——确认步骤与单物体流程**完全一致**（`observe → navigate → resolve → plan_grasp → pick → verify_grasp → place → verify_place → navigate_02 → verify_arrival_02`），产出中只有 `object_id: red-cup`，没有任何第二次 pick/place。

**这是最危险的一种**：用户要求搬两个杯子，系统搬了一个还报成功。它比直接失败更糟，因为**没有人会去检查**。

### 失败方式二：退化成纯导航任务

请求：

> 从客厅出发，去厨房**把红色杯子和蓝色杯子都**放进蓝色收纳盒，然后回到客厅

解析结果 `intent` 为：`action: home_route`，且 `object/source/destination` 的 `category` **全为空字符串**，`routeRooms: [living_room, kitchen, living_room]`。随后以 `NAV_STEP_LIMIT: home route has no movement segments` 失败。

原因在 `agent/intent/parser.go`：物体正则要求**每个子句都有动词**：

```go
homeObjectAction = regexp.MustCompile(`(?:拿|取|抓|拾)(?:(红色|蓝色|绿色|红|蓝|绿)的?)?(方块|积木|杯子|水杯|杯|瓶子|水瓶|瓶)`)
```

`把红色杯子和蓝色杯子都放进…` 以 **把** 开头，没有 拿/取/抓/拾，因此物体整体未被解析。

### 由此得到的三条结论

1. **颜色词表已经包含 蓝色 与 绿色**（正则里有），所以蓝杯/绿杯**可以**被命名——缺的不是颜色。
2. **每个子句必须有动词。** 现有多子句解析（`parseClause` 逐段解析）在**每段都能独立解析**时才成立；`把…和…都…` 这种并列结构不行。
3. **缺少 黄色 与 盘子/碟子** 等词，所以黄盘目前**无法被自然语言指代**。

### 修的方向（不属于场景工作，属于 intent 层）

| 缺口 | 修法 |
| --- | --- |
| 并列结构 | 支持 `A 和 B 都…`，或**明确拒绝**并要求"请逐步说明"（现有 `clarification("未能完整理解所有步骤…")` 已有此文案，但没有覆盖到这条路径） |
| **静默截断** | 最关键：解析出的意图数量少于子句数量时**必须澄清**，不能只执行第一条 |
| 词表 | 补 `黄色`、`盘子/碟子`、`碗` 等 |

**在 intent 层修好之前，不要对外声称支持多物体任务。** 场景侧已经准备好 4 个物体与一致的观测，缺的是语言层。

## 4. 不要做的事

| 诱惑 | 为什么不做 |
| --- | --- |
| 让感知读 MuJoCo body 位姿 | 会摧毁"仿真里能过说明真机上有意义"这个前提；现有源码注释明确禁止 |
| 用 RoboCasa 的物体资产直接搬进来 | 许可证与网格依赖需要单独评估；且它不解决感知接口问题（见下） |
| 把任务写成固定工具序列 | 那是在测脚本，不是在测 Agent |
| 为了通过而放宽颜色阈值 | 真机上阈值会更难，放宽只会把问题推到实机 |

## 5. 关于 RoboCasa365（另一条轨道，不在本方案内）

`datasets/robocasa/` 里 vendor 了 RoboCasa365（365 任务、2500+ 厨房场景、3200+ 物体），但：

- `robosuite` 与 `torch` **都没有安装**；
- 它使用**自己的 env 栈**，不跑我们的 runtime，因此**不会**自带我们的感知契约、工具层、安全监督、证据链与标定关联。

要用它，需要为整套 runtime 写一个适配层，工作量远大于本方案。**建议把"能否装上并加载一个场景"作为独立的可行性验证先做**，不要与本次家居扩充混在一起。
