# 探索操作身份与部分地图语义

本次针对上轮工作台验收中暴露的边界做软件修复。原始现场、桌边保护停止与两次部分扫描结果见[原实验](../experiments/2026-10-28-user-workbench-e2e/README.md)；下面的软件回归不证明旧场景已经脱困，也不证明全场景覆盖或物理巡检成功。

## 避免取消后来启动的探索操作

原先客户端先读 `mapping.status`，再无条件调用 `mapping.cancel`。两次请求间若旧操作结束、新操作已经启动，取消会错误作用于新操作。现在 `mapping.cancel` 接受可选参数 `expectedOperationId`，在操作状态锁内比较当前 `operationId`，不匹配时返回 `OPERATION_ID_MISMATCH`，不触发取消、不释放资源。检查、取消标志更新和返回状态快照使用同一锁。多段探索的 `sessionId` 可变化，因此必须绑定不变的 `operationId`。

原有无参数取消继续可用，以兼容显式操作员停止入口；需要防止误取消的自动工具必须提供期望 ID，不能只依赖事先的状态查询。此次没有修改机器人驱动的硬停止或租约检查。

启动续建会在驱动移动前核验基础地图与坐标系。若该核验失败，必须释放此前取得的机器人 reservation；原实现只在读取标定失败时释放，导致无效 `baseMapId` 后下一次有效请求可能一直收到 `ROBOT_BUSY`。现在失败路径清理续建引用并释放 reservation，不创建新 operation，重试可以正常启动。

## 建立租约后才让工作线程运行

原 `ServiceRegistry` 先调用 handler，再设置 operation lease，而建图 handler 内部已经启动线程；在并发调度下线程可能先采集甚至移动。现在建图启动、复用、完成和手动移动入口使用请求绑定的 invoker，在同一 Workflow 锁内执行 handler 与租约设置。新线程必须先通过该锁并检查取消及租约过期；设置失败时在其越过该门之前取消。无租约的操作员入口保持原语义。其他服务没有使用共享请求上下文，也未改变其行为。

带租约的 `mapping.move` 和 `mapping.finish` 必须绑定已有 `operation_id` 和 `operation_owner_id`，否则 `OPERATION_ID_REQUIRED` 拒绝；防止移动未经监督或结束保存时接管原操作所有者。依靠空 operation ID 的旧 Agent 能力调用需要调整；无租约人工操作不变。带已有 operation ID 的 `mapping.start`、`mapping.build` 和 `mapping.ensure` 不能用作续租，请使用 `mapping.status`，避免先切图后发现身份或租约失效。

多段探索切换阶段的 state 为 `exploring`，原 `start` 检查遗漏该状态；如果旧 reservation 刚释放，新请求可能替换 operation 和 provider。现在明确拒绝活跃探索，并等待旧 worker 真正退出后才允许新启动；启动响应在同一锁内生成，避免返回后来操作的 ID。

## 运动故障后的部分地图留存

本轮 `survey-001` 在收到 `MOTION_NOT_READY` 后终止，终止快照有 87 帧和 85 次配准，但没有发布地图。故障码可被 `_fault_of` 识别；真正的阻塞是驱动异常时设置的内部停止事件随后又被建图保存入口当成用户取消。恢复路径吞掉保存异常，导致原故障和保存失败无法区分。

现在标记仅由内部运动故障发起的停止：先等待运动线程结束，再允许在不清除停止事件的情况下保存满足原有测量、配准和位移要求的部分地图。用户取消、暂停、租约失效及无法确认来源的停止仍拒绝保存；写入发布前在锁内再次检查。故障时 `faultSalvage` 记录发布成功或保存失败及原因，不把原始运动故障改成成功。此修复不能追溯性恢复旧进程中未持久化的帧；重新部署前应保留现场并评估旧版本手动保存的语义，不能把它当作完整扫描。

此前 UI 在 `failed` 状态下允许点击“完成并生成地图”，但手动 `finish` 会清除停止事件并以正常地图保存，误报 `partial=false/completed`。现在人工重试沿用本会话的原故障代码与消息；缺少可信故障身份则拒绝，成功保存后仍为 `failed`、`partial=true`。它保留停止事件及原租约；受监督的抢救必须绑定已有 operation/owner，不能利用无身份请求新建租约。保存失败的次级原因单独记录，不覆盖原故障；人工取消胜过未发布的保存。

## 已登记家庭巡检路线的起点接入

本轮 survey002 从卧室附近 `[-1.5076, 3.3290]` 启动，原实现直接往首个走廊点插值，在 `[-1.0916, 2.9324]` 附近触及门角保护区并触发 `NAV_ENVELOPE`。控制器安全拒绝是正确的；这不是机器人未检测到障碍。已保存的 `scan-ede46f57012d` 是故障部分地图，原失败保持。

家庭参考场景明确绑定 commissioning 元数据和十站路线。对该**默认登记路线**，先将实测起点投影到距当前位置不超过 0.6m 的唯一登记线段，再沿登记的边回到首站，最后执行原完整十站。共线交叉处将登记的节点分割为图顶点，避免越过走廊后再折返；超出距离、歧义、非法数值或无法构建图均拒绝。实际问题起点对应的路线前缀为 `[-1.0916,3.35] → [0,3.35] → [0,3]`，随后才是原首站 `[0,1.85]`。客厅默认起点不增加前缀；自定义路线和非家庭机器人不改变。

这个接入只是对**已知参考场景登记路线**的提示，初始到投影点不是已观测自由空间证书；每一段仍必须经原 bounded driver 和实时 0.355m 保护检查。它没有适配任意陌生环境，也没有修改、清空或扩张地图。目标点是否可以导航仍需当前地图和定位证据，实景风险与本体安全由各自驱动承担。

独立软件 fixture 定向10项、相关组合199项通过，Ruff通过；固定1000个随机起点的独立几何复核覆盖接入之后的登记边。首次fixture错误地用布尔值替代commissioning元数据，出现9项失败；随后lint发现两处pairwise及导入顺序，均已修复，原终端输出未重定向，不伪造原日志。现有可复验命令、哈希和最终输出保存在本轮 `verification/commissioned-approach/`，真实重新建图与巡检由主实验单独记录。

## 区分操作终止和覆盖情况

续段无足够新平移时，若由于 `no_reachable_frontier`、`no_progress` 等阻塞，旧版本仅因上一张地图存在就返回 `completed`。现在保留旧地图和停止原因，同时对阻塞返回 `failed`；因预算或限时正常结束仍保留既有 `completed` 操作状态，避免改变客户端的操作终止合同。

地图 `slam-session.json` 的 `partial` 字段现在按探索结果记录：观测栅格的可达前沿尚未耗尽则为 `true`，而不是因为地图保存成功就写 `false`。`frontiersExhausted` 的范围仍只限本次非盲观测栅格；即使为 true，也不证明整栋建筑或全场景已覆盖。旧地图与旧实验不回写；依赖旧错误 `partial=false` 的消费者应按新语义处理。

## Gazebo 点云保护、观测等待和证据

受控移动在每个脉冲前使用同一份点云快照做保护检查。Gazebo 的点云源时刻须有效且推进，相对于新鲜里程计源时刻不能落后超过 1 秒或超前超过 0.25 秒；里程计接收年龄不得超过 0.5 秒。无效、倒退或不满足时效时停止。几何计算和等待就绪锁后，发布器还要检查原点云与里程计的期限、当前授权、取消和动作 deadline，避免用过期快照发布非零速度。

若发布器**仅**因 `RGBD_NOT_READY` 拒绝，系统发送零速度并在已有观测等待预算内重取观测、重新运行完整保护检查；间歇恢复不能无限重置同一等待预算。其他就绪阻塞、权限失效、超时和来源故障保持停止。实际预算以运行时配置与动作证据的 `holdBudgetSeconds` 为准。拒绝证据包含同次快照的来源、时刻、位姿、半径、侵入点数及最近点；它描述保护决策，既不是独立碰撞传感器，也不是自由空间证明。Gazebo 源时刻比较假设桥接数据共享仿真时钟，不能证明实体传感器时钟同步或硬实时行为。

## 独立试验与失败留存

`SIM_STACK_GAZEBO_ASSETS_ROOT` 允许将家庭场景准备和 Gazebo 导出放入指定资产根目录；默认目录不变。隔离试验还须分别配置镜像、端口、ROS domain、运行目录和机器人数据目录，单独设置资产根目录不足以隔离执行权威或数据库。生成的 Compose 覆盖文件不持久化导航令牌和宿主机专用导航 URL；令牌仍需按既有运行方式安全提供。

`scripts/build_sim_map.py` 出错时记录原异常、最后状态和取消结果；只有查询确认同一 operation 仍活跃才提交携带 `expectedOperationId` 的取消。状态查询或取消失败会被单独记录，不覆盖原始异常，也不表示机器人已停止；操作员应继续通过实际运行时和设备证据核对状态。
