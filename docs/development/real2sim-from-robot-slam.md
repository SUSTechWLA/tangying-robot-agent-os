# Real2Sim：用机器人自己的 SLAM 建图生成仿真场景

真机上只有一件事可做：**让机器人走一圈，用 SLAM 建图**。所以 Real2Sim 不应该是"下载一个数据集然后把机器人放进去"——那是在**别人的房子**里仿真。正确的路径是：

**机器人自己的 SLAM 测绘成果，就是仿真场景的来源。**

这条路比下载数据集更好，原因有三：

1. **是你自己的房子**，尺寸、布局、家具位置都是真的；
2. **由将要行动的那台机器人测绘**——传感器特性、视角高度、可达范围天然一致；
3. **闭环共享同一张地图**：仿真里验证过的路线与策略，对着的是真机上同一张图。

## 1. 完整链路

```
真机 RTAB-Map 建图
   └─ rtabmap.db（位姿 + 深度帧，或已优化点云）
        └─ 稠密点云 + 轨迹                    ← 已有：rtabmap_export.py
             ├─ 平面分割（地板 / 墙面）        ← 缺：RANSAC 或 Open3D
             ├─ 物体聚类 → 凸包                ← 缺：DBSCAN + convex hull
             └─ 房间分割（从地板的连通域）      ← 缺
                  └─ MuJoCo 场景
                       ├─ 地板：plane geom
                       ├─ 墙面：box geom（平面拟合直接给出）
                       ├─ 家具：凸包或包围盒
                       └─ 机器人：现有 XLeRobot 模型，放在测绘起点位姿
```

**已有的部分比想象中多**：点云读取、轨迹提取、体素降采样、LOD、占据栅格、地图产物与校验、机器人模型与放置方式——这些都已实现并测试过。

**真正缺的是一个转换器**：`点云 → MuJoCo 碰撞几何`。

## 2. 分段保真度：这是让 Real2Sim 可行的关键

不要试图用一张点云做所有事。真实世界的做法是**按用途分保真度**：

| 层 | 来源 | 保真度 | 为什么够 |
| --- | --- | --- | --- |
| **地板 / 墙面** | SLAM 点云平面拟合 | 高（平面就是平面） | 平面拟合精度远超需求，导航与避障完全够 |
| **大件家具** | SLAM 点云聚类 → 凸包 | 中 | 需要的只是"挡住去路"，形状细节无关 |
| **可操作物体** | **规范模型 + 感知给出的位姿** | 高 | 抓取需要精确几何；扫描分辨率（1m 外约 1cm）远不够 |
| **动力学** | 标定 + 物理估计 | — | 质量、摩擦从标定文档与实测来，不从点云来 |

第三行是最重要的一条：**可操作物体不要从点云重建**。红杯子在真机上应当用它的规范模型（CAD），位姿由感知给出——这正是我们场景里已经做的事（`HOME_TASK_ITEM_SPECS` 声明物体，运行时摆放）。

**这解释了一件事**：为什么"仿真里的物体"和"真机上的物体"本来就该分开对待。前者提供形状，后者提供位置。

## 3. 分阶段实施

### P1：只做静态场景（可导航）

- 点云 → 地板平面（RANSAC 找最大水平面）
- 剩余垂直平面 → 墙面 box
- 其余点云 → 体素化 + 凸包 → 家具障碍
- 输出 MuJoCo XML；机器人放在 `rtabmap` 第一个位姿
- **验收**：仿真里能走通真机上走过的同一条路线

### P2：加语义（能理解房间）

- 地板连通域 → 房间划分
- 房间命名（用户点选或从真机任务日志推断）
- 生成导航图（房间邻接），替代当前手写的 `HOME_ROUTE_EDGES`
- **验收**：`去厨房` 能解析到仿真里真实的房间几何

### P3：加可操作物体（能完成任务）

- 规范模型库（杯子/瓶子/盘子…）声明形状
- 位姿从实时感知来（仿真里由 RGB-D 检测给出，与真机同一条链路）
- **验收**：同一个自然语言任务在仿真与真机上产生相同的工具调用序列

## 4. Replica 的位置：它是"没有真机测绘时的替身"

Replica **不是 Real2Sim 的路径**，但它有价值：在还没有真机测绘成果时，提供一个**复杂度真实**的环境来开发上面那条 P1→P2→P3 的转换链路。

而且关键在于：**转换器的输入是点云**。Replica 场景与真机测绘成果都能转成点云，所以**同一个转换器两边都能用**——先在 Replica 上把转换器调通，等真机测绘出来直接接上。

这就是把 Replica 从"另一个房子"变成"测试夹具"的方式。

## 5. 现实约束（必须说清）

| 约束 | 影响 |
| --- | --- |
| SLAM 点云在玻璃、镜面、深色表面上缺失 | 这些区域在仿真里会变成"洞"，需要用户补扫或手工补几何 |
| 点云没有语义 | P2 的房间划分需要用户确认，不能全自动 |
| 扫描分辨率不足以重建小物体 | P3 必须用规范模型，不能靠扫描 |
| 单次建图的漂移 | 长走廊会弯曲；P1 验收前需要检查回环是否闭合 |
| MuJoCo 用凸包做网格碰撞 | 凹形家具（书架、桌下空间）会被填实，需要分块凸分解 |

最后一条是最容易低估的：**MuJoCo 的 mesh 碰撞体是凸包**。一张整屋网格会变成实心块，所以必须拆分——这正是 P1 里"平面拟合 + 分区凸包"比"直接丢整张网格"更重要的原因。

## 6. 与现有代码的衔接

| 环节 | 现状 |
| --- | --- |
| 读真机 SLAM 数据库 | ✅ `rtabmap_export.py`（已对真实 208MB 库验证） |
| 点云 → 地图产物 | ✅ `map_pipeline.py`（体素降采样、LOD、占据栅格、校验） |
| 仿真测绘（无真机时） | ✅ `scripts/build_sim_map.py`（驱动机器人走完 9 段路线） |
| 机器人模型与放置 | ✅ `xlerobot_home.xml` + 运行时摆放约定 |
| **点云 → MuJoCo 碰撞几何** | ❌ **缺这个转换器，是 Real2Sim 的核心** |
| 房间分割与导航图生成 | ❌ 缺 |
| 规范物体模型库 | ❌ 缺（当前物体是代码里声明的几何体） |

**结论：Real2Sim 的工程量集中在 P1 的转换器上，而不是在获取场景数据上。** 数据已经能从真机拿到了。
