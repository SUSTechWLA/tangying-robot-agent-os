更新：2026-09-15。本文回答三个问题：**现在这套系统处于什么水平**、**下一步该优化什么、按什么顺序**、**每一项怎么用对照实验证明真的变好了**。
范围约定：**不做框架级重构**；如果某项需要新增功能或模块，必须写清"为什么非加不可"，而不是"架构上更漂亮"。

## 一、当前系统评价

### 1.1 规模与验证基线（本机实测，非估计）

| 维度 | 现状 |
| --- | --- |
| 代码 | `robot/` 33.0k 行、`sim/` 19.4k、`web/` 15.7k、`fleet/` 10.0k、`edge/` 9.0k、`core/` 4.1k、`tasks/` 3.4k、`console/` 3.4k；Go 53 个包 |
| 测试 | Python 1641 通过 / 34 跳过；Web 375 通过；Go 全包通过；`make lint` 干净；`tools.json`（28 个工具）有 CI 校验 |
| 文档 | `docs/` 93 篇 markdown / 44.7k 行，按"你想做什么"组织 |
| 主线闭环 | 从零自动勘测 → 保存并启用地图 → 自然语言任务（`inspect-kitchen`、`patrol`、`mug-transfer`）4 个任务全成功、0 重试、0 复位 |
| SLAM | 无漂移 ATE 0.2–8.5 mm；注入 5%/10% 里程计漂移后 ATE 113–134 mm，仍优于纯里程计 179–212 mm |
| 语义层 | 物体层随地图发布（真实勘测：130 次轮询 / 12 次目击 / 3 个实例，位置误差 0.5–2 cm）；工作区可达位姿规划中位 9 ms 给 8 个候选 |
| 前端 | 控制台 6 个面板、关键帧检视、任务回放、地图放大看物体标签 |

**一句话评价**：这是一个**接口与证据先行、单机主线已经跑通、量化验收习惯已经建立**的系统；它的短板不在"能不能跑"，而在**系统自己产不出性能数据**、**已有收益还没进任务执行路径**、以及**实机维度完全空白**。

### 1.2 真正的强项（有证据支撑）

1. **契约与证据闭环**：Harness 不接受"工具调用成功"作为完成依据；未知物理结果永久禁止重放（`edge/agent/recovery_test.go`）；低 fence 完成被拒且不写事件（`fleet/coordinator/revisions_test.go`）；队列宕机不破坏任务图（`fleet/coordinator/coordinator_test.go`）。这些不是设计声明，是能跑的测试。
2. **语义层分层正确**：地点（勘测登记）/ 工作区（随地图发布）/ 物体（运行时观测 + 年龄）三者写者与新鲜度语义分开，避免了"把过期坐标当事实"。
3. **量化验收文化**：`scripts/evaluate_slam.py`、`scripts/benchmark_semantic_layer.py`、家居验收脚本、`tools.json --check` 都是"改动必须给出数字"的基础设施。
4. **单机主线端到端**：标定 → 勘测 → 地图启用 → 自然语言任务 → 证据回放，一条链没有断点。
5. **文档密度与口径纪律**：连宣传材料都要求"每句话指得出实现或测试"。

## 二、重点优化方向（按重要程度排序）

每一项给出四段：**为什么需要（为什么非加不可）→ 增加什么 → 对比实验 → 判据与风险**。

### P0-1 上机性能遥测：让"运行时间 / 资源 / 响应"变成系统自己的数据

**为什么需要。** 你要求后续每个模块都用对比实验量化，但目前**基线只能靠外部脚本**：`scripts/benchmark_semantic_layer.py` 是我在进程外测的，真实任务链路的耗时只能靠控制台前端推算（`web/task_trace.js`）。这带来三个具体问题：① 线上退化无法发现（没有人会每天手动跑基准）；② 无法回答"复杂任务里哪一段最慢"；③ 每次优化都要重建一套外部测量。**这不是架构问题，是缺数据——没有测量就没有优化。**

**增加什么。** Runtime 与任务侧的最小插桩（不引入新框架）：
- 每条命令记录四段耗时：排队 / 安全准入 / 执行 / 证据核验，用单调时钟；
- 每个任务步骤记录开始、结束、重试次数；
- 一张只读汇总接口（`GET /v1/telemetry/latency`）给出按工具、按步骤类型、按机器人分组的 p50/p95/p99；
- 资源侧：进程 RSS、地图产物字节、观测帧率（与控制台已有 FPS 同源）。

**对比实验。** 同一批 20 次家居任务（客厅→厨房→抓取→放置→回客厅）：
- A：现状（无插桩，外部秒表基准）；
- B：插桩后；再对同一批任务比较 **B vs B'（修复遥测指出的最慢环节后）**。
- 指标：① 插桩开销（任务总时长增量、内存增量）；② 遥测与外部基准的一致性（同一任务耗时偏差）；③ 能否定位到"最慢的 3 个步骤"；④ B' 相对 B 的 p95 改善。

**判据。** 插桩开销 < 1% 总时长、< 1 MiB 内存；与外部基准偏差 < 5%；数据缺失率 0（每个步骤都有四段耗时）；修复后 p95 至少 −15%。风险：计时本身引入锁竞争——用无锁累加 + 批量落盘规避。

### P0-2 把语义层接进任务计划：回忆 → 规划 → 导航

**为什么需要。** 今天的对比实验已经证明："到工作区"与"看得见目标"是两件事（复杂任务 0/5 → 5/5），而且**抽样 3 个登记工作区里 2 个在新地图上已不可通行**。但这份收益目前只存在于工具层：Go 计划仍按 `RouteGoals`（登记点）派发（`skills/manipulation/plugin.go:81`）。**要让家居任务吃到它，必须在计划里插入三步**——这是能力缺口，不是重构。

**增加什么。** 计划模板新增三个可选步骤与回退链：`recall_object`（取上次看到的位置与年龄）→ `plan_work_area`（拿可达候选）→ `navigate_to_pose`（去候选位姿），并新增失败回退"回忆过期 → 去工作区候选位姿观察一次再决定"。核验仍用返回的 `final_pose`，闭环语义不变。

**对比实验。** 家居验收套件（含"目标不在登记点视野内"的用例）各跑 10 轮：
- A：现状（登记点导航）；
- B：回忆 + 候选位姿。
- 指标：① 任务成功率；② "首次到达即可见目标"比例；③ 无效行驶距离（到达后未找到目标的那段）；④ 端到端 p95 延迟；⑤ 可恢复失败次数。

**判据。** 成功率 +≥15 个百分点；无效行驶 −50%；p95 不劣化超过 5%（多走的合理路程要单独列出，不做隐藏）。风险：回忆位置过期导致白跑——用年龄上限 + 二次观察兜底。

### P1-3 长走廊轴向退化的在线检测与处理

**为什么需要。** 这是当前 SLAM 的最后一块硬骨头：注入漂移后 ATE 113–134 mm，主要来自长走廊轴向不可观测（几何上无约束）；它还直接制造"导航到了但地图是歪的"和走廊幽灵墙。**现有系统知道自己"漂了"，但不知道自己"在某些方向上不可观测"。**

**增加什么。** 在线退化判据 + 应对策略（不需要新框架）：用配准残差/信息矩阵条件数判断"沿轴不可观测"，退化时 ① 限制速度并提示；② 优先横向 landmark；③ 地图里标记"轴向不可信区域"，导航在该区域提高安全余量；④ 要求一次闭环或人工确认才把该区域标为可导航。

**对比实验。** 两条路线（长走廊往返、整屋一圈），里程计漂移注入 0% / 5% / 10%，各 5 次：
- A：现状；B：加退化检测与策略。
- 指标：① ATE / RPE；② 回环接受率与误接受；③ 退化告警的准确率 / 召回率；④ 导航失败率（`GOAL_NOT_CLEAR`、碰撞拒止）。

**判据。** 漂移场景 ATE 至少 −40%；退化告警误报 < 10%、召回 > 80%；导航失败率下降且**不允许把失败变成"更慢但更安全"以外的其他代价**（时间增量 < 10%）。风险：过度保守会让勘测变慢——所以把时间增量写成判据。

### P1-4 从零扫全的完成度与时间

**为什么需要。** "开箱即用"的第一印象就是"一次扫完"。现在实测 81% 覆盖是被 `frame_budget`/期限停下的；用户看到的是"没扫完"，而不是"扫到够用了"。

**增加什么。** 停止判据从"预算/前沿耗尽"改成**房间级完成度 + 信息增益**：每个已识别房间达到"最小通过门限"（登记点可直接通行 + 关键通道两侧净空），并且继续探索的边际信息增益低于阈值时才停；控制台显示"剩余未知区域 + 预计还需几分钟"。

**对比实验。** 同一场景 10 次从零勘测：
- A：现状；B：完成度判据。
- 指标：① 达到"全部房间登记点可通行"的达成率与所需时间/行驶距离；② 是否需人工干预；③ 地图质量（ATE、可导航比例）；④ 预算利用率。

**判据。** 达标率 ≥ 90%（现状基线需同时测出）；中位时间 −25%；ATE 不劣化 > 10%。风险：判据可能过早停止——用"未知区域占比"作为辅助指标同时报告。

### P2-5 语义层的多视角一致性过滤与索引化

**为什么需要。** 物体层现在直接决定"去哪里找"，而真实勘测里 3 个实例中有 1 个是**单次目击的检测器误报**——那会让机器人白跑一次。另外关联是线性扫描：512 个实例时单次轮询 53.9 ms（实测），实例再涨就吃掉轮询预算。

**增加什么。** ① 可信度分级：≥2 个不同视角/关键帧的实例进"可信"，单次目击进"待确认"（保留、可显示、不作为目的地）；② 关联换空间索引（栅格哈希），把 O(n²) 降到近似 O(n)。

**对比实验。** 回放同一批真实勘测数据（含已知误报）并注入合成噪声：
- A：现状；B：一致性过滤 + 索引。
- 指标：① 对真值物体的精度 / 召回；② "错误目的地"比例（去了却找不到）；③ 检索 p95 延迟与内存；④ 单次轮询关联耗时（12 / 128 / 512 实例三档）。

**判据。** 错误目的地 −80%；召回下降 ≤ 5%；512 实例轮询从 53.9 ms 降到 < 5 ms。风险：过滤过严会丢掉"只出现过一次"的真物体——所以召回写进判据，并允许调用方显式请求"含待确认"。

### P2-6 文档与代码的一致性校验

**为什么需要。** 文档是本项目的主要交付面之一（93 篇），但已经出现漂移：`v1-release-status.md` 停在 v0.3.0 / 2026-09-11；宣传材料要求"每句话指得出处"，这轮我只能**人工**核对了 11 个测试引用（全部正确，但成本是分钟级且无法回归）。文档漂移会直接损害"证据链"这个核心卖点。

**增加什么。** 一个引用校验脚本（`tools.json --check` 已有先例）：扫描文档里的测试函数名、文件路径、工具名、常量，断言存在；发布时自动把"本次验证记录"追加到状态页；CI 增量运行。

**对比实验。** 对当前 93 篇文档：
- A：人工核对（以本轮人工核对 11 个引用为基准，记录耗时与漏检）；
- B：脚本核对。
- 指标：① 检出率（人为注入 20 个失效引用做基准）；② 误报率；③ 耗时；④ CI 增量时长。

**判据。** 注入失效引用检出率 ≥ 95%、误报 < 5%、CI 增量 < 10 s。风险：文档里的示例代码会误报——用白名单标注示例块。

### P3-7 学习型策略的最小闭环（policy sidecar 的首个消费者）

**为什么需要。** `PolicyExecution` 契约早就写好，但没有运行时消费者（`contracts.py:265` 只强制 deterministic 走本地路径）。真实抓取成功率是 Sim2Real 的头号未验证项，而没有消费者就无法开始积累数据。**这是"为什么非加不可"：策略能力必须有第一条通路，哪怕先用不需要训练数据的确定性技能策略。**

**增加什么。** 把"抓取位姿选择"从固定参考控制器改成**感知闭环的确定性技能策略**，作为 sidecar 的第一个消费者；契约、manifest 哈希、观测/动作约束沿用现有定义。

**对比实验。** 参考工位 50 次抓取：A 固定控制器 vs B 技能策略。
- 指标：① 成功率；② 平均尝试次数；③ 每次耗时；④ 失败分布（未达 / 遮挡 / 滑落 / 超时）。

**判据。** 成功率 +10 个百分点；尝试次数 −20%；失败分布要能区分"策略问题"与"感知问题"。风险：仿真工位的成功不代表实机——结论只写"仿真工位"。

### P3-8 影子模式：不动机器人也能拿到的真机证据

**为什么需要。** S5 的 12 项实机验收在本机一条都做不了，但这不等于"什么都做不了"：**感知与建图的数据通路可以先接真机数据，不驱动底盘与机械臂**。这能提前暴露标定残差、帧率、点云密度、检测一致性这些只在真实数据上出现的问题。

**增加什么。** 只读影子模式：接入真实相机（或录制数据集），跑同一套重建 / 检测 / 地图 / 语义层管线，产出"仿真 vs 真实"的差异报告；任何运动命令一律拒绝（默认 stowed、无使能）。

**对比实验。** 同一房间：仿真数据 vs 真机（或录制）数据各 10 分钟。
- 指标：① 帧率与端到端延迟；② 标定残差；③ 同一物体位置的观测方差；④ 地图可导航比例；⑤ 语义层实例一致性（与仿真真值对比）。

**判据。** 第一版**不设性能门槛**，只要求"能跑通并给出量化差距"；达到差异可解释（每个指标都有归因）即算通过。风险：没有硬件时用录制数据集代替，结论要标明来源。

## 三、排序理由与明确不做的事

**为什么是这个顺序。**
- **P0-1 先做**：它是"后续每一项优化都要用到的尺子"。没有它，后面所有对比实验都得重建外部脚本，也无法发现线上退化。
- **P0-2 紧随**：收益已经测出来（0/5 → 5/5），只差接进执行路径，属于"最低成本、最高确定性"的一步。
- **P1-3、P1-4** 是主线成败的两块硬骨头（地图质量与扫全体验），都在 SLAM 主线上，且都有现成的评测夹具（`scripts/evaluate_slam.py`）可扩展。
- **P2** 是质量与可信度：语义层精度、文档一致性。它们不阻塞主线，但决定"能不能被信任"。
- **P3** 依赖外部条件（数据/硬件/模型），先把通路建起来，不承诺指标。

**明确不做（本轮范围外）**：任何框架级重构；多主 HA 与跨地域；通用家务与开放域理解；把仿真结论包装成实机安全认证。理由：这些要么不影响当前主线，要么需要外部条件，做了也无法用对比实验证明收益。

**每一项的新增都必须能回答一句话**："不加它，哪一个具体任务会失败或无法衡量？"——上文每一节的"为什么需要"就是这句话的答案。

## 四、建议的下一步

1. **P0-1 + P0-2 并行**：P0-1 只动 Runtime/Task 的采集与一个只读接口（无行为变化，风险最低）；P0-2 只动计划模板与回退链。两者都能在现有夹具上做对照实验。
