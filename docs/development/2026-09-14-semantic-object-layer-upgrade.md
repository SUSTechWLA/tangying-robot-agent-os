# 语义层升级：物体记忆（`map.objects.v1`）与工作区可达位姿

**目标**：让地图回答第三个问题——"这个东西上次是在哪儿看到的"，并把"目的地"从单个登记点变成一组可达位姿。
**方法**：同一张地图、同一个脚本化机器人、同一个检测器，只切换语义层（baseline / upgraded），在四个维度上量化差异。
**可复现**：`.venv/bin/python scripts/benchmark_semantic_layer.py --output artifacts/semantic-benchmark/run-1`
**本次实测数据**：`artifacts/semantic-benchmark/run-1/report.json`（40,000 点地图 + 12 条物体记录，25 次采样）

---

## 1. 为什么要改：两个具体失效

**失效一：到了现场不等于看得见。**
家居验收里出现过 `RECOVERABLE_FAILURE GOAL_NOT_CLEAR`：任务要"去厨房拿杯子"，系统只知道**房间**，于是开到登记的厨房停靠点；而杯子在停靠点视野之外，或者停靠点本身在当前地图上已被判不可通行。此时系统手里没有任何"该去哪里找"的信息，只能报可恢复失败——**不是能力不足，是地图没记住**。

**失效二：目的地只有一个点，而这个点经常不能用。**
这张地图上实测（0.05 m 栅格、0.32 m 底盘包络，判据与路由器一致）：

| 登记工作区 | 登记点周围 0.32 m 内的非自由格 | 路由器结果 |
| --- | --- | --- |
| kitchen (2.05, 3.00) | **12** | `GOAL_NOT_CLEAR`：开不进去 |
| living_room (0.0, −1.25) | **11** | `GOAL_NOT_CLEAR` |
| home_corridor (0.0, 1.85) | 0 | 可通行 |

也就是说，**抽样 3 个登记点里有 2 个在新地图上已经不可用**。登记点是勘测时选的一个点，它不该是唯一选项。

---

## 2. 改了什么

### 2.1 物体层随地图发布（`object_memory.py` → `objects.json`）

- 建图期间以 **1 Hz** 向驱动索取一次感知实体（`WorkflowBindings.observe_entities`，走的是与 `observe_scene` 完全相同的观测路径，纯读取），按地图锚点折算到地图坐标系累积；
- 发布地图时**重新锚定**到最终锚点（与点云走同一个锚点，避免"点云换了坐标系、物体没换"）；
- 三条规则让它算证据：**只有观测进来的才算**（commissioned 目录依旧不含测量位姿）；**每次目击都带时间**（`lastSeenUnixMs` / `ageMs` / `sightings`）；**关联有上限**（同类别、属性不矛盾、0.12 m 门限内才归为同一实例，被移动的物体变成新实例而不是瞬移的旧实例）；
- 续建（`baseMapId`）继承上一段地图的物体层，但**保留各自的时间戳**——旧目击不会因为被继承就变新鲜。

### 2.2 目的地 = 可达位姿集合（`plan_work_area` / `navigate_to_work_area`）

`workspace_planner` 与 `map_catalog.plan` 此前只在测试里注册。现在：

- `plan_work_area(location_name)` 进入生产工具面，按当前地图、底盘足迹、机械臂包络给出**排序后的可达底盘候选**；
- `navigate_to_work_area(location_name, candidate_index)` 是**组合技能**：先规划，再经原子工具 `navigate_to_pose` 驱动到某个候选，并**回报实际下达的位姿**。它不偷偷调整目标——调用方必须用返回的 `final_pose` 再做一次到达核验，闭环契约因此针对"真正下达的动作"成立；
- 未配置地图提供者时两者**仍然注册**并给出明确拒绝，而不是从工具表里消失（能力必须可被发现：工具数 25 → 28）。

### 2.3 地图放大看细节（控制台）

地图面板新增"地图里的物体"一节：物体标签**随相机距离出现**（≤4 m，可勾选开关），形如 `white cup · 3 小时前`；点击条目把相机定位到该物体。没有物体层的历史地图会说明原因，几何与关键帧不受影响。

## 3. 对比实验：四个维度

### 3.1 运行时间（对方可复现，单位 ms，25 次采样）

| 指标 | baseline | upgraded | 说明 |
| --- | --- | --- | --- |
| "物体在哪"（`recall_object`） | **无法回答**（工具不存在） | 中位 **1.43** · P95 **1.64** | 读地图内的层 + 按年龄过滤 |
| "工作区哪里能站"（`plan_work_area`） | 只有 1 个登记点，无候选概念 | 中位 **9.05** · P95 9.30（真实地图上 3.4–17.3） | 8 个候选，含净空与臂展筛选 |
| 加层本身的边际成本（每次感知轮询） | — | **0.058**（12 个物体） | 关联是线性扫描 |
| 发布时一次性成本（`document` + 重锚定） | — | 0.025 + 0.025 | 每段地图一次 |

**接入驱动的成本**：轮询复用普通观测路径，实测一次感知（渲染 + 检测 + 打包）**中位 41.7 ms、P95 63.0 ms**；按 1 Hz 轮询占一秒钟的 **4.2%**，而且这条路径本来就是控制台 `observe_scene` 在用的路径，没有新增传感器工作。

### 3.2 占用资源

| 指标 | baseline | upgraded |
| --- | --- | --- |
| 地图产物总字节（40k 点合成地图） | 2,185,007 | 2,192,278（**+7,271**，+0.33%） |
| 单条物体记录 | — | **606 B/条** |
| 真实地图实测（220 帧勘测，40k→ ? 点） | 无 `objects` 角色 | **3,367 B**（130 次轮询 / 12 次目击 / 3 个实例） |
| 检索一次峰值内存 | — | **1.6 MiB**（含 JSON 解析；层本身 KB 级） |
| 层规模上限 | — | 512 条（约 165 KB，见下表） |

**扩展性（每次轮询的关联成本）**：

| 物体数 | observe (ms) | document (ms) | 文档字节 |
| --- | --- | --- | --- |
| 12 | 0.058 | 0.025 | 4,072 |
| 128 | 3.06 | 0.177 | 41,321 |
| 512（预算上限） | **53.9** | 0.760 | 165,593 |

**这条曲线是已知瓶颈**：关联是"每个实体扫描全部实例"的线性做法，512 个实例时单次轮询 54 ms。1 Hz 下仍只占 5.4% CPU，但实例再涨就该换成空间哈希/栅格索引——列进下一步。

### 3.3 复杂任务执行情况（脚本化，同机器人同地图同检测器，5 次）

任务："去厨房拿杯子，放进收纳盘"（检测器只在物体真值 0.6 m 内报告它——模拟真实桌面检测器的可见范围）。

| 指标 | baseline | upgraded |
| --- | --- | --- |
| 交付成功率 | **0 / 5（0%）** | **5 / 5（100%）** |
| 平均工具步骤 | 2（走 → 检测失败即结束） | 6（回忆 → 走 → 检测 → 抓 → 放 → 核验） |
| 平均行驶距离 | 3.76 m（走到登记点，**白跑**） | 8.04 m（去上次看到的位置，更远） |
| 失败次数 | 5 | 0 |

baseline 的失败不是"走得不好"，而是**它没有可以去的第二个地方**：登记点不在目标视野内，它就再也没有下一步——那 3.76 m 是纯浪费。升级后系统愿意多走 4.3 m 去"上次看到的位置"，把失败换成成功。**这一项的收益不是省时间，而是把 0 变成 1**；代价写在明处：更长的路程与 1.4 ms 的检索。

**真实勘测的交叉验证**（220 帧、`--mode survey`，地图 `scan-9bd97f00b5c4`）：物体层记录了 3 个实例，其中真值 `收纳盘 (2.46, 3.335)` 记为 `(2.46, 3.33)`（差 0.5 cm），`陶瓷杯 (2.275, 3.415)` 记为 `(2.27, 3.41)`（差约 2 cm）——**位置精度在厘米级**，与检测器本身一致。

同一次勘测里还留下一个**只有 1 次目击**的 `cup` 实例（检测器的形状误报）。它的存在恰好验证了 `sightings` 字段的价值：调用方可以据此不信任它，而不是被一个"看起来很确定"的位置骗过去。

### 3.4 任务执行响应（25 次采样）

| 指标 | baseline | upgraded |
| --- | --- | --- |
| 问"物体在哪"的返回 | 拒绝，中位 **0.003 ms**（没有答案） | 命中，中位 **1.54 ms**、最大 1.76 ms（可直接当目的地） |
| 问"工作区哪里能站"的返回 | 拒绝，中位 0.003 ms | 8 个候选，中位 9.64 ms、最大 13.5 ms |
| 从"收到目标"到"有可执行目的地" | **不成立**（无目的地可给） | ≤ 14 ms（工具层），叠加感知 42 ms（如需现场确认） |

结论很直接：**升级不是把某个动作变快，而是把"做不下去"变成"10 毫秒内拿到一个可执行的下一步"**。对上层任务而言，省掉的是一整次白跑的导航（上表 3.7 m）和一次可恢复失败。

## 4. 为什么这样提升（机制，而不是调参）

1. **把"地点"和"物体"分开存**。地点是勘测时登记的，物体是运行时观测出来的；混在一张表里就会像以前那样：commissioned 目录要么携带会过期的测量位姿，要么什么位置都没有。现在两者各有明确的写者与新鲜度语义。
2. **一切位置都带年龄**。`ageMs` 让"上次看到"和"现在在这儿"无法被混用；检索默认按年龄过滤，过期条目干脆不发布。这是把"记忆"变成"证据"的关键一步。
3. **关联门限让移动可见**。物体被挪走超过 0.12 m 就生成新实例，旧实例留在历史里——地图于是能表达"它以前在那儿"，而不是绘制一条瞬移轨迹。
4. **目的地不再是一个点**。单个登记点既可能被新地图判为不可通行，也可能贴着桌子角（余量 5 mm 那种）。把"目的地"换成"工作区 + 可达候选集"，就把**地图质量**与**能不能出任务**解耦了：地图差一点，只是候选排序变差，不再直接变成任务失败。
5. **组合技能不加新能力**。`navigate_to_work_area` 走的是同一个原子导航工具，因此安全准入、日志、闭环核验都与其它命令一致；它唯一多做的是"选一个位姿并如实回报"。

---

## 5. 边界与下一步

- **本层的消费者目前是工具层/MCP**：Go 任务计划仍按登记点下发导航。要让家居任务真正吃到这份收益，需要在任务计划里插入"回忆 → 规划 → 导航"三步（计划改动，不含新能力）。
- **检测器决定层的内容**：误报会进地图（本次勘测出现 1 例单次目击）。`sightings` 与 `ageMs` 是当前的判据；后续可加"多视角一致性"过滤（同一实例需 ≥2 个不同视角）。
- **关联是线性的**：512 实例时单次轮询 54 ms。实例规模再上一个量级就换空间索引。
- **没有验证"跨天"**：24 小时过期、继承保留时间戳都已实现并有单测，但没有跨天真实数据。
- **未做端到端任务级 A/B**：本次复杂任务是脚本化对照组（同机器人、同地图、同检测器），不是家居验收套件的重跑；套件级对照需要先把上面第一条的计划改动做掉。
